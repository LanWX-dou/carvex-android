# 仪表专辑图片传输

旧实现只转发文字，发现宿主图片字段时记录未实现日志。新增会话内图片加载器及
iAP2 service=1 文件传输；只在已认证运行链路且 5000 选择 group=0/attribute=0x1a 时启动。
5001 图片 ID 的 Link ACK、文件 Setup、接收端 Start、数据 ACK 和 Success 是独立步骤。
换歌/停止取消旧传输；旧回调按对象及链路代际隔离，待取消确认的 ID 不复用。
文件包单独路由，不参与控制消息 CSM 的分片重组。运行期回调通过队列交给图片状态机，
避免发布器锁与文件 ACK 回调形成反向锁顺序。

## 原镜像依据

研究仓库 `research/protocol/iap2_input_business_lifecycle/source/firmware/accessoryd`，
24A446，SHA256 `2b0a2010e6d2605e07d87f05659c932e03de34476a76431196a9bb58da7dc4fe`。
本次直接使用 NDK llvm-objdump 核对原指令，未以自动反编译文本代替证据：

- `0x10014600c` 选择 service 1；`0x100146024` 分配文件 ID。
- `0x100146060` 调用 `0x10000431c`，该 helper 返回 type=2；TypeData 的 NULL 数据
  分支在 `0x10006d514` 保存 type=2、扩展长度=0。
- `0x1001461c0..0x1001461d8` 写 group 0/attribute 0x1a 的 U8 ID；
  `0x100146258` 注册发送完成回调。`0x100081608` → `0x10014aee8` →
  `0x10014b23c..0x10014b25c` 在 ID 发送完成后启动图片缓冲传输，stream=false。
- `0x10006c034..0x10006c048` 写 ID、Setup=4、BE64 长度。v1 为 10 字节
  (`0x10006c32c` → `0x10006c688`)；v2 在 `0x10006c054..0x10006c06c`
  增加 BE16 type=2，固定部分为 12 字节。
- `0x10006c1b0..0x10006c1c8` 写数据头和首包标志 0x80；
  `0x10006c364..0x10006c36c` 写末包标志 0x40。
- `0x10006dedc` 取控制操作；Start=1 在 `0x10006e658` 从等待/暂停进入发送；
  Cancel=2 在 `0x10006e4a4` 回应取消；Pause=3 在 `0x10006e314` 回应暂停。
  Success=5/Failure=6 仅结束已发送最后数据的传输。
- `0x10006d00c..0x10006d020` 对 device 模式的发送 ID 设置高位，分配范围 128..255。

## 本端资源策略与限制

接受 Bitmap、图片字节、content/resource URI、HTTP(S) 图片地址；禁止自动 HTTP 重定向。
源数据最多 2 MiB，输出最长边 512 像素、JPEG quality=85、最多 512 KiB；读取超时 5 秒，
文件响应超时 30 秒后取消，不自动重试。这些是本端资源上限，不声称来自 Apple 协议。
部分元数据更新不清除同曲图片，换曲先清旧图；慢加载结果不能覆盖新曲。
未支持 file URI/base64 字符串。日志只记录大小、传输阶段及错误类别，不记录 URL。

原设备日志只证明 cover/coverUrl 键存在，没有图片类型/可访问性或本会话初始订阅信息。
因此显示结果保持 OPEN；需检查车机文件会话协商、图片订阅及 accepted/rejected 日志。
