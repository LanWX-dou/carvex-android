# 00 范围与术语

> 本文件定义本规范管什么、不管什么、条款怎么读。

## 00.1 方向

**R-0.1（MUST / CONFIRMED）** 本规范描述**发送方向**：设备侧（客户端）把屏幕画面编码、封装、加密后发给车机；车机是接收与显示端。规范中的"必须发送""必须处理"均以客户端为主语。

依据：`A00.3`。

**R-0.2（MUST / CONFIRMED）** 实现必须在 TCP 记录帧变体与 UDP/RTP 变体之间**显式选择**，并只使用所选变体的字段与流程；不得把两者的 SETUP 字段、记录格式或时间戳语义混用。

依据：`A00.3`、`A01.1`、`A01.7`。

## 00.2 术语

| 术语 | 定义 |
|---|---|
| 屏幕流 | 承载车机主画面的一条媒体流；本规范的对象 |
| 记录 | 128 字节头 + 载荷的自描述单元 |
| 帧记录 | 类型 0 的记录，载荷是一帧已编码画面 |
| 配置记录 | 类型1的记录；部分头字段含显示/时间数据，配置载荷及参数集布局仍待核 |
| 关键帧 | 可独立解码的帧；本规范只约束"何时必须产生"，不约束码流内 NAL 类型 |
| 协商数据 | AVC 协商器输出的二进制串，随建流传递 |
| 呈现模式 | 同一显示的一种呈现配置（分辨率/HDR 等） |

## 00.3 证据等级

**R-0.3（MUST / CONFIRMED）** 条款的证据等级只有两级：`CONFIRMED` 表示结论可回落到 `source/asm/` 的指令地址；`INFERRED` 表示只到调用形状/参数传递。任何 `OPEN` 的问题不得写成 `MUST`。

依据：`A00.5`。

## 00.4 不覆盖

**R-0.4（未定义 / CONFIRMED）** 本规范不定义：AirPlay 控制面（RTSP/HTTP）本身、音频与麦克风、输入事件、FairPlay 算法与密钥体系、对端解码器的内部实现。

依据：`A00.4`、`A04.1`。

## 00.5 记录头不可省

**R-0.5（MUST / CONFIRMED）** 本文已核TCP记录变体必须保留完整128B头，不能推广到尚未核验的UDP/RTP打包；不得为了省带宽裁剪、压缩或按 64 位对齐重排头字段。

依据：`A02.1`、`A02.2`。
