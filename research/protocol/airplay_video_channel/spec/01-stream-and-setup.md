# 01 视频流标识与 SETUP

> 回答第 1 项覆盖要求：用哪个类型、走哪条传输、SETUP 要交换什么。

## 01.1 类型

**R-1.1（MUST / CONFIRMED）** 已核无display入参分支向流对象+0x58写入110（0x6e）；这不能独自证明所有“主屏”都必须选110。有display时还需核比较与选择规则。

依据：`A01.2`。

**R-1.2（未定义 / OPEN）** 类型 **111（`0x6f`）** 的存在已证（`cinc …, eq` 分支），但其"主屏还是副屏"的语义、以及触发它的比较方向未闭合；实现不得在未取得显示 UUID 的情况下使用 111。

依据：`A01.3`。

## 01.2 建流前置

**R-1.3（SHOULD / INFERRED）** 应依据目标端点实际显示能力选择编码与几何。UUID、PixelSize、PhysicalSize等目前是内部显示字典取证，不是已证线上必填字段集合；可选项、默认值及缺失错误应逐个核验，不能规定缺任何一项都失败。

依据：`A01.4`、`A01.5`。

**R-1.4（SHOULD / INFERRED）** 可按已核CarPlay逐display构造流对象的路径组织实现；这不是所有profile“一显示必定一流”的线上强制约束，多屏组合与限制仍待核。

依据：`A01.4`、`A01.5`。

## 01.3 SETUP

**R-1.5（SHOULD / INFERRED）** 应校验SETUP返回的流身份、类型及参数是否符合请求与已支持profile。不应只用类型范围比较证明固件执行了“响应type等于请求type”检查；当前引用的sub/cmp仅证明类型分派。

依据：`A01.6`。

**R-1.6（MUST / INFERRED）** TCP 变体下，发送端是**主动连接方**：连接对端在 SETUP 响应中给出的数据端口，而不是监听。

依据：`A01.6`、`A00.3`（说明：端口方向来自 `APTransport`，未纳入本阶段 `source/`，故为 `INFERRED`）。

**R-1.7（未定义 / OPEN）** negotiationData/negotiatedBlob存在，但其必填条件、编码与空值行为未闭合；不能规定空blob被拒必然可恢复，需核对具体返回与会话状态。

依据：`A01.8`。

**R-1.8（未定义 / OPEN）** TCP变体SETUP请求体完整字段清单未闭合；应继续追构造器并以真实请求响应核验，不能将“发送猜测的最小请求再补齐”写成兼容方案。

依据：`A01.6`。

## 01.4 传输选择

**R-1.9（SHOULD / INFERRED）** 选择 UDP 变体时，传输描述必须是 `RTP/AVP/UDP`，且该变体自行构造 SETUP、自行解析响应；不得复用 TCP 变体的流描述。

依据：`A01.7`。

**R-1.10（未定义 / OPEN）** "何时选 TCP、何时选 UDP"的判定条件未闭合（对端能力位 `hasUDPMirroringSupport` 存在，但选择逻辑未读）。

依据：`A01.7`、`A00.3`。
