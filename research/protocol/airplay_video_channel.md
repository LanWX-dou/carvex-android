# 视频通道 — 任务要求（airplay_video_channel）

> **历史任务书**：本文件是上游任务书，现行版本以 `research/protocol/airplay_video_channel/TASK.md` 为准；本文件保留用于追溯，不再单独修订。


> 本文件是任务书，不是协议规范。角色已按项目总目标校正：另一平台扮演iPhone，向CarPlay车机发送视频；不是把该客户端做成车机接收器。
> 当前成果与未决见 [STATUS](airplay_video_channel/STATUS.md)。任务要求不代表功能已实现。

## 0. 定位

依赖建链、认证、IP/发现、AirPlay控制和密钥接口，完成设备端的编码、参数集管理、
协商、记录/传输封装、加密、发送、时间同步及断线恢复。
接收解密/解码器用于独立验收和解释对端约束，不是产品方向。
TCP记录与UDP/RTP变体分别取证，不预设所有CarPlay视频都走RTP。

## 1. 目标与完成判据

使第三方可按文档实现设备侧视频发送，并以车机持续显示、模式变化与恢复验证。

1. 以下12项均有定位到原指令/字节/运行样本的依据；未闭合的项登记OPEN，不将登记本身当功能完成。
2. 至少一段由设备侧实现产生的真实流可在目标车机稳定显示，并可独立解码核对。
3. 提供记录/访问单元/参数集测试向量；适用UDP/RTP时另有NAL分片/聚合测试。
4. 有派生、加密边界、长度、状态推进及错误负例；不以明文降级替代加密实现。
5. 有关键帧请求、断线重连、丢包/背压及画面恢复测试。
6. 校验脚本可复现静态与合成结果，真实回放明确依赖和缺失材料。
7. 不把解出一帧、结构自检通过或一台车机成功写成全profile兼容。

## 2. 证据

| 素材 | 目的与限制 |
|---|---|
| Sender原始镜像/切片/C | 确认发送顺序、字段、ABI和状态；C伪签名须由汇编核对 |
| Receiver与密码库原指令 | 约束接收格式与认证；不能自动证明Sender具体对象绑定 |
| 控制面与媒体真实抓包 | 关联profile、端口、请求响应、记录、帧及恢复 |
| 受控密钥/明文对照 | 验证密码路径；不将敏感材料提交公开日志/仓库 |
| 编码器与独立解码器 | 编码输出、参数集和目标车机解码约束 |
| RFC/编码标准 | 解释标准字段；不代替目标车机实现证据 |

## 3. 方法

先固定目标profile，再追显示/流选择与SETUP；从编码sample到记录和socket追完整数据流。
分别标出未加密长度、网络body长度、附加段、AAD、tag及nonce状态。
配置记录、关键帧、强制关键帧命令与重连需有调用链，不从类名/日志推出强制行为。
内部对象地址、队列和构造计数不作为独立实现必须复制的架构。

禁止把未知参数变成联网遍历选项，禁止从NULL cryptor推出明文授权，
禁止将局部no-op、构造成功或socket写成功当车机已认证/显示。

## 4. 抽样

至少覆盖配置/参数集与首个随机访问帧、多个后续帧、分辨率/模式变化、错误/断流与恢复、持续运行。
对实际支持的UDP/RTP模式另测单NAL、分片、聚合、乱序与丢包；
某模式未发现或不适用必须有范围说明，不能借未实现将整个传输分支宣称完成。

## 5. 十二项覆盖要求

| # | 要求 | 必须回答 |
|---|---|---|
| 1 | 视频建流 | 显示/类型、SETUP字段、端口与连接方向、TCP/UDP选择 |
| 2 | 视频封装 | 编码sample/访问单元/NAL关系，Annex-B/AVCC及转换责任 |
| 3 | 记录/传输格式 | TCP头与body边界；适用UDP时RTP及NAL打包边界 |
| 4 | 访问单元/时间戳 | 聚合/拆分责任、时间基准、间隔及相关字段 |
| 5 | 加密位置与顺序 | profile/provider/KDF、头与载荷、附加输出、nonce及错误状态 |
| 6 | SPS/PPS | 配置通路、载荷布局、传送时机及更新 |
| 7 | 关键帧 | 编码状态、头标志、forceKeyFrame及恢复行为 |
| 8 | 对端解码约束 | 协商数据、编码配置、格式限制；独立解码交叉验证 |
| 9 | 显示与同步 | 几何字段、帧率、时钟、音画同步及迟到帧 |
| 10 | 重连 | 挂起/恢复/断开、会话与密码状态有效性、重建配置 |
| 11 | 错误分类 | 原始错误、协议响应与黑屏/花屏/卡顿的证据关联 |
| 12 | 版本与性能 | 目标版本、编码差异、码率/分辨率上限和持续性能 |

重点专题：按实际变体给出完整发送顺序与接收验收；不能预写固定“RTP解析→解密→解码”来倒推发送实现。
恢复状态机必须覆盖未认证、部分建流、媒体运行、挂起及重建失败；节点名由实现选择，迁移条件由证据支撑。

## 6. 交付

现有目录 `research/protocol/airplay_video_channel/` 中保留analysis、spec、source、readable、runtime、tools、
verify.py、STATUS与manifest；复用现有来源并记录跨目录依赖，不改写原始切片或Ghidra产物。
继续补充可重放的向量、参考编解码与真实验收，不把目录存在当实现完成。

## 7. 非目标

音频/麦克风、iAP2输入、FairPlay内部算法本体及CarPlay应用UI由对应专题负责；
本专题仍须明确调用这些依赖的前置条件、生命周期和失败边界。

## 8. 风险与未决

发送cryptor绑定、nonce/附加输出、参数集、关键帧标志、时间基准及真实profile仍需核验。
抓包能补运行证据，但不能单独证明所有密码公式、模式分支和版本兼容性。
当前未决项唯一台账为 [spec08](airplay_video_channel/spec/08-open-items.md)。

## 9. 验收

- [ ] 真实设备侧发送与车机持续显示，并可独立解码；
- [ ] 记录/参数集与适用传输分片模式有向量；
- [ ] KDF/加密顺序、长度与状态有证据及负例；
- [ ] SPS/PPS/随机访问帧与强制关键帧处理正确；
- [ ] 丢包/背压/错误有分层诊断与恢复验证；
- [ ] 重连状态机和密码上下文生命周期完整；
- [ ] verify通过且真实互通验收单独记录；
- [ ] STATUS/OPEN/证据索引完整一致；
- [ ] 未把单帧解码或结构自检写成完整投屏兼容。

## 10. 一句话

本阶段是“生成并发送车机可接受的视频，正确处理协商、加密、时序和恢复”，不是实现车机接收端。
