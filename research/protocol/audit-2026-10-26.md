## 3. A1 深挖：认证协议族被混写

### 3.1 实际存在的三个消息族

| 协议族 | 消息 ID | 方向/用途 | 证据 |
|---|---|---|---|
| AccAuthentication | `0xAA00`–`0xAA06` | 车机向设备证明自己；23G90 七步样本 | `control/spec/11:20-35`；`link/spec/06:84-98`；23G90 日志 |
| DeviceAuthentication | `0xAA10`–`0xAA15` | 设备侧认证；handler 查询 feature 7 | `link/spec/06:84-98`；`analysis/14` |
| MFi4Auth | `0x5100`、`0x5110`、`0x5111`、`0x5112`、`0x5113`、`0x5115`… | `mfi4Auth_protocol_*` 的 Request/Auth 消息族 | 见下 |

### 3.2 MFi4Auth 的 ID 证据

反编译缓存中的直接立即数：

- `RequestAuthSetup` → `0x5100`：`research/protocol/iap2_link_establish/readable/ghidra/accessoryd/f_100132e28.ghidra.c:52`
- `RequestAuthStart` → `0x5110`：`f_100132fc0.ghidra.c:51`
- `AuthStart` → `0x5111`：`f_1000464e8.ghidra.c:168`
- `RequestAuthCert` → `0x5112`：`f_100048904.ghidra.c:35`
- `AuthCert` → `0x5113`：`f_1001330e0.ghidra.c:125`
- `RequestAuthChallengeResponse` → `0x5115`：`f_100044f3c.ghidra.c:33`

分派器 `research/protocol/iap2_link_establish/source/asm/accessoryd/f_100049224.s` 进一步显示：

- `0x5100` → `AuthSetup` handler `0x100045148`（`:167-173`），同时 `0x5100` 也进入 `AuthSetupFailed` `0x1000467e4`（`:207-212`）。
- `0x5110` → `AuthStart` handler `0x100046830`（`:83-88`）。
- `0x5112` → `AuthCert` handler `0x100046c78`（`:218-224`）。
- `0x5111` / `0x5113` 经掩码 `&~2` 后进入 `AuthFinish` `0x100048a1c`（`:134-140`）。
- `0x5115`…`0x5117` 另有成组分支（`:192`、`:410`）。

这说明：**MFi4Auth 的消息 ID 不是 `0xAAxx`，而是 `0x51xx`**；而且消息名与 ID 并非简单一一对应，存在同 ID 不同角色/成组处理。文档 `R-6.6.2` 只列名称、不列 ID，读者无法把它落到线上字节。

### 3.3 文档的具体问题

1. `link/spec/06:102-116` 的 `R-6.6.2` 用 `RequestAuthSetup/AuthSetup/...` 描述“认证协议的消息集”，但没有说明这是 MFi4Auth `0x51xx`，也没有给出 ID 映射。
2. `link/spec/06:149-158` 的 `R-6.6.7` 同时写了设备侧和配件侧的应答关系：
   - `RequestAuthCert → AuthCert` 是配件侧行为；
   - `AuthCert → RequestAuthCert + AuthenticationSucceeded` 是设备侧行为。
   设备侧实现者如果照全表实现，会把方向搞反。
3. `control/spec/11:20-35` 的七步是 `0xAA00/06/01/02/03/05`，与 MFi4Auth 完全不同的消息族；两处没有交叉说明。
4. `control/spec/12:48` 的 L2 自查仍写“六条认证消息”，与七步（含 `0xAA05`）不一致。

### 3.4 建议改法

新增一张“认证协议族”总表，至少包含：

| 列 | 内容 |
|---|---|
| 协议族 | AccAuthentication / DeviceAuthentication / MFi4Auth |
| 消息名 | 文档中的符号名 |
| 线上 ID | `0xAAxx` 或 `0x51xx` |
| 方向 | 设备→车机、车机→设备，分列，不混表 |
| 适用条件 | feature 0 / feature 7 / authType / 样本是否观测 |
| 证据 | 函数地址/缓存路径/日志 |
| 状态 | CONFIRMED / INFERRED / OPEN |

然后把 `R-6.6.2` 改成“MFi4Auth 消息名与 ID 映射（设备侧视角）”，`R-6.6.7` 改成“设备侧收到→发出”，另设“配件侧镜像”表；L2 改为“七条”或按协议族分别计数。

### 3.7 A12：`0x5702/0x5703` 被误标为 NowPlaying

这是审计 A1–A11 之后追加确认的 P0 错误。

**证据**

- `0x5703` 的 handler 是 `iap2_wifisharing_AccessoryWiFiConfigurationInformation`（`0x1001703cc`），注册在 feature 22 `kiAP2MessageHandlerEntries_WiFiSharing`（`control/analysis/14-message-table.md:120`）。
- 该 handler 解析 `0x5703` 参数：ID 0 = data（BSSID 候选）、ID 1 = SSID 字符串、ID 2 = 口令字符串、ID 3 = securityType U8、ID 4 = channel U8（`f_1001703cc.ghidra.c:40-205`）。
- 23G90 原始日志 `22:11:33.737` 的 `57 03` 携带 `CFMOTO4801`、口令、securityType `0x02`、channel `0x9d`（157）；随后 `22:11:35.875` 发起 Association。这不是媒体元数据，而是 Wi‑Fi 配置。
- NowPlaying 的实际消息族是 `0x5000/0x5001/0x5002/0x5003`（`iap2_input_business_lifecycle/spec/02-nowplaying.md`）。

**影响**

- 读者会把 `0x5702/0x5703` 当媒体元数据，错过一条 Wi‑Fi 凭据来源；
- 网络引导文档如果把 `0x4301` 当作唯一凭据入口，会解释不了“`0x5703` 先到、Association 后发生”的样本；
- 与 `iap2_input_business_lifecycle` 的 NowPlaying 章节产生交叉误导。

**修复**

- `iap2_control_session/spec/10-message-catalog.md`：`0x5702` 改为 Wi‑Fi Sharing 请求，`0x5703` 改为 Wi‑Fi 配置信息，并加“不是 NowPlaying”的注记；
- `bluetooth-iap2-overview.md`：步骤 15 与 §7.2 表同步；
- `iap2_control_session/runtime/23G90-bt-classic-2026-10-16.md`、`iap2_input_business_lifecycle/runtime/23G90-bt-classic-2026-10-16.md`：时间线标签改为 Wi‑Fi Sharing/配置；
- `iap2_input_business_lifecycle/analysis/09-runtime-evidence.md`：修正“车机回 4E0D/4E0E”的方向错误，改为设备发送 5702/4E0D/4E0E、再 5702、车机回 5703；

## 4. A2 深挖：mDNS `features`/`fex` 优先级

文档两条 MUST 直接相反：

- `airplay_mdns_discovery/spec/04-features-bits.md:18` `R-4.10`：优先 `features`，缺失才 `fex`。
- 同文件 `:44` `R-4.7`：24A446 优先 `fex`。

分析台账的实际结论：

- `analysis/03-txt-and-features.md:67`：`_deviceFound` 的消费路径是“优先 `fex`，否则 `features`”，然后做 bit55/56 查询。
- `analysis/A-conclusions.md:37` `A02.5`：`fex` 存在时优先取 `fex`；否则把 `features` 转成 64 位整数。该条标为 **INFERRED**（桩名被剥离），不是 CONFIRMED。

因此：**两条 MUST 冲突是确认的；但“fex 优先”本身仍不是 CONFIRMED。** 正确修法不是简单把 R-4.10 改成 fex 优先，而是：
- 只保留一条 MUST，写“24A446 分支优先 `fex`（INFERRED）”；或
- 把两条都降为 OPEN/条件规则，等真实 TXT 样本或更强反汇编再定。

- `fairplay/spec/01:3-8` `R-1.1` 只说 FairPlay 走流对象 vtable、操作码 `fp25`，没有写它对应 RTSP `POST /fp-setup`。
- `control/analysis/05-rtsp-methods.md:53` 已给出 `fp25 → POST /fp-setup → application/octet-stream`。
- `fairplay/spec/01:37` 写 `/setup`（plist/SDP），而 `control/spec/05:5` 明确 body 必须是 binary plist。
- 结论：**承载映射缺失，不是算法错误**。建议在 FairPlay spec 加“fp25 ↔ /fp-setup”的映射，并统一 `/setup` 的 body 描述；“SDP”若指 Session Description Protocol 应删除或解释。

## 7. 不是错误、不要过度修正的项

- `airplay_rtp_timing/STATUS` 的“spec/00–09 完成”与“spec/05–06 无条款”并不矛盾：前者指文件已交付，后者指章节本身是缺口章节。
- `OPEN-RTP-14` 是历史已关闭项，不是未登记的新 OPEN。
- `OPEN-SES-2` 在 audio/input 中跨 docset 引用是有效的；需要修的是 tunnel TASK 里“字段映射仍 OPEN”的过期描述，不是删掉所有引用。
- `0x4301` 的“9 外层/14 叶子字段”不是与“14 字段”冲突，而是不同层级计数。
- `bluetooth_rfcomm` 的 `OPEN-BND-1/4` 已在 analysis/STATUS 标记关闭；spec 中提到它们是历史说明，不是未决项。
