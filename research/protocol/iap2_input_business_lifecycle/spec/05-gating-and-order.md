# spec/05 — 门控与顺序

## 5.1 三道关

`R-5.1` MUST 区分会话准入、特性存在和适用必需表检查。不是所有消息都有必需表，
也不是固定先检查三关再解析：导航先解析参数后检查必需表（A12.6）。
依据：A06.1、A06.2、A06.3。

`R-5.2` 会话准入：入站消息 MUST 满足
`认证状态 == 2 ∧ 识别状态 == 6 ∧ 消息 ID ∈ 入站集合`；
出站消息 MUST 满足 `认证状态 == 2 ∧ 识别状态 == 6 ∧ 消息 ID ∈ 出站集合`。
依据：A06.1（细节见 `sess/R-5.x`）。2/6为固件内部枚举，独立实现不必使用相同数字；集合偏移属于识别对象，不是 endpoint 本身。

`R-5.3` 本规范涉及的全部消息都不在"无条件放行"子集里，因此认证/识别未完成时
设备 MUST NOT 发业务；若收到提前到达的业务，应拒绝分派而非假定对端绝不会发送。
依据：A06.1。

`R-5.4` 不能依赖每个特性失败都有专属错误回执；StartHID无特性时局部返回0，
其它路径/外层可能记录日志。对需要等待应答的请求，应设计有界超时，而非把所有入站业务都视为请求应答。
依据：A06.2。

`R-5.5` 有必需消息表的特性（导航、目标检测、辅助触控），配件 MUST 在识别阶段
把"必需"项全部声明；未声明时该特性的消息会被丢弃。
依据：A06.3。

`R-5.6` 检查器返回 all，并将 any 写出参；导航调用方以 all=0拒绝并返回0。
该局部没有专属错误回包，不保证外层无日志。设备 SHOULD 记录具体门控原因，不以超时推定根因。
依据：A11.4、A12.6。

## 5.2 声明集合的维护

`R-5.7` 设备视角的入站/出站能力 MUST 分开维护；不能互换。识别消息由车机自述，
集合读取不证明设备必须上报全部 ID；集合完整填充链仍待核。
依据：A05.1（表项带方向位）。

## 5.3 顺序

| 约束 | 强度 | 依据 |
|---|---|---|
| 认证/识别后才收发业务消息 | MUST | A06.1 |
| 特性启动后才处理该特性消息 | MUST | A06.2 |
| 有效描述符与启动/启用状态就绪后才注入本地输入 | 本地安全策略，非所有HID消息的固件前置门 | A03.3；analysis/13 |
| `0x5000` 早于 `0x5001` | SHOULD | A04.7 |
| `0x5200` 早于 `0x5201/0x5202/0x5204` | SHOULD | A05.1 |
| `0x0D00` → `0x0D01` → `0x0D02` | SHOULD | A05.2 |

`R-5.8` 上表 SHOULD 是当前实现建议，不是已证明的完整固件顺序。早到消息需检查前置条件，
可有界缓存或拒绝，不意味着应无条件执行。
依据：A04.7、A05.1。

## 5.4 缺省行为

`R-5.9` 未识别的参数 ID MUST 被忽略而不丢弃整条消息。
依据：A04.2（`0x5000` 的未知参数分支）。

`R-5.10` 客户端须严格检查参数长度；固件getter返回错误不等于调用者必定检查。
StartHID参数1/2/3没有立即检查错误出参；GetReportResponse对应分支会检查并失败返回。
不能把某条日志推广成全部处理器/全部参数的统一拒绝行为（analysis/13）。
依据：A03.2、A04.3。
