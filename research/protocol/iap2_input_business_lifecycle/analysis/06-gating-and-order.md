# analysis/06 — 门控与顺序

以下是逻辑检查分类，不是每条处理器都具有的固定调用顺序（导航先解析参数后检查必需表，见 A12.6）：

```text
① 两张准入名单（0x100051054 / 0x100005138）   ← 会话层，见 sess/R-5.x
        ↓ 通过
② 特性是否存在（_iap2_feature_getFeature(endpoint, feature)）
        ↓ 存在
③ 必需消息表（只有部分特性有）                 ← 本阶段新发现
        ↓ 通过
   处理器开始解析参数
```

## 6.1 ① 两张准入名单（引用，不重推）

- 入站 `0x100051054`：`{0x0000,0x0004,0x0005,0x1D01,0x1D05,0x1D06,0xAA01,0xAA03}` 无条件放行；
  `0xAA06` 仍需识别对象、识别完成及入站集合含该 ID（免认证检查）；其余必须 `认证==2 ∧ 识别==6 ∧ ID ∈ 入站集合(+0x60)`。
- 出站 `0x100005138`：`{0x0000,0x0004,0x0005,0xAA00,0xAA02,0xAA04,0xAA05,0x1D00,0x1D02,0x1D03}` 无条件；
  其余 `认证==2 ∧ 识别==6 ∧ ID ∈ 出站集合(+0x68)`。

`A06.1`：本阶段的**全部**消息（HID 7 条、NowPlaying 4 条、导航 8 条、AssistiveTouch 5 条）
都不在上面的"无条件"子集里，因此都必须等认证/识别完成。

## 6.2 ② 特性存在性

StartHID先查特性11；Report/GetReportResponse经组件校验查询，Stop解析后查特性。
`A06.2`：StartHID无特性时局部返回0，不证明其它路径或外层dispatcher静默。
客户端不能假设每次本地失败都会产生专属线上错误响应。详见analysis/13。

## 6.3 ③ 必需消息表（本阶段的关键发现）

`_iap2_identification_checkRequiredMsgIDs(endpoint, list, count, out)`（`0x100050c2c`）检查
"识别阶段登记的集合里是否有这些 ID"。表项 12 字节：`{u16 msg_id; u32 dir; u8 required}`
（布局与指令证据见 `analysis/05` 5.1）。

解出的三张表：

**导航** `_gskMsgNavigationMainList`（`0x1001b40e0`，5 项）
`0x5200`(入,必需) `0x5201`(出,必需) `0x5202`(出,必需) `0x5203`(入,必需) `0x5204`(出,可选)

**目标检测** `_gskMsgRoadObjectDetectionMainList`（`0x1001b411c`，4 项）
`0x0D00`(出,必需) `0x0D01`(入,必需) `0x0D02`(出,必需) `0x0900`(入,可选)

**AssistiveTouch** `_gskMsgAssistiveTouchList`（`0x1001b3bd0`，5 项）
`0x5400`(入,必需) `0x5401`(入,必需) `0x5402`(入,必需) `0x5403`(出,必需) `0x5404`(入,必需)

`A06.3`：HID 与 NowPlaying **没有**这类表（`0x100130444`、`0x1001499f0` 的函数体里没有
`0x100050c2c` 的调用）。因此"必需消息表"是**按特性**存在的，不是全局规则。

`A06.4`：`required`（表项 +8 字节）的语义已读出（`0x100050c2c`）：
函数维护两个结果——`any = (任一 ID 在集合里)`、`all = (所有 flag==1 的项都在集合里)`；
`flag==0` 的项只参与 `any`，不参与 `all`。所以 `0x5204`、`0x0900` 这类"可选"项
不影响"必需集是否齐全"的判定，但仍影响 any 和逐消息能力门；any 写出参，all 为返回值（A12.6）。
`A06.5`：导航必需表检查返回0时，`0x1001755c0` 跳 `0x100175908` 返回0；局部没有专属回包。
不能由无 else 推出外层无失败日志。参数已在此检查前解析（A12.6）。

## 6.4 顺序要求（能证的与不能证的）

| 顺序 | 证据 | 结论 |
|---|---|---|
| 认证/识别 → 任何业务消息 | 6.1 | **必须**（否则入站被丢） |
| 特性/组件可用 → 相应业务处理 | 6.2 | 逐处理器检查，非统一入口序列 |
| `0x6800` → 本地输入注入 | analysis/13：组件校验没有读启动/启用位 | 本地安全策略要求有效描述符与状态；不能称所有报文都有此固件前置门 |
| `0x5000` → `0x5001` | 订阅者模型（`analysis/04` 4.6） | 语义上必须，但代码未强制（`OPEN-NP-5`） |
| `0x5200` → `0x5201/0x5202/0x5204` | 仅有序号语义 | `OPEN-NAV-5` |
| `0x0D00` → `0x0D01` → `0x0D02` | 同上 | `OPEN-NAV-5` |
| 订阅前收到更新 | 无强制 | 未证 |

## 6.5 客户端要做的三件事

1. 按设备视角分开维护方向能力，核对车机识别资料与本地支持；读侧集合不证明设备必须上报全部 ID；
2. 等认证/识别通过再发业务消息；2/6是该固件内部枚举，不是独立实现必用值；
3. 收到"特性不存在"的路径没有错误回执——只能靠日志/抓包判断，客户端要自己超时。
