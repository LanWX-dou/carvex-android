# spec 02 FairPlay 交换（L1 接口 + L2 编排）

## R-2.1 L1需要可用的FairPlay实现与合法接口

本docset未实现下列五项；集成前须取得目标profile适用的合法实现/授权接口。
以下是固件接口形状，不是由静态代码证明的“禁止自行实现”或任意MFi模块都具备这些能力：

| 能力 | 本固件对应 | 输入 | 输出 |
|---|---|---|---|
| 取硬件信息 | `APCUGetFairPlayHWInfoEx` | — | 96 字节区（大小由核心约定） |
| 建会话上下文 | `cp2g1b9ro` | `hwInfo` | `ctx` |
| 推进握手 | `Mib5yocT` | `type, hwInfo, ctx, in, inLen` | `out, outLen, state` |
| 加密 16 字节密钥 | `U4HBs` | `ctx, key16` | `blob, blobLen` |
| 销毁上下文 | `IPaI1oem5iL` | `ctx` | — |

依据：A-07、A-08、A-09、`OPEN-1`。级别：C（可写接口形状，不可写算法）。

## R-2.2 `type` 的本地选择分支

| ET | `Mib5yocT` 的 type |
|---|---|
| `8` | `2` |
| `32` | `3` |
| 其它 | 拒绝 |

上表仅限`X-Apple-ET`范围整数getter成功。getter失败后取`CSeq`字符串：返回非NULL选2、NULL选3。
不得把CSeq值当ET，也不得把这个本地fallback当作通用降级授权。
证据：`0x2518a53cc..5438`，A-38。
发送侧本版本固定传 `3`（`0x251ace918` 的 `w0=3`）。
客户端必须确认目标profile的ET选择和发送责任；接收函数读取入站请求，不证明ET由车机下发。
不要自动尝试32失败后回退8：失败状态能否复用未证。实际profile→`OPEN-3`。
依据：A-08、A-10、A-38、`OPEN-3`。级别：A（限定映射）/ C（客户端策略）。

## R-2.3 认证类型标识为 4

`GetAuthenticationType` 返回 `4` 表示 FairPlay；密钥刷新逻辑只对 `4` 生效。
依据：A-06（`0x251ace720`）、A-13、A-14。级别：A。

## R-2.4 失败处理

| 情况 | 处理 |
|---|---|
| `state ∉ {0,1}` | 终止，`0xfffee786`，销毁上下文 |
| 核心返回非 0 | 终止，透传 `OSStatus`，销毁上下文 |
| 收不到响应 | 终止，不透传空载荷给核心 |
| 重认证 | 先销毁旧上下文再新建（`0x251ace7c8` → `0x251ace7d8`） |

依据：A-08、A-25。级别：A。

## R-2.5 不许做的事

- 不要假设 FP 载荷里有 magic/版本字段（`OPEN-12`，反证见 A-28）。
- 不要把 `hwInfo` 写死或复用别的设备的值（来自硬件，`OPEN-1`）。
- 不要在握手未完成时发 `/setup` 的 `ekey`（接收侧要求 `fpCtx` 非空，否则 `0xffffe59e`）。
依据：A-24、A-28、A-08。级别：A。
