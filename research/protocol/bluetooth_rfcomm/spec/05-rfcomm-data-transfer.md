# 05 RFCOMM 数据传输与流控

## 5.1 接收侧校验顺序

**R-5.1** 接收方**必须**按下列顺序处理每个帧，任一步失败即按"失败行为"列处理，**不得**跳过或合并步骤：

| 序 | 校验 | 失败行为 |
|---|---|---|
| 1 | 帧能归属到一条会话（按通道标识） | 丢弃 + 计数 |
| 2 | 帧总长 ≥ 4 | 丢弃 + 计数 |
| 3 | `Control & 0xEF` 属于 {`0x2F`,`0x43`,`0x63`,`0x0F`,`0xEF`} | 丢弃 |
| 4 | FCS 正确 | 丢弃 + 计数 |
| 5 | `Address` bit0 = 1；C/R 与会话方向匹配 | 丢弃 |
| 6 | 会话处于"已就绪"状态 | 丢弃 |
| 7 | `Address` < `0xF8` 且 DLCI ≠ 1 | 丢弃 |
| 8 | 总长 == 头长 + 信息长度 + 1 | 丢弃 |
| 9 | （若 P/F=1）会话启用信用流控，否则该帧非法 | 丢弃 |

**R-5.2** 第 8 步的"精确匹配"是硬要求：多一字节或少一字节都**必须**丢弃整帧，**不得**按"取前 N 字节"或"忽略尾部"处理。

## 5.2 UIH 帧解码

**R-5.3** UIH 帧（`Control & 0xEF == 0xEF`）的信息字段布局：

```
+---------------------------+
| （可选）信用 1 字节         |  当且仅当 Control bit4（P/F）= 1 且启用信用流控
+---------------------------+
| 用户数据                   |
+---------------------------+
```

**R-5.4** 头长计算：

| 条件 | 头长 |
|---|---|
| 单字节长度，无信用字节 | 3 |
| 双字节长度，无信用字节 | 4 |
| 单字节长度，有信用字节 | 4 |
| 双字节长度，有信用字节 | 5 |

**R-5.5** 启用信用流控的会话收到 P/F=1 的 UIH 时，**必须**先取 1 字节信用，再取用户数据；未启用信用流控却收到 P/F=1 的 UIH，**必须**判为非法帧。

**R-5.6** 用户数据长度**必须**等于**长度字段的值**；信用字节**不**计入长度字段。

> **订正依据（固件 + 线上双重确认）**：
> ① 固件 `0x1003c679c` `ldrb w24,[x1,w9,uxtw]` 取 `帧[头长]` 为信用、`0x1003c67a0` `add w9,w9,#1`
> 把**头长**加一，`0x1003c67ac`/`0x1003c67b0` 以 `长度字段 + 头长 + 1(FCS)` 校验总长；
> ② 340 个真实 UIH 帧里 P/F=1 恒有 1 字节信用、P/F=0 恒无，一对载荷相同（`FF 55 02 00 EE 10`）
> 的帧无论是否带信用，长度字段都是 6。
> 详见 `analysis/05-rfcomm-data-path.md` C3.1 与 `runtime/captures/2026-10-rfcomm-pklg-reanalysis.md` §8。
> 本条已由固件 `0x1003c679c`–`0x1003c67b8` 与线上 340 帧双重确认，措辞差异项关闭。

## 5.3 信用流控

**R-5.7** 设备**必须**为每个 DLCI 维护两个相互独立的 16 位计数器：

| 计数器 | 含义 | 变化 |
|---|---|---|
| `credit_to_peer_remaining` | 己方已授予对端、尚未被消耗的信用 | 每收到一个数据帧减 1 |
| `credit_from_peer` | 对端授予己方、可用于发送的信用 | 收到信用授予时累加；每次发送减 1 |

**R-5.8** 收到数据帧且 `credit_to_peer_remaining == 0` 时：

- **必须**记录"超信用接收"错误；
- **可以**仍把数据交付上层（实现选择）；
- **不得**因此断链。

**R-5.9** 收到信用授予时**必须**做溢出检查：若 `credit_from_peer + credits > 0xFFFF`，**必须**报"信用溢出"错误并**不得**更新计数器。

**R-5.10** 设备**应当**在 `credit_to_peer_remaining` 低于阈值时主动补发信用；补发数量**必须**使对端总量不超过其窗口。

**R-5.11** `credit_from_peer == 0` 时**不得**发送数据帧，**必须**排队等待信用；若上层要求"无信用也必须发"，则视为配置错误。

> 依据：附录 A 的 T-04、T-05。

## 5.4 数据交付（向上层）

**R-5.12** 每收到一个合法的 UIH 数据帧，**必须**向上层交付**一次**，交付内容为：

```
( DLCI 号 : 16 位, 数据指针, 数据长度 : 32 位 )
```

**R-5.13** 交付**必须**是"帧边界即交付边界"：

- **不得**把相邻两帧合并成一次交付；
- **不得**把一帧拆成多次交付；
- **不得**在交付前做跨帧重组。

**R-5.14** 数据指针指向的内容**必须**在本帧处理期间有效；若上层需要长期持有，**必须**由上层复制。

**R-5.15** 交付**必须**按接收顺序进行；同一 DLCI 上的乱序交付视为不符合。

**R-5.16** 上层回调抛错/返回失败**不得**影响后续帧的接收与交付。

## 5.5 发送侧

**R-5.17** 发送**必须**按"块"进行，每块对应一个信息字段：

```
块最大长度 = min( N1, 单次发送缓冲上限 )
```

本实现的单次缓冲上限为 **2570 字节**，N1 由连接时协商（无线 iAP 场景为 1007）。

**R-5.18** 发送**必须**串行排队：同一会话内，前一块完成（或失败）后才能发下一块。**不得**并行写入同一会话。

**R-5.19** 队列满或底层未就绪时，**必须**把数据留在队列中并稍后重试，**不得**静默丢弃。

**R-5.20** 每块发送**必须**产生一个完成事件，携带 `(DLCI 号, 块标识, 状态)`；状态非 0 时**必须**上报给上层。

**R-5.21** 会话在发送过程中被销毁时，**必须**释放该会话所有排队块并上报"会话已关闭"，**不得**泄漏缓冲。

**R-5.22** "部分写"的语义**必须**定义为"本次只消费了块的前 k 字节"：

- 设备**必须**记住已消费字节数，下次从 `k` 处继续；
- **不得**把已消费部分重发；
- 剩余部分构成新的待发块，长度**必须**重新按 N1 计算。

**R-5.23** 设备交付给上层的"可用载荷长度"**必须**是 N1；若接口沿用 "MTU" 命名，**必须**在文档中注明其语义是"最大信息字段长度"，不是 L2CAP MTU。

## 5.6 数据完整性

**R-5.24** RFCOMM 层**必须**依赖 FCS 做单帧完整性校验；**不得**假设上层已做校验。

**R-5.25** RFCOMM 层**不得**实现重传、序号、确认——这些属于上层（见 06.4）。丢帧只**必须**通过丢弃计数暴露。

**R-5.26** 设备**必须**提供下列计数器，供上层与诊断使用：

| 计数器 | 含义 |
|---|---|
| `frames_rx_total` | 收到的帧总数 |
| `frames_rx_dropped_fcs` | FCS 错丢弃数 |
| `frames_rx_dropped_length` | 长度不符丢弃数 |
| `frames_rx_dropped_state` | 状态/地址非法丢弃数 |
| `credit_overflow_errors` | 信用溢出次数 |
| `data_rx_without_credit` | 超信用接收次数 |
| `frames_tx_total` / `frames_tx_failed` | 发送总数/失败数 |

## 5.7 一致性判据

1. 构造"长度字段比实际数据多 1/少 1"的帧，均被丢弃且不产生响应。
2. 构造 FCS 错误的帧，被丢弃。
3. 信用溢出（累加超过 0xFFFF）产生明确错误。
4. 连续两个 UIH 帧产生两次交付，且长度分别正确。
5. 上层持有的数据指针在下一帧到达后**不再**被引用（验证生命周期）。
6. 发送 3000 字节数据时按 N1 分块，且完成事件数与块数一致。
7. `N1 > 2570` 时按 2570 分块（受缓冲上限约束）。
