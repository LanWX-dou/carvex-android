# 08 向上层交接契约

本章只定义**蓝牙 → 上层**的接缝：交付什么、以什么单位交付、上限多少、怎么关闭、以及**本层不提供什么**。
它回答的是"别人拿到这条 RFCOMM 通道后，能依赖什么、必须自己做什么"，不定义 iAP2 的任何语义。

状态标记：`CONFIRMED` = 固件字节/汇编直接支撑；`INFERRED` = 由上一条 + 结构约束推出，未直接取证；
`OPEN` = 证据不足，已登记 manifest，实现方不得依赖。

> **外接客户端（非 iOS 进程内实现）请直接读 `spec/09-client-open-rfcomm.md`，不要照抄本章。**
> 本章的 `kCBMsgArgSocket`、`socketpair`、`kCBMsgArgMTU`、fd 所有权等契约是 **iOS 内部**
> bluetoothd 与其上层进程之间的交付方式；外接客户端拿不到这些接口，也不应假设存在 `socketpair`。
> 外接客户端只需要：SDP 查通道 → SABM/PN/MSC → 字节流读写（`spec/09`）。
> 本章对两类读者都成立的部分只有：帧边界不可见（R-8.9/R-8.10）、上限 `min(N1,2570)`（R-8.14）、
> 不重组/不重传（R-8.23/R-8.24）、EOF/错误语义（R-8.19）。

## 8.1 交付形态：两条通路，一条跨进程

**R-8.1**（`CONFIRMED`）实现**必须**同时提供两种交付形态，二者可以并存于同一通道：

| 形态 | 载体 | 适用范围 |
|---|---|---|
| 逐帧回调 | 进程内 C 函数指针 `(uint16 dlci, uint8* data, uint32 len)` | 与协议栈同进程的客户端（OBEX 服务、HFP 等） |
| 字节流 | `socketpair` 的一端（fd） | **任何跨进程客户端**，包括 CarPlay / Wireless iAP |

依据：`0x1003c59a0` C 行 348–349 每收一帧调用一次函数指针；`0x10040c934` C 行 62–83 通过 XPC 把 fd 交给客户端。

**R-8.2**（`CONFIRMED`）跨进程客户端**只能**使用 fd 通路：逐帧回调是**进程内函数指针**，
不可能跨进程传递。因此"主通路"取决于客户端形态，而不是协议栈有偏向：

- 出进程（CarPlay / Wireless iAP，`source/firmware/bluetoothd` 内零 `iap2` 字符串）→ **fd 是唯一通路**；
- 同进程服务 → 回调与 fd 都可能用，参照实现两者都实现。

**R-8.3**（`CONFIRMED`）fd **必须**随"通道已连接"的 XPC 响应消息交付，键名 **`kCBMsgArgSocket`**，
类型为文件描述符（发送侧调用 `_xpc_dictionary_set_fd`）。同一条消息内**必须**同时给出：
`kCBMsgArgDeviceUUID`、`kCBMsgArgResult`、`kCBMsgArgRFCOMMChannelID`、`kCBMsgArgMTU`（语义见 R-8.13）、
`kCBMsgArgIsIncoming`、`kCBMsgArgServiceUUID`。

**R-8.4**（`CONFIRMED`）该 fd **必须**是一个 `socketpair` 的一端：固件存在
`Failed to create socket pair for pipe 0x%04x with result %d`（串表 `0x100acbb3d`）与
`os_channel_create_extended failed for pipe 0x%04x ... skywalk pipe registration`（`0x100acbfa5`）。

**R-8.5**（`INFERRED`）所有权：XPC 传递后，客户端持有**自己那一端**的读写描述符；
协议栈保留另一端用于中继（`Failed to send data to socket on pipe` `0x100acc42f`、
`Failed to transmit data from socket on pipe` `0x100acc74f` 两条方向相反的中继日志）。
客户端**必须**在通道关闭时自行 `close()`，与 R-8.18 的错误通知顺序无关。

**R-8.6**（`CONFIRMED`）回调的注册与注销**没有**独立 API，生命周期等于 DLCI 生命周期：

| 时机 | 行为 | 依据 |
|---|---|---|
| 建链 | 回调块指针随 `OI_RFCOMM_Connect` 的 `param_2` 复制进 `dlci+0x28` | `0x1003c2b00` C 行 80 前后 |
| 收帧 | 取 `*(dlci+0x28)+8` 作为数据回调 | `0x1003c59a0` C 行 348–349 |
| 销毁 | 随 DLCI 记录整体释放，**不再单独注销** | `0x1003c16dc` C 行 17–41 |

**R-8.7**（`OPEN`）两通路在**同一通道**上的实际使用比例只能由运行时确定（静态不可判；原 `OPEN-BND-1` 已关闭（结构性证据），残余仅涉运行时比例）。
实现方**不得**假设"有 fd 就没有回调"，反之亦然。

## 8.2 数据单位、边界与缓冲

**R-8.8**（`CONFIRMED`）回调通路的交付单位**必须**是**一个 RFCOMM 信息字段**：一次调用 = 一帧的载荷，
长度为该帧长度字段的值（不含地址/控制/长度/信用/FCS）。依据 `0x1003c59a0` C 行 348–349，第三参 `uVar14`。

**R-8.9**（`CONFIRMED`）fd 通路的交付单位是**字节流**，**帧边界对客户端不可见**：
fd 是 socket 语义，协议栈把收到的载荷写入 socket，接收方按 `read()` 的返回值切分，
`read()` 的切分点与 RFCOMM 帧边界**没有任何对应关系**。

> **后续阶段修订（2026-10）**：本条替代 `06` 旧 R-6.24"传输桥层必须保证不丢失帧边界"的表述。
> 旧条款与 `analysis/07` C2 冲突——主通路是 fd 字节流，套接字层不存在"带长度消息队列"。
> 以固件证据为准：帧边界只在**回调通路**存在。

**R-8.10**（`CONFIRMED`）因此上层**不得**依赖"一次 `read` = 一个 iAP2 报文"，也**不得**依赖
"一次 `read` 不跨报文"；任何基于读取边界的假设都必须替换为对报文自身长度字段的解析。
（iAP2 是否真的携带自描述长度，属 iAP2 side 的事实，见交接事实清单 F-11，待对方确认。）

**R-8.11**（`INFERRED`）缓冲有效期：回调通路的 `data` 指针指向底层 MBUF 的内部视图，
**仅在回调执行期间有效**；需要保留**必须**立即拷贝。依据：同一轮投递处理结束后
`0x1000eb4e8` 调用 `_os_channel_advance_slot()` 归还槽位（C 行 406–413），槽位一旦推进，指针内容即失效。

**R-8.12**（`INFERRED`）同一 DLCI 上回调节奏为**串行**：单条 `os_channel` 取槽—投递—推进循环，
不存在并发回调；回调内**不得**阻塞，且**必须**按接收顺序处理（回调顺序 = 帧顺序）。

**R-8.13**（`CONFIRMED`）`kCBMsgArgMTU` 的语义是 **N1（最大信息字段长度）**，不是 L2CAP MTU；
无线 iAP 场景实测为 **1007**。实现**必须**按 N1 理解并对外注明（与 R-5.23 一致）。

## 8.3 上限、分块与完成语义

**R-8.14**（状态逐句见下表）分块与重组职责**必须**按下述三句划分，不得重复也不得留空：

> **适配层把 iAP2 帧切成 ≤ `min(N1, 2570)` 的写块；RFCOMM 不重组；iAP2 链路层不分片。**

| 分句 | 状态 | 依据 |
|---|---|---|
| 单块上限 = `min(N1, 2570)` | `CONFIRMED` | 2570 = 协议栈单次缓冲/槽位上限（`0x1000eb4e8` C 行 72、87–90）；N1 的语义见 R-8.13 |
| 切块（allocation）发生在**适配层** | `INFERRED` | 本层不提供切块接口、也不重组（R-8.23/R-8.25），因此切块只能发生在层之上；具体的写块分配策略由 **iAP2 docset** 的 `R-1.13` 定义 |
| RFCOMM 不重组 | `CONFIRMED` | R-8.23；`0x1003c59a0` 逐帧交付、无跨帧状态 |
| iAP2 链路层不分片 | `INFERRED` | 非本 docset 证据，由 iAP2 docset 的 `R-1.13` 与 iAP2 帧格式定义 |

> 读法：**上限**（limits）是本层固件事实；**谁负责切块**（allocation）是跨层约定，
> 本层只证明「不是我」，正向定义在 iAP2 docset 的 `R-1.13`。
>
> 编号提示：本 docset 的 `R-1.x` 属「发现与识别」章，与 iAP2 docset 的 `R-1.x` **各自独立编号**，
> 本章出现的 `R-1.13`/`R-1.14` 一律指 iAP2 docset。

> **后续阶段修订（2026-10）**：本条合并了旧 R-8.14（"上层自行分块"）与旧 R-8.16
> （"fd 写入会被协议栈按 `min(N1,2570)` 重新切分"）。两者并存会让读者二选一：
> 前者说协议栈不拆，后者说协议栈会重切。统一后的表述只保留一处权威：
> **切块责任在适配层，RFCOMM 不重组，iAP2 链路层本身不分片**。

**R-8.15**（`CONFIRMED`）发送**必须**串行排队，一块完成再发下一块；每块**必须**产生一个完成事件
`(DLCI, 块标识, 状态)`（R-5.20）。**部分写**的语义见 R-5.22：本次只消费前 k 字节，
剩余部分构成新的待发块并按 N1 重算。

**R-8.16**（`OPEN`）背压：当对端信用耗尽或槽位占满时，fd 通路对 `write()` 的反馈形式
（阻塞 / `EAGAIN` / 静默排队）未取证。实现方**必须**在 fd 上同时容忍阻塞与短写，
**不得**假设 `write()` 返回即已上线。

## 8.4 关闭、句柄失效与错误通知

**R-8.17**（`CONFIRMED`）主动关闭**必须**发送 DISC 并等待确认（R-6.1–R-6.5）；
被动关闭对合法且存在的 DLCI **必须**回 UA 并释放资源（R-6.6–R-6.8）。对上层而言两条路径的**可观测结果相同**：
DLCI 记录被销毁、回调不再触发。

**R-8.18**（`CONFIRMED`）关闭原因**必须**用"导致该 DLCI 关闭的原因"上报，而不是"最后一次操作的结果"
（R-6.12）；最后一个 DLCI 关闭时用 `dlci[0xa4]` 的错误码通知上层（`0x1003c16dc` C 行 33–35）。

**R-8.19**（`INFERRED`）fd 通路的关闭**必须**按「**EOF 是触发信号，detach 是随后显式执行的动作**」处理：

- 客户端看到 `read()` 返回 0 或读写错误（`EPIPE`/`ECONNRESET` 等）时，只把它当作**触发**；
- 随后**必须显式执行 detach**（关闭 fd、停止读写、走自己的通道销毁流程），
  **不得**把 EOF 本身当作已完成 detach，也**不得**在 detach 前继续复用该 fd；
- 依据：协议栈中继读失败的日志 `Read zero bytes from socket on pipe 0x%04x`（`0x100acc896`）
  与 `Received error %d from socket on pipe 0x%04x`（`0x100acc8c1`）。

> 与 iAP2 docset 的 `R-1.14` 对齐：两侧对关闭的表述统一为「EOF = 触发，detach = 显式动作」，
> 本条只定义蓝牙侧可观测信号，不定义 link 侧的 detach 流程细节。

**R-8.20**（`CONFIRMED`）旧链路句柄在会话销毁后**必须**失效；用旧句柄发起接受/断开**必须**返回"句柄无效"
（日志 `OI_RFCOMM_Accept - linkhandle %d not found`、`OBEX server RFCOMM disconnect on bogus link handle %x`）。

**R-8.21**（`INFERRED`）错误通知的双通路差异：回调客户端收到错误码参数；fd 客户端只能从
读/写错误与 EOF 得知，**没有**独立的"错误消息"通道。实现方**应当**同时提供带外诊断（日志/计数器），
不要求客户端解析错误码。

## 8.5 本层不提供什么

**R-8.22**（`CONFIRMED`）本层**不**实现、也**不**识别 iAP2：整个固件的 `iap2` 字符串计数为 **0**，
`Wireless IAP` 仅作为服务名/日志出现（`analysis/07` C3）。任何 iAP2 帧格式、标识、鉴权都在上层。

**R-8.23**（`CONFIRMED`）本层**不**做跨帧重组、**不**做流式拼接、**不**解析 payload；
接收路径对长度不符的帧**静默整帧丢弃**（R-5.4 / `analysis/05` C4），不通知是哪一帧。

**R-8.24**（`CONFIRMED`）本层**不**重传、**不**排序、**不**确认：丢帧只通过计数器暴露（R-5.25）。
需要可靠性的上层**必须**自带序号与重传（link 侧已确认 iAP2 自带 16 位长度、8 位序号与 ACK/重传，原 `OPEN-BND-4` 已关闭）。

**R-8.25**（`INFERRED`）本层**不**提供"帧边界元数据"给 fd 客户端：没有 `recvmsg` 控制消息、
没有每帧长度前缀、没有 `MSG_EOR` 语义。需要帧边界的客户端只能走同进程回调（R-8.1）。

**R-8.26**（`OPEN`）本层**不**保证"通道号在同一设备上稳定"：通道号来自 SDP 结果（R-3.16，实测 4/1/5），
上层**必须**每次连接重新取，缓存需带失效条件。

## 8.6 一致性判据

1. 跨进程客户端只拿 fd，能收发数据，且 `read()` 切分与帧边界不一致时仍能正确工作（R-8.9/R-8.10）。
2. 同进程客户端注册回调后，一次回调恰好拿到一个信息字段，长度等于长度字段值（R-8.8）。
3. 回调返回后再访问 `data` 指针属于未定义行为（R-8.11 的负向测试：构造内存在回调后释放）。
4. 发送 3000 字节：按 `min(N1,2570)` 分块，完成事件数与块数一致，且顺序与提交顺序相同（R-8.14/R-8.15）。
5. 关闭通道：fd 客户端在有限时间内观察到 EOF 或错误，**并把 EOF 当作触发、显式执行 detach**；回调客户端不再收到回调（R-8.17/R-8.19）。
6. 旧句柄操作返回明确错误（R-8.20）。
7. 断链原因可区分：正常 DISC 与异常断链上报的错误码不同（R-8.18）。
