# 蓝牙 iAP2 总链路说明（设备侧客户端）

> **定位**：这是一份把三套 docset 串起来的“总览 / 导读”，不是新的规范。
> 事实以 `research/protocol/bluetooth_rfcomm`、`research/protocol/iap2_link_establish`、`research/protocol/iap2_control_session` 为准；本文件只做汇总、排序和标注冲突。
>
> **目标读者**：实现“设备侧客户端”（模拟 iPhone）的人。
> **目标场景**：客户端通过 Bluetooth Classic RFCOMM 连接车机（accessory），验证配件身份，并向 CarPlay 网络会话交接。本目录尚不足以独立实现完整 CarPlay 客户端。
> **证据基线**：24A446 静态分析 + 23G90 运行时抓包；23G90 不是 24A446，时序类结论只能当参考。


---

## 0. 一句话

```text
SDP 找车机 ...caff → RFCOMM 开通道 → 等车机 SYN → SYNACK
  → 识别（0x1D00/01/02）→ 认证（0xAA00…0xAA05）
  → 控制会话 → 收 0x4301 → 网络/CarPlay 会话建立（文档缺口）→ 音视频与输入（文档缺口）
```

---

## 1. 角色、范围、两个 version

### 1.1 角色

| 角色 | 是谁 | 在本链路里做什么 |
|---|---|---|
| **设备侧客户端** | 模拟 iPhone | 跟踪握手确认的会话条目、发起识别/认证、处理控制会话与 `0x4301` |
| **车机 / accessory** | 车机 | 暴露 SDP 记录、发 SYN、回识别信息、提供证书/签名、发 `0x4301` |

本文件只写**设备侧客户端**。如果客户端要扮演 accessory，状态机入口、SYN 发起、认证方向都要镜像，本文不覆盖。

### 1.2 范围

- 承载：**Bluetooth Classic（BR/EDR）RFCOMM**。
- 不覆盖：USB、无线 CarPlay 的 Wi‑Fi 切换、CarPlay 音视频面。
- 认证：样本七步是客户端验证车机证书与签名，不要求由客户端提供配件私钥。客户端仍须具有可信验证材料与正确的验证实现；另一路设备自身认证的凭证要求尚待核实。不能把“持有 MFi 凭证”当作完整互通的充分条件。

### 1.3 先分清两个 version

这两个 version 不在同一层，不能混：

| 名字 | 位置 | 取值 | 作用 |
|---|---|---|---|
| **iAP2 链路 SYN version** | SYN 载荷第 0 字节 | 默认 `1`；解析布局分 0/1/>=2，目标合法性检查为调用方 minVersion..3 | 决定尾部格式并参与合法性/协商检查 |
| **控制会话 version** | 会话表项 `[2]` | `0/1/2/...` | `==2` 识别优先；`!=2` 认证优先 |

实际抓包可以是：**SYN version=1 + 控制会话 version=2**。不要因为看到“version 2”就以为 SYN 里带了 2。

## 3. 端到端流程

### 3.1 分步表

| # | 阶段 | 方向 | 动作 | 说明 |
|---|---|---|---|---|
| 1 | SDP | 设备 → 车机 | 按车机侧接收端 UUID `...caff` 查 `ProtocolDescriptorList` | 通道号从记录取；同一服务抓包出现过 4/1/5，不能写死 |
| 2 | RFCOMM | 设备 → 车机 | 平台 RFCOMM connect；系统负责 L2CAP/控制帧/信用 | 1007 是参考 N1；内部容量 15 不是 PN 线上初始信用（低 3 位）。`0x8D` 仅为 MSC 样本值 |
| 3 | 首字节 | 车机 → 设备 | Detect（`FF 55 02 00 EE 10`）或直接 SYN（`0x80`） | 设备先等 `T_first_byte=2 s`；没有就发 Detect；`T_detect=5 s`；`T_link=30 s` |
| 4 | 链路握手 | 设备 → 车机 | SYNACK `0xC0`；验证车机 ACK 的校验、序号和确认号 | `0x90` 的触发条件未确认；不能仅凭 ACK 位判定握手成功 |
| 5 | 识别 | 设备 → 车机 | `0x1D00`，无参数，`hdr[7]`=握手确认的会话号 | 23G90 样本为 2/3；不能任意选号。样本中链路控制帧填 0，完整分配规则仍 OPEN |
| 6 | 识别 | 车机 → 设备 | `0x1D01`，参数组 0 携带车机自述 | 参数 ID ≤ `0x22`；设备早期发 `0x1D01` 会被门控拦下 |
| 7 | 识别 | 设备 → 车机 | `0x1D02`，无参数 | 表示接受 |
| 8 | 认证 | 设备 → 车机 | `0xAA00`，带 `00 04 00 00` 空参数 | 设备侧主动发起 |
| 9 | 认证 | 车机 → 设备 | `0xAA06`，32 B ASCII 串 | 证书序列 / 选择符 |
| 10 | 认证 | 设备 → 车机 | `0xAA00`，无参数 | 第二次请求 |
| 11 | 认证 | 车机 → 设备 | `0xAA01`，DER（本样本 607 B） | 按配置的信任策略验链；样本容器不含 Apple 根，不能仅凭样本宣称已验到根 |
| 12 | 认证 | 设备 → 车机 | `0xAA02`，32 B 随机挑战 | 保存挑战 |
| 13 | 认证 | 车机 → 设备 | `0xAA03`，64 B 签名 | 用叶证书公钥验签 |
| 14 | 认证 | 设备 → 车机 | `0xAA05`，无参数 | 验签通过后发 |
| 15 | 会话 | 双向 | `0x5702/0x5703`（Wi‑Fi Sharing）、`0x4E0D/0x4E0E`（设备信息） | 门控：认证==2 且识别==6 |
| 16 | CarPlay 启动 | 车机 → 设备 | `0x4301`，14 字段 | 静态 `param_id→field` 已闭合；平台必填性、错误/重试及后续网络/媒体/输入仍 OPEN |
| 17 | 拆除 | 双向 | 平台 shutdown/close，链路显式 detach；重连重新 SDP | DISC/UA 由系统栈处理，不能作为应用字节写入 socket |

### 3.2 定时器

以 `control/spec/09` §8.8 为唯一来源：

| 定时器 | 值 | 起止 | 超时后 |
|---|---|---|---|
| `T_first_byte` | 2 s | RFCOMM 打开 → 收到首字节 | 发 Detect |
| `T_detect` | 5 s | 发出 Detect → 收到 SYN | 判 `NO_SYN`，重连 |
| `T_link` | 30 s | RFCOMM 打开 → 链路 `Connected` | 重连 |

这三个值是 `[建议]`，不是固件常量。当前 `link/spec/09` §9.10 已统一为 `T_detect` 超时记 `NO_SYN` 后重连；主动 SYN 是独立的实验配置，不是超时后的自动切换。

## 4. 帧与字段

### 4.1 iAP2 链路帧

```text
FF 5A | len_hi len_lo | ctrl | seq | lt | extra(hdr[7]) | hdr_cksum | payload | payload_cksum
```

- `len` 是**整帧长度**。创建默认 8 位校验；无载荷帧只有 9 字节头（含头校验），有载荷时才有尾校验。16 位模式的无载荷头长为 10。
- 头部校验**包含** `FF 5A`；传统帧 `FF 55` 的校验**不含** `FF 55`，这是最容易写错的一处。
- `ctrl` 常见值：SYN `0x80`、SYNACK `0xC0`、ACK `0x40`、RST `0x10`、RST|SYN `0x90`（触发条件未确认）。

### 4.2 消息与参数

```text
消息：40 40 | total_len (2) | msg_id (2) | params
参数：param_len (2) | param_id (2) | value
```

- 消息的 `total_len` 含 6 字节消息头；参数的 `param_len` 含 4 字节参数头。
- 参数可以嵌套；`len=4` 的空参数（`00 04 00 00`）真实存在。通用遍历器必须接受并继续按长度推进；是否解释为 presence/请求标记由消息 profile 决定。

### 4.3 SYN version 与载荷尾部

| SYN version | 载荷总长 | 尾部 |
|---|---|---|
| `0` | `10` 字节 | 无 |
| `1` | `10 + 3n` | 无扩展字节；`n` = 特性条目数 |
| `>=2` | `12 + k + 3n` | 先 `k`（扩展字节数），再 `k` 字节扩展，再 `n` 和条目 |

- 默认 `version=1`，默认 SYN 载荷 `0101ffff03e8000a1e00`。
- 该 10 字节默认值是结构初始化与编码向量；`R-3.5` 的接收合法性检查还要求至少一条有效特性条目。不要把“能编码”误写成“对端一定接受”。
- `version>=2` 时不能按 version 1 的偏移读特性条目；扩展字节语义仍是 `OPEN-SYN-4`。
- `R-3.9` 的整体协商决策仍有未决点；`IsValidSynParam` 的局部校验已确认为 minVersion..3，不能由此推出“version 2 自动降级到 1”。

### 4.4 `hdr[7]` 会话号

- `hdr[7]` 是链路头第 8 字节（`extra`），承载**会话号**。
- 应使用握手确认的控制会话条目。样本车机 SYN / iPhone SYNACK 尾部已分别含 `02 00 02` 或 `03 00 02`，业务 `hdr[7]` 随后为 2/3；不是客户端任意选号后才在首条业务消息声明。完整分配/表填充规则仍待核实。
- 链路控制帧（SYN/SYNACK/ACK/RST）的 `hdr[7]` 一律为 `0`。

### 4.5 帧长 vs RFCOMM 写块

- iAP2 的 `max_packet` 默认 `0xFFFF`。
- `min(N1,2570)=1007` 是参考 iOS 内部队列配置，不是所有平台 API 的上限。
- 发送按实际平台限制串行写并处理部分写；接收按 iAP2 长度字段重组，不把一次 `read()` 当一帧。

## 5. 识别

| 消息 | 方向 | 参数 | 作用 |
|---|---|---|---|
| `0x1D00` | 设备 → 车机 | 无 | 开始识别；`hdr[7]` 使用握手已确认的控制会话号 |
| `0x1D01` | 车机 → 设备 | 组 0，参数 ID ≤ `0x22` | 车机自述 |
| `0x1D02` | 设备 → 车机 | 无 | 接受识别结果 |
| `0x1D05` | 车机 → 设备 | 未观测 | 取消识别 |
| `0x1D06` | 车机 → 设备 | 未观测 | 更新识别 |

- `0x1D01` 是**入站无条件**；设备出站 `0x1D01` 需要认证+识别，客户端早期发会被门控拦下。
- 解析失败不能直接回接受；`0x1D03` 出站门控放行不等于其拒绝载荷 schema 已确认。未实现适用拒绝 profile 时本地报错停止，不猜造无参数取消消息。
- 配件自述的最小可接受参数集合尚待确定（`OPEN-ID-2`）。仿 iPhone 端负责解析/校验配件的 `0x1D01`；不要照配件角色发送名称、型号和 transport component 来替代设备侧的 `0x1D00`。

## 6. 认证

### 6.1 七步序列

> **协议族提示**：下面描述的是 **AccAuthentication**（`0xAA00`–`0xAA06`）。`link/spec/06` 另记 DeviceAuthentication（`0xAA10`–`0xAA15`，feature 7）与 MFi4Auth（构造侧 `0x5100`/`0x5110`/`0x5111`/`0x5112`/`0x5113`/`0x5115`）两套不同消息族；三者不能互推，也不能把本七步套到另外两族。

| 步 | 方向 | 消息 | 参数 | 客户端动作 |
|---|---|---|---|---|
| 1 | 设备 → 车机 | `0xAA00` | `00 04 00 00`（空参数） | 发出请求 |
| 2 | 车机 → 设备 | `0xAA06` | ID 0 = 32 B ASCII 十六进制串 | 解析并保存 |
| 3 | 设备 → 车机 | `0xAA00` | 无参数 | 第二次请求 |
| 4 | 车机 → 设备 | `0xAA01` | ID 0 = DER（本样本 607 B） | 解析证书链、验链、取叶证书公钥 |
| 5 | 设备 → 车机 | `0xAA02` | ID 0 = 32 B 随机数 | 生成挑战并保存 |
| 6 | 车机 → 设备 | `0xAA03` | ID 0 = 64 B 签名 | 用叶证书公钥验签 |
| 7 | 设备 → 车机 | `0xAA05` | 无 | 验签通过后发出 |

- 第 1 次 `0xAA00` 带 `len=4` 空参数，第 2 次不带参数；这是观测事实，不要合并成一次。
- `0xAA01` 长度随证书链变化，不能写死 607。
- 样本 `0xAA03` 为 P1363 裸 `r‖s`（各 32 B）；两次交换实际验签均成功。必须直接把该样本的 32 B 挑战传给 digest 验签接口，再做一次 SHA-256 会失败。不可未经验证推广到其他认证类型。
- 样本 PKCS#7 只有一张叶证书，不包含 Apple 根；其 serialNumber 与 `0xAA06` 文本匹配。证书签名算法是 `ecdsa-with-SHA256`，公钥算法 OID 是 `id-ecPublicKey`，曲线参数是 P-256，三者不能混用。完整验链仍需可信 CA/信任锚；见 `control/spec/11` 与 `runtime/verify-auth-sample.ps1`。

### 6.2 方向与门控

- 设备侧可主动发（白名单）：`0xAA00`、`0xAA02`、`0xAA04`、`0xAA05`；本流程实际用到 `0xAA00/02/05`。
- 车机回：`0xAA01`、`0xAA03`、`0xAA06`。
- `0xAA06` 入站要求识别信息对象存在、识别状态 == 6 **且接收集合非空并包含该 ID**，不要求认证完成。其他非白名单消息还要求认证 == 2；精确规则见 `control/spec/05` 及 `0x100051054` 汇编。

### 6.3 封装边界

当前 `link/spec/06 R-6.6` 已确认普通 `0xAAxx` 消息直接携带参数，`0x5500/0x5501` 属于中继路径，不能套用。24A446 的 `0xAA01` 还支持 ID 1/2；23G90 样本只有 ID 0，不等于所有版本都只有 ID 0。

## 7. 控制会话与门控

- 控制会话是会话表里**类型 0** 的表项；不是独立对象。
- 控制缓冲 `65535` 字节，单条消息上限与它一致。
- 初始化顺序：注册消息处理器 → 注册识别参数处理器 → 创建特性；初始化不发报文。
- 特性槽 29 个；奇数特性号跳过识别门控，偶数特性号要先通过“该特性已识别”。
- 版本门控：`version == 2` 先识别，`!= 2`（含 0、1）先认证；缺表时 version=0，默认认证优先。

### 7.1 两张门控名单

| 方向 | 无条件放行 | 需要“认证 2 + 识别 6 + 集合含 ID” |
|---|---|---|
| 入站 | `0x0000`、`0x0004`、`0x0005`、`0x1D01`、`0x1D05`、`0x1D06`、`0xAA01`、`0xAA03` | 其余 |
| 出站 | `0x0000`、`0x0004`、`0x0005`、`0x1D00`、`0x1D02`、`0x1D03`、`0xAA00`、`0xAA02`、`0xAA04`、`0xAA05` | 其余 |

`0xAA06` 是例外：不检查认证状态，但仍要求识别信息对象存在、识别 == 6 与接收集合包含该 ID。

### 7.2 常见业务消息

| 消息 | 方向 | 说明 |
|---|---|---|
| `0x5702` | 设备 → 车机 | Wi‑Fi Sharing 请求 |
| `0x5703` | 车机 → 设备 | Wi‑Fi 配置信息（SSID/口令/security/channel；**不是 NowPlaying**） |
| `0x4E0D` | 设备 → 车机 | 参数 0 = 1 字节 `0x01` |
| `0x4E0E` | 设备 → 车机 | 设备信息上报（MAC / 序列号） |

## 8. CarPlay 启动 `0x4301`

- `0x4301` 是**入站**消息（车机 → 设备），由特性 26 的处理器表承载，最终调用 `platform_CarPlay_startSession`。当前 `control/spec/04 R-4.12` 与 `spec/10 R-9.9` 已统一方向；平台调用存在不等于车机已显示画面。
- 14 个字段（顺序即日志格式串顺序）：

```text
usbIP, wifiIP, ssid, pass, securityType, channel, port,
deviceID, pubKey, srcVer, sdkVer, assetID, assetVer, mutualAuth
```

- 参数 ID → 字段的**静态映射已取证**：外层 `0/1/2/3/4/5/6/7/8`，外层 1 子 ID `0…4`，外层 7 子 ID `0…1`；端口/assetVer 为大端 U32，securityType/channel 为 U8，字符串值 NUL 结尾。可直接参考 [control spec/14](<iap2_control_session/spec/14-carplay-start-schema.md>)。
- 处理器 `0x10016d3ac` 的首个调用参数是按 primary-endpoint UUID 查得的 `EAConnectionID`，不是 endpoint；后续 14 字段按日志顺序传给平台。
- 平台必填性、错误/重试、Wi-Fi/IP、控制/媒体/输入和断线恢复仍是 `OPEN-SES-2`；L4 不能用本端 handler 返回 1 或调用日志代替端到端验收。

## 9. 拆除与重连

- 平台 socket：调用 shutdown/close，由系统栈完成协议关闭；应用不写 DISC 字节。
- 原始栈：DISC 基值 `0x43`，P/F=1 时线上为 `0x53`；收到合法 DISC 通常回 **UA**（线上 `0x73`），不是 DM。按状态机回收该 DLCI，监听服务独立管理。
- 重连：重新做 SDP（或使用带失效条件的缓存），拿新通道号；不要复用旧 DLCI。
- 不要用 EOF 隐式完成 detach；EOF 可以作为触发信号，但释放必须显式执行。

## 10. 客户端实现等级

| 等级 | 内容 | 通过判据 |
|---|---|---|
| **L0** | 链路 | 收到车机握手帧；收到 SYN；回 SYNACK 并被 ACK；60 s 无重传耗尽 |
| **L1** | 识别 | 发 `0x1D00`；收 `0x1D01` 并解析；发 `0x1D02`；链路不重置 |
| **L2** | 认证 | 七步齐全；按部署信任锚完成证书链验证（本样本不含 Apple 根，不能把样本验签当作根信任证明）；`0xAA03` 验签通过；发 `0xAA05`；车机继续发消息 |
| **L3** | 会话 | 已协商条目路由、重组、门控和异常测试通过；业务仅按支持的 profile 测试，见 control spec/12 |
| **L4** | CarPlay 启动 | 收到 `0x4301`；按静态 schema 解析 14 字段；平台交接及 Wi-Fi/IP、控制、媒体、输入仍需实机验收 |

L4 当前被 `OPEN-SES-2` 阻塞；不要跳级验收。

## 13. 版本判定速查

```text
SYN version：
  0    → SYN 载荷 10 字节，无尾部
  1    → 10 + 3n，无扩展字节（默认）
  >=2  → 12 + k + 3n，带扩展字节

控制会话 version：
  ==2  → 识别优先：0x1D00 → 0x1D01 → 0x1D02 → 认证
  !=2  → 认证优先：0xAA00 … 0xAA05（含 version 0、1）

两者独立：
  抓包可以是 SYN version=1 + 控制会话 version=2
```
