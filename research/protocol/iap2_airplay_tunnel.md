# iAP2 隧道封装适配 — 任务要求（`iap2_airplay_tunnel`）

> **历史任务书**：本文件是上游任务书，现行版本以 `research/protocol/iap2_airplay_tunnel/TASK.md` 为准；本文件保留用于追溯，不再单独修订。


> 本文件是**任务书**，不是协议规范。
> 目标：给出 AirPlay 字节流在 iAP2 上的封装规范：字节分片、流复用、通道标记、流控适配、分包重组。
>
> 口径：`CONFIRMED` 只表示“在本阶段证据范围内可复核”；隧道字段、通道号、最大分片等必须以抓包/实现证据为准，不得先验假定。

> **执行状态（2026-10-26）**：本任务已执行，产出在 [`iap2_airplay_tunnel/`](iap2_airplay_tunnel/TASK.md)（`verify.py` 10/10 通过）。
> 执行中发现**方向需修正**：24A446 里没有“AirPlay 字节装进 iAP2”的证据；证据支持的是
> **AirPlay 作为 iAP2 的传输**（23G90 抓包，`transport=AirPlay`、会话 3）与**iAP2 中继信封**
> （`0x5164/0x5264` 外层 + `0x5500/0x5501/0x5502/0x5503` 内层，`0x100022264`/`0x100022398`）。
> 因此下文 §5 的"字节分片/流复用/流控适配"在本阶段被证为**负结论**（信封层无分片、无复用、无信用），
> 逐项对账见 `iap2_airplay_tunnel/TASK.md` §5 与 `analysis/A-conclusions.md`。

## 0. 阶段定位

```text
AirPlay 控制面（airplay_control_plane）
  └─ RTSP SETUP / type=130 隧道交接
        ↓
【本阶段】AirPlay over iAP2 隧道
  ├─ 字节分片
  ├─ 流复用 / 通道标记
  ├─ 流控适配
  └─ 分包重组
        ↓
RTP / FairPlay / 视频 / 音频（后续阶段）
```

本阶段只回答：

- AirPlay 字节如何进入 iAP2；
- 分片头/通道标记/流 ID 的格式；
- 多路流如何复用；
- iAP2 的信用/流控如何映射到隧道；
- 接收端如何重组、排序、丢弃、报错。

**不回答**：AirPlay 控制面、FairPlay 算法、RTP 时序、编解码、输入业务。

---

## 1. 目标与完成判据

**目标**：产出可复现的隧道适配规范，使第三方客户端能：

1. 把 AirPlay 字节流封装进 iAP2；
2. 在多个流/通道之间复用；
3. 按对端信用/窗口发送；
4. 正确重组乱序/丢失/重复分片；
5. 处理隧道建立、拆除、错误与重连。

**完成判据**：

1. 12 项覆盖要求逐项有证据或 `OPEN`；
2. 至少一份真实抓包能展示“AirPlay 字节 → iAP2 分片 → 重组回 AirPlay 字节”的闭环；
3. 有分片/重组测试向量：正常、乱序、丢片、重复、超大、零长度；
4. 有流控测试：信用耗尽、窗口满、背压；
5. `verify.py` 可回放；
6. 不得把“能重组一条消息”写成“所有流可用”。

---

## 2. 素材与证据来源

| 素材 | 要求 |
|---|---|
| iAP2 抓包 | 含隧道建立、分片、流控、拆除 |
| AirPlay 原始字节 | 控制面/媒体流，用于对照重组结果 |
| 多流样本 | 至少视频 + 音频，或控制 + 媒体 |
| 流控样本 | 信用变化、窗口满、暂停/恢复 |
| 异常样本 | 丢片、乱序、重复、超时、断连 |
| 参考 | iAP2 既有 docset、AirPlay 控制面/隧道交接结论 |

---

## 3. 方法与证据链

1. **字节对齐**：先确定 AirPlay 字节流与 iAP2 消息的边界；
2. **封装解析**：逐字段解析隧道头、通道标记、流 ID、分片序号/长度/标志；
3. **重组**：按流 ID + 序号重建；记录乱序窗口、超时、丢片处理；
4. **流控**：记录信用/窗口变化与发送节奏；
5. **多流**：验证不同流 ID 的独立性与公平性；
6. **异常**：构造丢片、重复、乱序、超大分片；
7. **结论分级**：`CONFIRMED` / `INFERRED` / `OPEN`。

**禁止**：

- 把 iAP2 链路层的包边界当成 AirPlay 消息边界；
- 假设一个 iAP2 包只承载一个分片；
- 假设分片按序到达；
- 忽略流控直接灌数据。

## 4. 抽样策略

至少覆盖：

1. 隧道建立/交接；
2. 单流小包、单流大包（跨多分片）；
3. 多流并发；
4. 信用耗尽/窗口满；
5. 乱序、丢片、重复；
6. 隧道拆除/重连。

## 5. 覆盖要求（12 项）

| # | 要求 | 必须回答的问题 |
|---|---|---|
| 1 | **隧道建立** | 谁发起？与 `type=130` 的关系？建立时交换什么？ |
| 2 | **封装头** | 通道标记、流 ID、长度、标志位、序号各在哪？ |
| 3 | **字节分片** | 最大分片、分片边界、首片/中间片/末片如何标识？ |
| 4 | **流复用** | 多流如何区分？流 ID 宽度、分配、释放？ |
| 5 | **排序与重组** | 序号宽度、回绕、乱序窗口、重复/丢片处理？ |
| 6 | **流控适配** | iAP2 信用/窗口如何映射？何时暂停/恢复？ |
| 7 | **背压** | 接收端慢/缓冲满时如何反馈？是否丢流/断流？ |
| 8 | **错误处理** | 非法长度、未知流 ID、序号跳变、超时如何分类？ |
| 9 | **拆除** | 单流关闭 vs 隧道关闭 vs 链路断开，顺序与幂等性？ |
| 10 | **并发与公平** | 多流竞争时如何调度？有无优先级？ |
| 11 | **安全边界** | 隧道内数据是否已加密？是否信任流 ID？ |
| 12 | **版本与差异** | 不同车机/固件的封装差异？哪些字段可变？ |

### 5.1 重点专题

#### A. 封装与通道标记

必须给出线格式图：

```text
iAP2 消息/载荷
  └─ 隧道头（待证）
       ├─ 通道标记
       ├─ 流 ID
       ├─ 分片序号/标志
       └─ 数据
```

每个字段给出偏移、宽度、字节序、取值。

#### B. 分片与重组

必须给出：

- 最大分片与 MTU/链路包长的关系；
- 首片/末片标志；
- 重组缓冲上限；
- 乱序窗口与超时；
- 丢片时丢弃整条消息还是保留部分；
- 重复分片是否幂等。

#### C. 流控

必须给出：

- iAP2 信用/窗口的观测点；
- 隧道层是否有独立信用；
- 发送队列/背压；
- 流控暂停时是否缓存、丢弃或断流。

## 8. 已知风险与待决

| 风险/待决 | 影响 |
|---|---|
| 隧道头字段未证 | 无法互通 |
| 分片最大长度随链路变化 | 硬编码会失败 |
| 流 ID 分配规则不清 | 多流冲突 |
| 流控映射不清 | 发送过快/停滞 |
| 丢片策略不清 | 花屏/静音/整条丢弃 |
| 不同车机封装差异 | 不能一套打天下 |
