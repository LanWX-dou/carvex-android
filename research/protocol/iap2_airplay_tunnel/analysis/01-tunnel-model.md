# analysis/01 — 隧道模型：三层与两个方向

本文件回答"隧道到底在哪一层、谁包谁"。一句话：**24A446 里的隧道是"iAP2 消息包 iAP2 消息"，外层是一对中继消息（`0x5164`/`0x5264`），内层是 `0x55xx` 信封；AirPlay 只是承载 iAP2 链路的一种传输，不改变帧格式。**

## 1.1 三层

```text
传输层（BT Classic / USB / AirPlay …）
  └─ 链路层：iAP2 包（FF 5A | len | ctrl | seq | lt | session | hdrChk | payload | payloadChk）
       └─ 消息层：iAP2 消息（40 40 | len | msgID | params）
            └─ 中继层：0x5164 / 0x5264 外层消息（1 个参数：整条内层消息）
                 └─ 信封层：0x5500/0x5501（type+data）或 0x5502/0x5503（请求/信息更新）
```

- 传输层与链路层：见 `link/R-2.x`、`link/R-5.x`，本阶段不重复；
- 消息层：见 `control/R-3.x`；
- **中继层与信封层是本阶段新增**，代码全部在 `mfi4Auth`（MFi 认证会话）对象里，不在 iAP2 链路对象里。

## 1.2 中继对象（`mfi4Auth` 会话）

字段是从指令直接读出来的偏移；对象大小未定（`OPEN-TUN-8`）。

| 偏移 | 宽度 | 含义 | 指令依据 |
|---|---|---|---|
| `+0x10` | 8 | 消息缓冲指针（传给 `iAP2MsgInitWithSom`）| `0x1000858a0` `ldr x4,[x19,#0x10]` |
| `+0x18` | 4 | 消息缓冲长度 | `0x1000858a0` `ldr w5,[x19,#0x18]` |
| `+0x1c` | 2 | 最近一次发出的中继命令 ID（当前 `0x5164`）| `0x1000858a0` `strh w23,[x19,#0x1c]` |
| `+0x1e` | 1 | 关闭中标志（`==1` 时所有入口直接失败）| `0x10008449c` `0x100084da8` 开头 |
| `+0x58` | 4 | 动作/状态计数（发 `0x5502` 前置 `0xF`）| `0x100083ecc` `str w?, [x19,#0x58]` |
| `+0x80` | 8 | 本次协商出的 capabilities 掩码 | `0x100083ecc` `ldr x?, [x19,#0x80]` |
| `+0x88` | 8 | 已生效（processed）的 capabilities 掩码 | `0x100083ecc` `[+0x88]` 读写 |
| `+0xE8 + 8*type` | 8×3 | `type` 0/1/2 的接收 handler（`type<3`）| `0x100084da8`、`0x10008449c` |
| `+0x140` | 8 | handler 提供者（虚表 `+0x10` 为 `startRelay(type)`）| `0x100084bd4` `param_1[0x28]` |
| `+0x150` | 2 | 本会话的 SOM 值（传给 `iAP2MsgInitWithSom`）| `0x1000858a0` `ldrh w1,[x19,#0x150]` |

> `+0xE8` 的 `type<3` 上界在**两个方向**都检查（入站 `0x10008449c`、出站 `0x100084da8`），日志串分别是 `"no secureTunnelHandler for type %d !!!"` 与 `"invalide secureTunnelType (%d)"`（`0x1f1e57`、`0x1f1aa2`）。

## 1.3 消息对（方向与 ID）

| ID | 方向 | 名称（由代码结构命名）| 载荷 | 指令依据 |
|---|---|---|---|---|
| `0x5164` | 设备 → 车机 | 中继请求 | 1 个参数（id 0）= 整条内层消息字节 | `0x1000858a0` `mov w23,#0x5164` / `0x1000858fa` |
| `0x5264` | 车机 → 设备 | 中继数据 | 1 个参数 = `0x5501`/`0x5503` 字节 | `0x100083ecc` `mov w8,#0x5264` @`0x100083f8c` |
| `0x5265` | 车机 → 设备 | 中继失败 | 无/错误信息 | 同上 @`0x100083f80` |
| `0x5266` | 车机 → 设备 | 中继成功 | 无 | 同上 @`0x100083f74` |
| `0x5500` | 设备 → 车机 | 隧道数据（设备侧打包）| param0=type(u8), param1=data | `0x100022264` `mov w8,#0x5500` @`0x1000222d4` |
| `0x5501` | 车机 → 设备 | 隧道数据（对端打包）| 同上 | `0x100022398` @`0x10002244c` |
| `0x5502` | 设备 → 车机 | 请求配件信息更新 | 无参数 | `0x100084acc` `mov w1,#0x5502` @`0x100084b28` |
| `0x5503` | 车机 → 设备 | 配件信息更新 | param0..4 字符串、param 0xF2 u64 | `0x100022398` @`0x100022440`、`0x100085034` |

**方向规则（已确认）**：

1. 设备只**发送** `0x5164`、`0x5500`、`0x5502`；只**接收** `0x5264/0x5265/0x5266`、`0x5501`、`0x5503`。
2. 本构建**没有**"接收 `0x5500`"的分支（`unpack` 只认 `0x5501`/`0x5503`），也**没有**"发送 `0x5501`"的调用点（全二进制里 `packIntoTunnelDataiAP2Msg` 的唯一调用点传 `flag=0`，得 `0x5500`）。
3. 因此 `0x5500`/`0x5501` 是**同一结构的两个方向 ID**，而不是"分片首/续片"（见 `A07.1`）。

## 1.4 一次完整往返（由代码拼出）

```text
设备                                                  车机
 |  (可选) 0x5502 请求信息            ──0x5164──▶
 |                                                    | 回 0x5503（信息）
 |◀──0x5264──  0x5503 字节
 |  解析 param 0..4 + 0xF2，更新 capabilities 掩码
 |
 |  掩码 bit2 由 0 变 1 → StartRelayForType(type=2)
 |
 |  业务数据 d，type=t(0..2)         ──0x5164──▶
 |      内层 = 0x5500(param0=t, param1=d)
 |                                                    | 回 0x5264（0x5501）或 0x5265/0x5266
 |◀──0x5264──  0x5501(param0=t, param1=d')
 |  d' 交给 handler[+0xE8+8*t]
```

每一步都有指令依据；"何时发第一条 `0x5502`"取决于 `+0x58==0 && 掩码非 0 && bit0 变化`（`0x100083ecc` @`0x10008447`–`0x1000844ac`），完整状态图见 `analysis/03`。

## 1.5 与 AirPlay 的关系

- AirPlay 是**传输**：同一个 accessoryd 用 `transport=AirPlay` 记录 iAP2 包（`A05.1`）；
- 中继层与信封层**不感知**传输类型：`processIncomingMessageRelay` 只拿消息对象，不查 `transportType`；
- 所以"隧道跑在 AirPlay 上"这件事，在 accessoryd 里**没有**专门代码分支——它由传输插件把字节送进来（`OPEN-TUN-5`）。
