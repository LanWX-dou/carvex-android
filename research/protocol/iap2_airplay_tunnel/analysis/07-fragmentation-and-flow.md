# analysis/07 — 分片、重组与流控（负结论）

本阶段最重要的四个"没有"，全部给出检索口径，避免"没看到 = 不存在"的偷懒。

## 7.1 信封层没有分片

`pack` 只加两个参数，且顺序固定（`0x1000222f0`、`0x1000222fc`）：

```text
param0: id=0, u8   type
param1: id=1, data 整块
```

`unpack` 只认这两个 id（`0x1000224c4`–`0x1000224d4`）：

```text
id==1 → data  (CFDataCreate，长度 = GetParamValueLen)
id==0 → type  (GetDataAsU8)
其它 → 忽略
```

**没有** fragment index / total / more-flag / offset / sequence 字段。因此：

> 信封是"一条消息一次装完"的原子单元；不存在"首片/中间片/末片"。

## 7.2 多个 param1 是覆盖，不是拼接

`0x1000224b8` 循环里，遇到第二个 `id==1` 会先 `CFRelease` 旧的再建新的，日志 `"Already have unpackedMessage %ld bytes !!!, release and create new one"`（串 `0x1da562`）。所以即使对端发了多片，本侧也**只保留最后一片**——这进一步证明协议设计上不允许分片（否则会拼接）。

## 7.3 外层 `0x5164` 也只有 1 个参数

`initMessage_DeviceiAP2RelayRemote`（`0x1000858a0`）只调用一次 `iAP2MsgAddDataParam(msg, 0, 0, inner, len)`，`0x5163`（`0x100084fa4`）干脆没有参数。没有"第 N 包"的位置。

## 7.4 真正的分片/重传在链路层

- 链路层包有 `seq`/`ack`/`lt`/`hdrChk`/`payloadChk`，消息跨包由链路层保证顺序与重传（`link/R-2.x`、`link/R-4.x`）；
- 会话层解析器是**逐字节**喂的（`control/A08.1`：`iAP2MsgParserConsumeByte` 每次 1 字节），因此一条 65 KB 的信封消息在链路上必然跨多个包，但这对信封层不可见；
- 抓包里 `0xAA01` 617 字节的消息在 627 字节的链路包里一包发完；`0x1D01` 313 字节同理——只能说明"这个尺寸没跨包"，不能说明链路 MTU。

## 7.5 流控：隧道层没有信用/窗口

| 层 | 流控机制 | 证据 |
|---|---|---|
| iAP2 链路 | seq/ack/重传/队列上限 | `link/R-4.x`、`control/R-6.x` |
| 中继（`0x5163/0x5164/0x5264`）| 参考实现保守停等；完整并发限制未证 | `A03.4` |
| 信封（`0x55xx`）| **无** | 信封里没有信用/窗口字段（`A02.1`）|

已证实 `0x5164` 更新最近命令字段、`0x5266` 触发 `0x5163`、失败回调更新认证状态。这些证据不足以证明所有发送入口受同一个单条在途闸门约束，也不能由信封无窗口字段推断对端必为停等。

## 7.6 对实现的含义

1. 设备侧原型建议采用"发送队列 + 一次一条"作为保守策略，完整调度与对端并发能力仍待验证。
2. 单条隧道数据的上限是 **65,520 字节**（`A02.3`）；超过必须由上层业务自己切，切完的各条之间**没有**序号，恢复顺序要靠业务字段。
3. 不要试图在信封上实现"重传/去重"——没有序号可用；重传只发生在链路上。
