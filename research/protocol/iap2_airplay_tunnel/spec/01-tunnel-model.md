# spec/01 — 隧道模型与消息族

## 1.1 分层

**R-1.1** 设备侧必须按下列顺序封装：传输 → 链路包 → iAP2 消息 → 中继消息（`0x5164`/`0x5264`）→ 信封（`0x55xx`）。任一层不得越级写字节。
依据：A01.1、A02.1

**R-1.2** 状态存放在该连接关联的 `mFi4Auth` 对象；`protocolRouter` 是连接级对象，并通过 endpoint 指针绑定到该连接。是否能在不同传输之间复用同一认证状态，当前未由固件证明，不能把“换传输不重建”作为 MUST。
依据：`analysis/09-open-items-firmware.md` §9.6、A01.2、A01.4；跨传输复用为 OPEN。

**R-1.3** 中继层不得因传输类型（BT/USB/AirPlay）改变线格式。
依据：A01.4

## 1.2 消息族与方向

**R-1.4** 在 24A446 该 handler 路径中，设备侧观察到发送：`0x5163`、`0x5164`、`0x5500`、`0x5502`；这不是整个 CarPlay/AirPlay 协议的全局枚举。
依据：A01.3

**R-1.5** 在同一路径中，设备侧观察到接收：`0x5264`、`0x5265`、`0x5266`、`0x5501`、`0x5503`；其它 msgID 的处置属于该 handler 的错误策略，不应泛化为所有实现的全局规则。
依据：A01.3、A03.2

**R-1.6** 本设备侧业务发送用 `0x5500`，接收投递用 `0x5501`。格式工具可解析两者用于回放自测，但真实会话默认不投递对端的 `0x5500`；若其它 profile 需要兼容，须取得独立证据并显式启用，不能由格式同构推出方向合法。
依据：A01.3、A02.1

## 1.3 中继消息一览

| ID | 方向 | 参数 | 用途 |
|---|---|---|---|
| `0x5163` | 设备→车机 | 无 | 请求对端重发一条隧道数据 |
| `0x5164` | 设备→车机 | param0 = 整条内层消息 | 发出隧道数据 |
| `0x5264` | 车机→设备 | param0 = 内层消息字节 | 对端发来隧道数据 |
| `0x5265` | 车机→设备 | — | 失败 |
| `0x5266` | 车机→设备 | — | 成功 |

**R-1.7** `0x5164` 的参数必须恰好一个，ID 为 0，值是**完整的内层消息**（从 `40 40` 开始，含长度字段）。
依据：A03.1

**R-1.8** `0x5163` 必须无参数（总长 6）。
依据：A01.3

## 1.4 type

**R-1.9** `type` 必须取 0、1、2 之一；发送前与接收后都必须校验 `< 3`，越界即丢弃（发送侧不发、接收侧不投递）。
依据：A04.1

**R-1.10** 设备侧必须为每个 type 维护一个接收槽位；槽位未启用时不得收发该 type（发送侧拒绝、接收侧丢弃）。
依据：A04.2

## 1.5 状态机（设备侧）

```text
[会话建立]
   ↓
[AUTH_READY] ── 收到 0x5264(0x5503) → 更新 capabilities；bit0 新置位优先发 0x5502，
   ↓                                       同次调用不再处理 bit2；否则 bit2 新置位 → 启动 type2 槽
[IDLE] ── 上层要发数据(type t) → 组 0x5500 → 套 0x5164 → 发
   ↓
[WAIT_RSP] ── 0x5266 → 发 0x5163 → 保持 WAIT_RSP（等下一条 0x5264）
   │        └ 0x5265 → 认证失败（AuthState=1），隧道不可用
   │        └ 0x5264 → 投递数据 → 回 IDLE
   └ 超时/空载荷 → 按 R-3.5
```

**R-1.11** 状态迁移只允许沿上图箭头；未收到响应前不得再发 `0x5164`（见 R-3.4）。
依据：A03.3、A03.4
