# spec/05 — 设备侧实现指南（L0–L4）

本文件回答"照着这份文档能不能写出客户端"。结论：**可写出信封 codec 与受限事务原型；完整 L0–L4 还需认证、传输、业务 profile 和真实车机验证**。一个实验不保证关闭全部缺口。

## 5.1 分级

| 级别 | 内容 | 依赖 | 可验证性 |
|---|---|---|---|
| **L0** | 识别信息（`0x1D00/01/02`）与认证（`0xAA00…`）在 AirPlay 传输上照常 | `control/` | 抓包可验 |
| **L1** | 中继信封编解码（`0x5500/0x5501/0x5502/0x5503`）| 本文 R-2.x | 向量可验 |
| **L2** | 中继事务（`0x5163/0x5164/0x5264/0x5265/0x5266`）| 本文 R-3.x | 向量 + 抓包 |
| **L3** | 按 `type` 把数据交给业务（Location 等）| `OPEN-TUN-2` | 需实验 `EXP-1` |
| **L4** | AirPlay 隧道本体的帧/MTU/握手 | `OPEN-TUN-5` | 需 AirPlay 侧文档 |

**R-5.1** 实现必须至少完成 L0–L2 才能声称"支持 iAP2 隧道"；L3 只有在 `EXP-1` 通过后才能声称。
依据：A01.1、A02.1、A03.2

## 5.2 L1 最小实现（信封编解码）

**R-5.2** 内层编码函数：`encode_tunnel_data(type, data) -> bytes`，输入校验 `0 ≤ type ≤ 2`、`len(data) ≤ 65520`，输出 R-2.2 的布局；真正经 `wrap_relay`/MFi4 发送时还必须执行 R-2.14a 的外层长度校验。
依据：A02.1、A02.4

**R-5.3** 解码函数：`decode_tunnel_data(bytes) -> (msg_id, type, data)`，必须：
1. 校验 `40 40`、`len` 自洽；
2. 入站业务投递仅接受 `msg_id == 0x5501`；codec 解析 `0x5500` 只服务于格式检查，不代表会话接受该方向；
3. 遍历参数，取最后一个 `id==1`；
4. 缺 `id==1` 时返回"空载荷"而非空字节串。

依据：A02.1、A02.5、A03.5

**R-5.4** 信息更新编码：`encode_request_info() -> 40 40 00 06 55 02`；信息更新解码：`decode_info_update(bytes) -> dict`（0–4 字符串、`0xF2` u64）。
依据：A02.2、A04.3

## 5.3 L2 最小实现（事务）

**R-5.5** 参考实现使用发送队列 + 保守停等状态机（R-3.9/R-3.10）；等待响应时可入队，但不发下一条。对端并发限制未证。
依据：A03.4

**R-5.6** 收到 `0x5266` 立即发 `0x5163`；收到 `0x5265` 终止隧道；收到 `0x5264` 走 `R-3.5` 分派。
依据：A03.2、A03.3

**R-5.7** 日志必须能区分五种失败：`type` 越界、槽位未启用、内层 ID 未知、长度非法、空载荷（对应 `A06.1` 的日志串）。
依据：A06.1

## 5.4 L3 的缺口（必须做实验）

**R-5.8** 在 `EXP-1` 完成前，不得把"业务数据走 `type=0/1`"写进实现说明；Location 类数据在 23G90 抓包里走的是**独立消息 `0xFFFA/0xFFFB/0xFFFC`**，不是 `0x55xx`。
依据：A05.3、A05.4、A04.1

**R-5.9** 若 `EXP-1` 发现对端用 `0x5501(type=t)` 下发业务数据，实现必须把 `type=t` 的槽位接到对应业务解码器；在此之前槽位保持"未启用"是合法状态。
依据：A04.1、A04.2

## 5.5 L4：AirPlay 传输接入

**R-5.10** 在当前 23G90 AirPlay 样本中，设备侧看到的是**iAP2 帧字节原样收发**，未见额外自定义头；这只是样本观察，不是所有 AirPlay 版本/车机的 MUST。目标实现应把传输适配层做成可配置，并用抓包确认是否存在外层封装。
依据：A05.1、样本限定（23G90）

**R-5.11** 会话号应沿用 SYN/SYNACK 的协商结果；本样本为 `3`，不得把样本值硬编码为通用常量，也不得另开未协商会话。
依据：A05.2

**R-5.12** AirPlay 隧道自身的帧格式与 MTU 属 `OPEN-TUN-5`；在补齐前，实现应把 MTU 当"未知"处理，通过 `EXP-2` 探测。
依据：A05.1、A05.4

## 5.6 明确不要做

| 不要做 | 原因 |
|---|---|
| 在信封里加序号/分片/校验 | 固件没有这些字段，对端会忽略或报错（R-4.1）|
| 未经验证就流水线发多条 `0x5164` | 对端并发限制未闭合，参考实现保守停等（R-3.9）|
| 把 `0x5265` 当"丢一条" | 对端把它升级为认证失败（R-3.7）|
| 用 `0x5501` 发送 | 固件从不发这个方向（R-1.6）|
| 假设隧道内已加密 | 信封明文，加密只在 MFi 层（`OPEN-TUN-10`）|

## 5.7 验收自检

**R-5.13** 声称 L2 完成前，必须能复现下列四件事：编码向量全过、解码向量全过、停等状态机在"响应丢失"时不重发、`0x5265` 后不再发送任何中继消息。
依据：A03.3、A03.4、A06.1

**R-5.14** `reference-impl/relay_session.py` 可作明文事务模型（`RelaySession.enqueue/tick/on_message`）。`secure=True` 只采用更小长度上限，**不实现加密**；仍须补 MFi4 AEAD、认证状态、能力闸门生命周期、超时与实际 I/O。能力方法输出的是内层查询意图，不是可直接写入传输的完整握手。合成自检不能证明替换 I/O 即可互通。
依据：A03.3、A03.4、A03.5

**R-5.15** 若目标车机已完成 MFi4 会话（密钥就绪），`0x5163/0x5164` 的载荷是**密文**：客户端要么实现该会话（`ccsigma` KEX + AEAD，见 `analysis/09` §9.5），要么明确声明"只在认证前/无密钥链路上工作"。不得把明文信封发进已加密会话，也不得把密文当明文解析。
依据：A09.5、A09.6
