# 00 — 范围、术语与证据等级

> 本规范回答“**怎么在 Wi-Fi 上找到车机的 AirPlay 服务，并把它解析成可连接的地址/端口/能力**”。
> 不回答：配对、加密、媒体、CarPlay 投屏、蓝牙 iAP2。发现成功 ≠ 可连接 ≠ CarPlay 可用。

## 0.1 范围

**做**：

- 组播/单播 mDNS 报文的收发与解析（§1）；
- `_airplay._tcp` 及同类服务的浏览（§2，待补）；
- TXT 的线格式与键表（§3）；
- `features` 位图的读取方式（§4）；
- 地址解析与候选排序（§5，待补）；
- 客户端实现顺序与验收（§6，待补）。

**不做**：AirPlay 配对（Pair-Setup/Pair-Verify）、RTSP、RTP、镜像/音频、iAP2、A2DP。
见任务书 §7 与 `analysis/00` §0.1。

## 0.2 术语

| 术语 | 定义 |
|---|---|
| 服务类型 | DNS-SD 的服务名，形如 `_airplay._tcp`，枚举时加 `.local.` |
| 实例（instance） | 某个服务类型下的一个具体服务，形如 `Living Room._airplay._tcp.local.` |
| 目标主机（target） | SRV 里的 target，形如 `Receiver.local.` |
| 主机地址 | 目标主机的一条 A/AAAA |
| 候选（candidate） | 一个实例 + 它的 SRV + 至少一条地址，可被连接尝试 |
| QU | question 的 unicast-response 位 |
| cache-flush | RR 的 CLASS 最高位 |
| goodbye | TTL=0 的记录撤销 |
| `features` | AirPlay TXT 里的能力位图（文本形式） |

## 0.3 证据等级

与 `analysis/00` §0.3 一致：

- `CONFIRMED`：本阶段材料内可复核（字节、指令地址、哈希、可执行测试）；
- `INFERRED`：由指令形态推断，文中写“推断”；
- `标准`：RFC 6762/6763 条文，**本阶段未联网取回原文**；
- `OPEN`：无证据，登记在 [`08-open-items.md`](08-open-items.md)。

## 0.4 规则

- **R-0.1**（MUST NOT）本规范不得用于描述配对、加密、媒体传输或 CarPlay 投屏；这些问题归后续阶段。
  依据：`A00.1`（本阶段证据只有 `APTransport` 的发现层字符串与解析函数）

- **R-0.2**（MUST）实现必须把“服务类型 / 实例 / 目标主机 / 主机地址”四层分开建模；PTR 给出实例，SRV 给出目标与端口，TXT 给出属性，A/AAAA 给出地址，四者可独立缺失。
  依据：`A02.1`、`[RFC 6763 §5.2]`

- **R-0.3**（MUST）任何未取证的字段、位、键、行为，必须在实现里保留原始字节并标记 `OPEN`，不得静默丢弃、不得按“常见含义”赋值。
  依据：`A02.2`、`OPEN-MDNS-10`

- **R-0.4**（MUST）文档必须区分“24A446 静态代码证明的行为”与“车机实测行为”；前者不得写成后者。
  依据：`A00.1`、`A09.1`

- **R-0.5**（MUST）客户端不得把发现结果直接当作身份：TXT 里的 `pk`/`pi`/`gid` 未被证明用于校验，连接前必须走配对流程（后续阶段）。
  依据：`A02.3`、`OPEN-MDNS-13`

- **R-0.6**（MUST）在拿到真实车机 mDNS 抓包之前，`spec/01` §1.5 与 `spec/03` 的所有“车机取值”类结论只能是 `OPEN`，实现必须能在“服务图为空”时正常退出而不是崩。
  依据：`A09.1`、`A09.3`、`OPEN-MDNS-7`
