## 12.1 解码规则

A12.1（已确认）消息处理器表以 **16 字节**为一项，布局为：

```
struct { u32 msg_id; u32 reserved; u64 handler; }
```

A12.2（已确认）`handler` 指针有两种编码（rebase / chained fixup），统一按
`target = 0x100000000 + (value & 0xFFFFFFFFFF)` 解码。该规则对 `__DATA_CONST`
中的状态机表、特性表同样成立（见 `source/metadata/tables.json` 的 `pointer_rule`）。

A12.3（已确认）表项按 `msg_id` 严格递增排列，扫描为线性查找；`msg_id` 为 16 位。

## 12.4 观察与限制

A12.4（已确认）`Identification` 表只有 3 条，且 handler 均为**无符号函数起点**
（`0x10011e6e4`、`0x10011ec18`、`0x10013bcc8`）；它们存在于 `LC_FUNCTION_STARTS`，
说明是真实函数，只是名字被剥掉。因此**不能**用符号名反推这三条消息的语义。

A12.5（已确认）`CarPlayStartSession` 只有 1 条（`0x4301`），`ExternalAccessory` 只有 1 条
（`0xEA03`）——这两个「阶段边界」消息在固件里都是单条，说明它们不是批量消息族。

A12.6（未确认 / `OPEN-MSG-1`）所有 handler 的**参数与副作用**未取证：本文件只确认
"哪个 msg_id 由哪个函数处理"，不确认处理内容。

A12.7（未确认 / `OPEN-MSG-2`）`msg_id` 的编号空间（例如 `0x1D0x`、`0xAA1x`、`0x43xx`）
在本二进制里没有枚举名可读，前缀语义无法从固件取证。
