# spec/06 — 识别、认证与会话启动边界

本文件规范识别与认证两阶段的**消息级与参数级**事实：`msg_id` → handler、参数 ID → 取值类型。识别参数见 `R-6.3`；`0xAAxx` 认证消息直接携带参数，不套 `0x5500/0x5501` 中继封装（`R-6.6`）。23G90 的识别/配件认证观测顺序见 control `spec/09`、`spec/11`；不得将该样本推广为所有版本、认证类型的唯一顺序。

## 6.1 识别阶段

`R-6.1`（MUST / CONFIRMED）识别阶段的触发是传统 iAP 的 RequestIdentify 帧（`R-2.11`），响应是一组 iAP2 识别消息。

依据：`A08.2`、`A07.3`。

`R-6.2`（MUST / CONFIRMED）识别消息共 3 条：

| `msg_id` | handler |
|---|---|
| `0x1D01` | `0x10013bcc8` |
| `0x1D06` | `0x100050934` |
| `0x1D05` | `0x10013b28c` |

依据：`A08.1`（表 `0x10021a7e0`）。

`R-6.3`（MUST / CONFIRMED）`0x1D01` 的识别参数按**参数组 0** 逐参数解析，由 `__parseIdentificationParams`（`0x1000512e8`）按参数 ID 分派；合法上限 `0x22`，越界即拒绝。各 ID 的取值类型：

| 参数 ID | 类型 | 参数 ID | 类型 |
|---|---|---|---|
| `0x00`–`0x05` | 字符串 | `0x12` | 拒绝 |
| `0x06`/`0x07` | 数据（消息集合，方向位 1/0） | `0x13` | 拒绝（显式） |
| `0x08`–`0x0b` | 拒绝 | `0x14`–`0x17` | 拒绝 |
| `0x0c` | 字符串 | `0x18` | transport component 4（无线 CarPlay） |
| `0x0d` | 字符串集合（重复即拒绝） | `0x19` | 拒绝 |
| `0x0e`–`0x11` | transport component 0–3 | `0x1a` | transport component 5（蓝牙 LE） |
| | | `0x1b`–`0x21` | 拒绝 |
| | | `0x22` | 字符串 |

拒绝必须记录 `(paramID, reason)`，reason 至少 `1`（未处理/越界）、`4`（集合重复）、`8`（字符串解析失败）。

依据：`A08.4`、`A08.7`、`A08.8`（`f_1000512e8.s` 的 switch 与 `__addRejectParam` 调用点）。

`R-6.3.1`（MUST / CONFIRMED）transport component 的编号是固定常量，每个 component 内部再按子参数解析：

| 编号 | 传输 | 子参数 `0x00` | `0x01` | `0x02` |
|---|---|---|---|---|
| 0 | 串行 | U16 标识 | 名称字符串 | 存在性标志（空数据→1，非空→拒绝） |
| 1 | USB Device | 同上 | 同上 | 同上 |
| 2 | USB Host | 同上 | 同上 | 同上 |
| 3 | 蓝牙 | 同上 | 同上 | 同上 |
| 4 | 无线 CarPlay | 同上 | 同上 | 同上 |
| 5 | 蓝牙 LE | 同上 | 同上 | 同上 |

依据：`A08.5`、`A08.6`（`0x1000515e4` 附近 5 处回调绑定；`0x10004f254` 的三段子参数分派）。

`R-6.4`（未定义 / OPEN）识别消息的**发送顺序**、必需参数集合、超时，以及 `0x1D01/0x1D05/0x1D06` 的角色差异未确认。实现须把这些做成配置。

依据：`A08.9`、`OPEN-ID-1`、`OPEN-ID-2`、`OPEN-ID-4`。

## 6.2 认证阶段

`R-6.5`（MUST / CONFIRMED）认证消息分两组：

| 组 | `msg_id` | handler |
|---|---|---|
| DeviceAuthentication | `0xAA10` | `0x100123108` |
| | `0xAA12` | `0x100123204` |
| | `0xAA14` | `0x10012356c` |
| | `0xAA15` | `0x100123690` |
| AccAuthentication | `0xAA01` | `0x1001850bc` |
| | `0xAA03` | `0x100185d6c` |
| | `0xAA06` | `0x1001860d4` |

依据：`A09.1`、`A09.2`（表 `0x100218eb0`、`0x1002205d8`）。

`R-6.6`（MUST / CONFIRMED）认证消息的**载荷是消息自身的参数组 0**（裸参数），**不是**嵌套的 `0x5500/0x5501` 隧道。按消息与方向分别确认：

| 消息 | 方向 | 载荷位置 | 依据 |
|---|---|---|---|
| `0xAA01` / `0xAA03` / `0xAA06` | 车机 → 设备 | 直接 `iAP2MsgGetFirstParam` 读参数组 0 | `A09.9`（`0x1001850bc`、`0x100185d6c`、`0x1001860d4`） |
| `0xAA11` / `0xAA13` | 设备 → 车机 | `iAP2MsgInit(msg_id, buf, 0xFFFF, …)` + `iAP2MsgAddDataParam`（组 0） | `A09.10`（`0x10002e5b4`、`0x10002e730`） |

`0x5500/0x5501` 是**中继路径专用**（`A09.11`：唯一构造者 `0x100022264`，唯一调用者 `0x100084ef4`），**不得**用作 `0xAA01/0xAA03/0xAA06/0xAA11/0xAA13` 的封装。

**不得**实现成"两种封装都支持"：本阶段有证据的只有裸参数这一种。

依据：`A09.9`、`A09.10`、`A09.11`。

`R-6.6.1`（MUST / CONFIRMED）已确认的认证消息参数（参数组 0；入站 `0xAA01/0xAA03/0xAA06` 与出站 `0xAA11/0xAA13` 均为裸参数，见 `R-6.6`）：

| `msg_id` | 参数 | 类型 | 语义（固件日志字符串） |
|---|---|---|---|
| `0xAA01` | `0x01` | U8 | auth type |
| `0xAA01` | `0x02` | 数据 | `pAccCertData`（配件证书） |
| `0xAA01` | `0x00` | 数据 | `pAccIntermediateCertData`（中间证书） |
| `0xAA03` | `0x00` | 数据 | `pAccSignData`（配件签名） |
| `0xAA06` | `0x00` | 数据 | `pAccSerNumData`（证书序列号） |
| `0xAA12` | `0x00` | 数据 | `pChallengeBytes`（挑战） |
| `0xAA10` | 无参数 | — | 触发型：请求设备证书 |
| `0xAA14` | 无参数 | — | 状态置 1（失败） |
| `0xAA15` | 无参数 | — | 状态置 2（成功） |

两组 handler 的 feature 不同：AccAuthentication（`0xAA01/03/06`）查询 **0**，DeviceAuthentication（`0xAA10/12/14/15`）查询 **7**；不存在时返回未处理。不得将 feature 7 的门控套到配件认证。汇编例：`0x10018510c` 与 `0x100185db8` 为 `mov w1,#0`，`0x100123130` 为 `mov w1,#7`，均调用 `0x100003360`。

依据：`A09.5`、`A09.6`、`A09.7`。

`R-6.6.2`（MUST / CONFIRMED）`0xAAxx` 与 `0x51xx` 是**不同认证协议族**；实现必须先判族，不能把同名/近名消息互相当作同一载荷：

| 协议族 | 线上消息 | 角色/门控 | 证据状态 |
|---|---|---|---|
| AccAuthentication | `0xAA00`–`0xAA06` | 车机向设备证明；feature 0；23G90 七步样本 | 样本已观测 |
| DeviceAuthentication | `0xAA10`–`0xAA15` | 设备侧认证；handler 查询 feature 7；无端到端样本 | 静态 |
| MFi4Auth | `0x5100`、`0x5110`、`0x5111`、`0x5112`、`0x5113`、`0x5115`… | `mfi4Auth_protocol_*`；设备/配件双向握手 | 静态；部分 ID 映射 |

下表只描述 **MFi4Auth**；`0xAAxx` 两族见 `R-6.5`、`R-6.6.1`。**消息构造侧**已确认的 ID：

| 消息 | 构造侧 ID | 构造/处理函数 | 依据 |
|---|---:|---|---|
| RequestAuthSetup / AuthSetup | `0x5100` | `0x100132e28` / `0x100045148` | `f_100132e28.ghidra.c:52`；`f_100049224.s:167-173` |
| RequestAuthStart | `0x5110` | `0x100132fc0` | `f_100132fc0.ghidra.c:51` |
| AuthStart | `0x5111` | `0x1000464e8` | `f_1000464e8.ghidra.c:168` |
| RequestAuthCert | `0x5112` | `0x100048904` | `f_100048904.ghidra.c:35` |
| AuthCert | `0x5113` | `0x1001330e0` | `f_1001330e0.ghidra.c:125` |
| RequestAuthChallengeResponse | `0x5115` | `0x100044f3c` | `f_100044f3c.ghidra.c:33` |
| AuthChallengeResponse / AuthFinish / AuthSetupFailed | 未完全闭合 | 分派侧与 `0x5115`–`0x5117`、`0x5111/0x5113` 分组相关 | `f_100049224.s:134-140,192-212` |

**构造侧 ID 只证明发送时写入的值；接收分派可能按方向/状态复用或成组处理。** 例如 `0x5100` 在分派侧同时进入 `AuthSetup` 与 `AuthSetupFailed`，`0x5112` 进入 `AuthCert` handler，`0x5111/0x5113` 经掩码 `&~2` 进入 `AuthFinish`，`0x5115`–`0x5117` 另有成组分支。因此不能只凭 ID 判定语义，精确映射仍需逐分支闭合（`OPEN-AUTH-1`）。

本条的 `CONFIRMED` 仅指“三套协议族不同”与上表已列出的构造侧 ID；表中标“未完全闭合”的接收分派项仍归 `OPEN-AUTH-1`，不得当作已证线上映射。

依据：`A14.1`（`0x100045148`、`0x100046830`、`0x1000468dc`、`0x100046c78`、`0x100048bd8`、`0x100048a1c` 等）及上述原切片。

`R-6.6.3`（MUST / CONFIRMED）认证协议的密码学操作是**操作级接口**，实现应调用平台提供的能力，而不是自行实现算法：

| 操作 | 输入 → 输出 | 说明 |
|---|---|---|
| 生成挑战 | 无 → 随机字节串 | 随机源为系统随机（固件用 `arc4random_buf`）；长度随证书确定 |
| 校验证书链 | 证书链 → 通过/失败 | 由平台框架完成 |
| 验证挑战响应 | 挑战 + 签名 + 证书 → 通过/失败 | 由平台框架完成 |
| 解析证书 | 证书字节 → 结构 | 固件内含轻量 X.509 解析（只解析，不做签名运算） |
| 隧道载荷加解密 | 字节串 + 会话 → 字节串 | 对称加解密，作用于内层消息载荷 |

**规范不规定曲线、摘要算法或密钥长度**：这些由平台提供，固件二进制内不可得（`OPEN-AUTH-5`）。

依据：`A14.4`、`A14.5`。

`R-6.6.4`（未定义 / OPEN）同一 `authType` 内部的**完整推进时序**（哪条先、何时推进）未证明；已证明的包括每条消息的应答关系（`R-6.6.7`）、`AuthSetup` 之后的分支（`R-6.6.6`）与失败回退阶梯（`R-6.6.9`）。实现须把时序做成可配置的状态机。

依据：`A14.7`、`OPEN-AUTH-1`。

`R-6.6.6`（MUST / CONFIRMED）`AuthSetup` 携带 `authType`，设备据此选择下一动作：

| `authType` | 设备发出 | 附带值 |
|---|---|---|
| `0` | `RequestAuthChallengeResponse`（`0x5115`） | 16 字节随机数 |
| `1` | `RequestAuthStart`（`0x5110`） | 16 位会话标识（非 `0`、非 `0xFFFF`） |
| `2` | `AuthStart`（`0x5111`，需标志位 3/4） | — |
| 其它 | 失败 | — |

随机数必须来自系统随机源；会话标识必须落在 `1 … 0xFFFE`。

依据：`A14.10`、`A14.11`。

`R-6.6.7`（MUST / CONFIRMED）**设备侧（本客户端）**的应答关系如下；不要照抄配件侧镜像：

| 收到 | 发出 | 说明 |
|---|---|---|
| `AuthSetup`（`0x5100`） | 按 `R-6.6.6`：`RequestAuthChallengeResponse`（`0x5115`）/ `RequestAuthStart`（`0x5110`）/ `AuthStart`（`0x5111`） | 由 `authType` 分支 |
| `AuthCert` | `RequestAuthCert`（`0x5112`）+ `AuthenticationSucceeded` | 设备侧验完证书 |
| `AuthChallengeResponse` | `RequestAuthCert`（`0x5112`） | 接收侧 ID 未完全闭合 |
| `AuthFinish` | `RequestAuthCert`（`0x5112`） | 接收侧 ID 未完全闭合 |
| `AuthSetupFailed`（`0x5100`） | 无出站消息，仅上报失败 | 与 `AuthSetup` 同 ID、不同状态 |

配件侧镜像（仅当实现角色反转为配件时使用）：

| 收到 | 发出 |
|---|---|
| `RequestAuthCert`（`0x5112`） | `AuthCert`（`0x5113`） |

依据：`A14.12`、`A14.7`。

`R-6.6.8`（MUST / CONFIRMED）认证超时**缺省 10 秒**（传输类型 `3`）；其它传输类型为 `0`（不超时），可由配置键 `MFi4AuthTimeoutValueS` 覆盖，负值按 `0` 处理。

依据：`A14.14`、`A14.15`。

`R-6.6.9`（MUST / CONFIRMED）认证失败后的重试是**认证类型回退**，不是同类型重传：

- 维护一个尝试位图（低位 4 位 + 高位 2 位，共 6 种）；
- 失败时把当前类型标记为已尝试；
- 仍有未尝试类型 → 重新发起 `RequestAuthSetup`；
- 全部尝试完 → 上报失败（状态 `1`）。

实现不得实现"同一类型重发 N 次"的机制。

依据：`A14.16`。

`R-6.6.10`（MUST / CONFIRMED）认证状态只有两个取值：`1` = 失败，`2` = 成功；`AuthenticationReset` 受配置键 `IgnoreAuthReset` 控制，置真时忽略。

依据：`A14.17`、`A14.18`。

`R-6.6.5`（SHOULD / INFERRED）**MFi4Auth** 的认证状态序列（推断，未经汇编证明，仅供实现参考；构造侧 ID 见 `R-6.6.2`，接收分派映射仍 OPEN）：

```
AuthSetup → AuthStart → RequestAuthCert / AuthCert → AuthChallengeResponse → AuthFinish
异常出口：AuthenticationReset / AuthenticationFailed
```

依据：`mfi4Auth_*` 符号名与 `A09.2` 的消息角色。`OPEN-AUTH-1`。

`R-6.7`（MUST / CONFIRMED）认证不改变链路状态；链路 FSM 无"认证中"状态。

依据：`A09.8`、`analysis/06`。

## 6.3 会话启动边界

`R-6.8`（MUST / CONFIRMED）会话启动消息唯一：

| `msg_id` | handler |
|---|---|
| `0x4301` | `0x10016d3ac` |

依据：`A10.3`（表 `0x10021e650`）。

`R-6.9`（MUST / CONFIRMED）"链路可用"的判定是 FSM 进入 `Connected`（状态 5）；在进入之前，链路层会丢弃找不到会话的数据。

依据：`A10.6`、`A10.1`。

`R-6.10`（MUST / CONFIRMED）外部配件协议识别消息唯一：`0xEA03` → `0x100154964`。

依据：`A10.3`、`A08` 表（`0x10021d268`）。

`R-6.11`（未定义 / OPEN）`0x4301` 的静态字段 schema 已在 control/spec/14 给出；本阶段仍未确认运行时平台必填性、错误/重试、所有 profile 的发起方，以及“会话已启动”是否有独立状态位。

依据：`A10.4`、`A10.7`。`OPEN-SES-2`、`OPEN-SES-3`。
