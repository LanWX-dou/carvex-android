# spec/09 — 客户端实现指南（把规范变成可运行程序）

本文件**不引入新的事实**，只给出"按本规范实现一个对端"的顺序、判定标准与字节模板。所有条款引用均指向 `spec/02`–`spec/07`；本文件不是规范本身，冲突时以那些文件为准。

## 9.0 角色与前提

本规范描述的是 **iPhone 侧（device 侧）** 的链路建立行为（目标二进制 `accessoryd`）。因此：

- 按本规范实现的是"**设备侧客户端**"：它等价于 iPhone 在 iAP2 链路层的角色，可与充当 accessory 的车机对话；
- 若要对端扮演 accessory，`R-5.*`（序号/确认）与 `R-3.*`（SYN）依然适用，但状态机的入口事件不同（`A06.9`），本文件不覆盖；
- **传输层不在本规范范围内**：如何在具体承载上打开一条双向字节流（`OPEN-TX-1`），由实现者提供。本规范只约定"字节流里应该出现什么"。

## 9.1 四层结构与规范映射

| 层 | 负责 | 依据 | 完成判定 |
|---|---|---|---|
| L1 帧编解码 | `FF 5A` 头、长度、校验、传统帧 | `spec/02` `R-2.1`–`R-2.12` | 向量 V1–V6 全部复算通过 |
| L2 链路控制 | SYN 协商、序号/ACK/重传、控制位 | `spec/03` `R-3.1`–`R-3.8`、`spec/04` `R-4.1`–`R-4.5` | SYN 可编码/解析；窗口与重传按协商值工作 |
| L3 状态机 | 8 状态、事件分派、非法事件无副作用 | `spec/05` `R-5.1`–`R-5.11` | 迁移表逐条实现；5 条惰性条目不迁移 |
| L4 识别 | 18 个参数 ID、6 类 transport component | `spec/06` `R-6.1`–`R-6.3.1` | 能构造并解析识别消息 |

认证（`spec/06` `R-6.5`–`R-6.7`）只覆盖已取证的消息/参数与状态边界，不等于完整验证实现；普通认证不是隧道封装。会话（`R-6.8`–`R-6.11`）只到边界。

## 9.2 里程碑

| 里程碑 | 内容 | 判定标准 | 阻塞项 |
|---|---|---|---|
| M1 | 帧编解码 | 能重算 V1–V6；能拒绝长度/校验不符的帧 | 无 |
| M2 | SYN 协商 | 能解析对端 SYN、生成自己的 SYN，并按协商值设置窗口/最大包/重传次数 | `OPEN-SYN-1`（`+0x04` 语义） |
| M3 | 序号与确认 | 能对收到的数据回 ACK；能按窗口判断"已确认/缺失"；能重传 | `OPEN-SEQ-*`（重传定时器细节） |
| M4 | 状态机 | 8 状态迁移与 `spec/05` 表一致；惰性条目不迁移 | `OPEN-FSM-3`（部分事件触发点） |
| M5 | 识别 | 能发 `0x1D00`（无参数）、收 `0x1D01`（解析参数组 0）、发 `0x1D02`（无参数）；能处理 `0x1D05`/`0x1D06`（可选更新/取消）；参数 ID/类型与 `R-6.3` 一致 | `OPEN-ID-2`（必需集合） |

> `0x1D01` 是车机→设备；设备出站 `0x1D01` 需认证+识别，早期发会被门控拦下（control `R-5.4`/`R-5.6`）。
| M6 | 认证 | **本规范不足以实现**（见 9.6） | `OPEN-AUTH-1`…`OPEN-AUTH-5` |

## 9.3 启动序列（device 侧）

前提：已有一条双向字节流（L1 可用）。下表只列**有证据支持**的动作；"期望收到"写的是触发条件，而不是对端必须照做的义务。

| 步 | 触发 | 我方动作 | 期望收到 | 依据 |
|---|---|---|---|---|
| 1 | 传输就绪 | 默认等对端 SYN；首字节超时可发 Detect，Detect 超时重连，不自动切换为主动 SYN | 校验通过的 SYN 或传统响应 | control `R-8.10`、本章 §9.10 |
| 2 | 收到并验证对端 SYN | 按协商结果回 SYNACK（样本 `ctrl=0xC0`），保留确认的会话条目 | 有效 ACK，确认号须与待确认 SYNACK 匹配；不以 ACK 位单独判成功 | `spec/03`、`spec/04`、control `R-7.15` |

> 23G90 两次连接均回 `0xC0`，未出现 `0x90`；默认按 `0xC0` 实现（control `C-4`）。`RST|SYN`（`0x90`）的**触发条件**未取证，登记为 `OPEN-SYN-7`，不再与 ACK 下限问题重号。
| 3 | 收到 ACK | 协商完成：窗口、最大包、重传次数以协商结果为准 | 对端数据帧或空 ACK | `spec/03`、`spec/04` |
| 4 | 超时未收到 ACK | 重发 SYNACK，最多 `MaxRetrans` 次；耗尽后进入 `Failed` | — | `spec/03` `R-3.7`、`spec/05` |
| 5 | 链路 `Connected` | 发送 **`0x1D00`**（StartIDPS，**无参数**；会话号放在帧头 `hdr[7]`） | **`0x1D01`**（车机自述其识别信息） | control `R-5.1`/`R-5.4`/`R-7.15` |
| 6 | 收到且通过适用 profile 校验的 `0x1D01` | 发送 **`0x1D02`**（接受对端识别结果） | 按版本门控推进，不把“收到”当作“接受” | control `R-5.4`/`R-7.15` |
| 7 | 识别完成 | **由 device 侧主动发起认证**：`0xAA00` → … → `0xAA05` | 车机回 `0xAA06` / `0xAA01` / `0xAA03` | control `R-7.15`；参数格式见本规范 `R-6.6`、`R-6.6.1` |
| 8 | 验链/验签失败或所需认证 profile 未实现 | 不发送认证成功；报告原因并安全停止 | — | 见 9.6；配件认证不要求客户端持有配件私钥 |

**后续阶段修订（原表第 5/6 步有误）**：原写"device 发送 `0x1D01`"，与 control 阶段 `R-7.15`/`R-5.1`/`R-5.4` 冲突。正确方向是 device 先发 `0x1D00`、收 `0x1D01`、再发 `0x1D02`。

注意：`0x1D01` 是**入站无条件、出站有门控**——device 主动发 `0x1D01` 需要先通过认证与识别，客户端在早期阶段发它会被门控拦下。`0x1D00`/`0x1D02` 与 `0xAA00`–`0xAA05` 的编号与方向来自 control docset，本 docset 未单独取证（`OPEN-MSG-4`）。

## 9.4 帧模板（示例字节由参考实现算出）

iAP2 帧（`R-2.1`–`R-2.9`）：

```
FF 5A | len_hi len_lo (整帧长度) | ctrl | seq | lt | extra | hdr_cksum | payload | payload_cksum
```

| 帧 | 字节 |
|---|---|
| SYN（8 位，默认参数；无会话条目，仅编码向量） | `ff5a001480000000130101ffff03e8000a1e00ed` |
| RST（8 位，无载荷） | `ff5a0009100000008e` |
| RST\|SYN（8 位，仅编码向量，不表示触发条件已确认） | `ff5a001490000000030101ffff03e8000a1e00ed` |
| ACK（8 位，`seq=1, ack=0`，无载荷） | `ff5a0009400100005d` |

默认 SYN 载荷 `0101ffff03e8000a1e00` 的字段顺序见 `R-3.1`：version=`1`、MOP=`1`、max_packet=`0xFFFF`、ack_timeout=`1000`、cumack_timeout=`10`、max_retrans=`30`、max_cumack=`0`。**这些是报价，不是协议常量**：实现必须接受对端协商回来的值（`R-3.4`）。

传统帧（`R-2.10`、`R-2.11`）：

| 帧 | 字节 |
|---|---|
| Detect | `FF 55 02 00 EE 10` |
| DetectNACK | `FF 55 04 00 02 04 EE 08` |
| RequestIdentify | `FF 55 02 00 FE 00` |

传统帧的校验范围**不含** `FF 55`；iAP2 帧的头部校验**包含** `FF 5A` —— 这是最容易写错的一处。

## 9.4a 帧长与 RFCOMM 写块

`R-9.2`（MUST / CONFIRMED）iAP2 帧的 `max_packet` 默认 `0xFFFF`（`R-3.2`），与 RFCOMM 信息字段 N1、平台 API 写入限制不是同一个上限。`min(N1,2570)=1007` 仅对应参考 iOS 内部队列与该 N1 配置，不是所有平台的 socket 契约（bluetooth `R-9.14`）。

- 发送：按实际平台 API 串行写并处理部分写；如复刻内部队列可选上述保守块长，不得硬编码为所有平台上限。
- 接收：按 iAP2 长度字段重组；不得把一次 `read()` 当一帧。
- 协商后的 `max_packet` 若小于帧长，按 `R-3.4` 以协商值为准。

（同一条契约的传输侧表述见 `spec/01` `R-1.17`。）

## 9.5 识别阶段接收与校验

仿 iPhone 端发送的是无参数 `0x1D00`，接收车机 `0x1D01`。以下是目标解析路径的已取证行为，不是客户端要发送的自述清单，也不能仅凭 ID 上限决定接受：

- ID 上限 `0x22`，超出即整条消息被判拒绝；
- `0x13` 被显式拒绝；
- `0x08`–`0x0b`、`0x12`、`0x14`–`0x17`、`0x19`、`0x1b`–`0x21` 一律拒绝；
- 字符串类 ID：`0x00`–`0x05`、`0x0c`、`0x0d`（集合）、`0x22`；
- 数据类 ID：`0x06`/`0x07`（消息集合）、transport component `0x0e`–`0x11`、`0x18`、`0x1a`；
- transport component 内部子参数：`0` = U16 标识、`1` = 名称字符串、`2` = 存在性标志（空数据）。

**最小可接受集合**没有完整取证（`OPEN-ID-2`）；不能建议设备侧发送名称、型号和 component 来替代 `0x1D00`。23G90 样本含目标路径表中被标拒绝的 ID，跨版本/完整特性分派的接受规则仍需复核。识别拒绝消息 schema 未闭合时应本地报错，不猜造载荷或无条件发接受。

## 9.6 认证：本规范的边界

已确认（`R-6.5`–`R-6.7`、`analysis/09`、`analysis/14`）：

- **认证消息的参数就在消息自身的参数组 0（裸参数）**，与 23G90 抓包一致。已按消息与方向复核：入站 `0xAA01`/`0xAA03`/`0xAA06` 由 handler 直接读参数组 0（`0x1001850bc` 等），出站 `0xAA11`/`0xAA13` 由 `iAP2MsgInit` + `iAP2MsgAddDataParam` 构造（`0x10002e5b4`、`0x10002e730`）——见 `R-6.6`。
- `0x5500/0x5501` 是**中继路径专用**封装（唯一构造者 `0x100022264`，唯一调用者 `0x100084ef4`），**不是**认证消息的封装，不得套在 `0xAA01/0xAA03` 上（`A09.11`）。
- 车机侧认证消息的参数 ID/类型（`0xAA01` / `0xAA03` / `0xAA06`，见 `R-6.6`、`R-6.6.1`）；
- device 侧认证结果状态（`0xAA10`→失败、`0xAA12` 挑战、`0xAA14`/`0xAA15` 状态）；
- 认证不改变链路状态（`R-6.7`）。

**认证由 device 侧主动发起**：`0xAA00` → … → `0xAA05`，车机以 `0xAA06` / `0xAA01` / `0xAA03` 应答（序列来自 control 阶段 `R-7.15`，本 docset 未单独取证，登记 `OPEN-MSG-4`）。

**配件认证与设备自身认证必须分开**：`0xAA00`–`0xAA06` 的样本路径由车机提供证书/签名，客户端验证；不能把客户端持有配件私钥设为此路径的前提。客户端需要可信验证材料、正确的密码学处理和完整状态机。`0xAA10`–`0xAA15` 是另一条设备认证路径，其合法凭证要求和端到端兼容性尚未闭合。持有某种 MFi 凭证本身也不能证明可以完整实现两条路径。

不能验证证书或挑战响应时，不得发送认证成功；记录明确的验证失败原因并停止该认证。样本验签方法与局限见 control `spec/11`，不是跳过认证。

| ID | 内容 |
|---|---|
| `OPEN-MSG-4` | `0x1D00`/`0x1D02`、`0xAA00`–`0xAA05` 的编号与方向来自 control docset，本 docset 未单独取证 |
| `OPEN-AUTH-1` | 同一 `authType` 内部的推进时序 |
| `OPEN-AUTH-5` | 证书链/签名算法参数（由平台提供） |
| `OPEN-SYN-7` | `RST|SYN`（`0x90`）的触发条件未取证；样本默认回 `0xC0` |

## 9.7 常见实现错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 传统帧校验把 `FF 55` 算进去 | 校验值差 `0xAA`，对端丢弃 | `R-2.10`：从长度字节开始算 |
| iAP2 头部校验不含 `FF 5A` | 头部校验错 | `R-2.9`：含同步字节 |
| 长度字段写成"载荷长度" | 解析错位 | `R-2.2`：整帧长度，含两个校验 |
| SYN 字段字节序写反 | 协商值错乱 | `R-3.1`：多字节字段一律大端 |
| 把窗口默认当 1 就只发 1 帧 | 吞吐极低但正确 | `R-4.4`：以协商值为准 |
| 用 `seq` 直接比较大小判断新旧 | 回绕时误判 | `R-4.2`：按 8 位模差 |
| 忽略惰性条目 | 在 `Idle` 收到 `0x05` 时错误迁移 | `R-5.7`：5 条惰性条目不迁移 |

## 9.9 本规范不能提供的东西

| 缺什么 | 影响 | 去向 |
|---|---|---|
| 传输打开流程（RFCOMM/USB/其它） | 无法发出第一个字节 | `OPEN-TX-1`，需按平台实现 |
| 认证验证材料与未闭合的认证 profile | 无法声称完整认证互通 | 配件认证需可信验证材料；设备自身认证需另行确认合法凭证。样本验签见 control `spec/11`（`OPEN-AUTH-5`） |
| 识别必需参数集合 | 可能被车机拒绝 | `OPEN-ID-2`，按对端反馈补 |
| 会话层（控制会话、业务消息） | 无法发起 CarPlay 会话 | 后续阶段（`research/protocol/iap2_control_session/`） |
| 重传/超时定时器的精确参数 | 行为可能与 iPhone 不同但可互通 | `OPEN-TMR-*`、`OPEN-SEQ-*` |


## 9.10 定时器与重试默认值

`R-9.1`（SHOULD / INFERRED）实现应按下表取初值；标"实现选择"的项没有固件证据，可按平台调整，但不得低于对端可接受范围。

| 项 | 默认值 | 状态 | 依据 |
|---|---|---|---|
| SYN 载荷：`max_packet` | `0xFFFF` | CONFIRMED | `R-3.2`、`A15.4` |
| SYN 载荷：`ack_timeout` | `0x03E8`（1000） | CONFIRMED（值）/ INFERRED（单位按毫秒） | `R-3.2`、`A03.5` |
| SYN 载荷：`cumack_timeout` | `0x000A`（10） | 同上 | `R-3.2` |
| SYN 载荷：`MaxRetrans` | `0x1E`（30） | CONFIRMED | `R-3.2` |
| SYN 重发间隔／上限 | 等同 `ack_timeout`，最多 `MaxRetrans` 次 | INFERRED | `R-3.7` |
| ACK 超时后重传 | 按 `ack_timeout` 重传未确认帧 | INFERRED | `R-4.x` |
| 累积 ACK 超时 | 按 `cumack_timeout` 触发一次性确认 | INFERRED | `R-4.x` |
| `Detect` 等待对端 SYN（`T_detect`） | **5 s**；**超时即 `NO_SYN`，走重连流程**（与 control `§8.8` 一致）。`T_detect` 内**不得**翻成主动发 SYN | 项目建议 | control `§8.8` |
| 主动发 SYN | 非默认实验路径；只有明确实现并验证该 profile 才能启用，不能只靠配置开关补齐状态机 | 未验证 | 本章 §9.3 的证据边界 |
| 认证会话超时 | **10 s** | CONFIRMED | `A14.14`、`R-6.6.8` |

依据：`A03.5`、`A14.14`、`A15.4`；"实现选择"项无固件证据，不登记为结论。
