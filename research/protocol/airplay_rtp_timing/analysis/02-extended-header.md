# 02 — 扩展头（元素区）

> 覆盖要求第 2 项。地址均属 `AirPlaySender`。本文只写指令能直接证明的位级布局；语义猜测一律标 `OPEN`。

## 2.1 结论摘要

| 编号 | 结论 | 强度 |
|---|---|---|
| `A02.1` | 元素区从 `pkt+12` 开始；固定 4 字节 indexed helper 使用 `pkt + 12 + 4i`，但通用扫描按元素实际 1/4 字节推进 | `CONFIRMED（路径限定）` |
| `A02.2` | 元素两态：首字节最高位 = 0 → 元素占 **1 字节**；= 1 → 元素占 **4 字节** | `CONFIRMED` |
| `A02.3` | 4 字节元素的位布局（大端）：`[31]=1`，`[30:24]` 7 位标记，`[23:10]` 14 位差值，`[9:0]` 10 位长度 | `CONFIRMED` |
| `A02.4` | 解包结果按另一个次序排列：`len<<22 | delta<<8 | (byte)` | `CONFIRMED` |
| `A02.5` | 14 位差值的用途：子包时间戳 = 包头时间戳 − 差值 | `CONFIRMED` |
| `A02.6` | 只有特定 payload type 才解析元素区：`{0x61,0x68,0x69,0x6c,0x6d}`，另加 `0x60` 且合并数>1 | `CONFIRMED` |
| `A02.7` | 取包路径存在第二套 payload type 掩码，其分支语义仍待核，不能据此推出交错布局 | `OPEN-RTP-4` |
| `A02.8` | Compose字段来源已核；跨profile消费语义和上游长度上限保证待核 | `OPEN-RTP-5` |
| `A02.9` | 内部前置2B已由消息M复制到I+2解释；网络适配/连续性仍缺 | `OPEN-RTP-8` |

## 2.2 元素两态与步进

`APSRTPPacketHandlerReadExtendedHeader`（`0x251ace454`）是唯一的元素解包原语：

```asm
0x251ace454: ldrsb w9, [x0]          ; 元素首字节（符号扩展）
0x251ace458: and   w8, w9, #0xff
0x251ace45c: str   w8, [x1]          ; 出参 = 该字节（低 8 位）
0x251ace460: tbz   w9, #0x1f, #0x251ace480   ; bit7 == 0 → 只占 1 字节
0x251ace464: ldr   w9, [x0]          ; 否则按 32 位读整个元素
0x251ace468: rev   w9, w9            ; 大端 → 主机序
...
0x251ace480: cbz   x2, #0x251ace498
0x251ace484: tst   w8, #0x80         ; 用解出的字节再判一次
0x251ace488: mov   w8, #4
0x251ace48c: csinc x8, x8, xzr, ne   ; ne（bit7=1）→ 4；否则 0+1 = 1
0x251ace490: add   x9, x0, x8
0x251ace494: str   x9, [x2]          ; 出参 = 下一个元素地址
```

结论：**元素是变长的（1 或 4 字节），由首字节 bit7 区分**（`A02.2`）。这解释了为什么"元素区长度 = 4×元素个数"只在 4 字节形态下成立。

## 2.3 4 字节元素的位布局

解包（`0x251ace4f0`–`0x251ace52c`）：

```asm
0x251ace4f0: ubfiz x8, x1, #2, #0x20      ; x8 = 4 × index
0x251ace4f4: ldrsb w10, [x9, x8]          ; 首字节
0x251ace4fc: str   w8, [x2]               ; 先写出"首字节"
0x251ace500: tbnz  w10, #0x1f, #0x251ace508   ; bit7=1 才继续
0x251ace508: mov   w10, w1
0x251ace50c: add   x9, x9, x10, lsl #2
0x251ace510: ldr   w9, [x9]               ; 读 4 字节
0x251ace514: rev   w9, w9                 ; 大端 → 主机序（记作 W）
0x251ace518: lsr   w10, w9, #2
0x251ace51c: and   w10, w10, #0x3fff00    ; 取 W[21:8] = 原 W[23:10]
0x251ace520: orr   w9, w10, w9, lsl #22   ; 再并入 W[9:0] → 位 31..22
0x251ace524: orr   w8, w9, w8             ; 并入首字节
0x251ace528: str   w8, [x2]
```

即解包输出 = `(W[9:0] << 22) | (W[23:10] << 8) | (W[31:24])`（`A02.4`）。

打包（`APSRTPPacketHandlerComposeRTPPacketWithBBuf`，`0x2519c3728`–`0x2519c374c`）：

```asm
0x2519c3728: ldr   w8, [x27]              ; 描述符第一个 32 位字
0x2519c372c: ldp   w10, w9, [sp, #0x38]   ; 两个 32 位：起始/结束时间戳
0x2519c3730: sub   w9, w9, w10
0x2519c3734: ubfiz w9, w9, #0xa, #0xe     ; 取低 14 位 → 位 10..23
0x2519c3738: ldur  x2, [x29, #-0x58]      ; 该子包数据长度
0x2519c373c: orr   w8, w9, w8, lsl #24    ; 低 7 位放到位 24..31
0x2519c3740: bfxil w8, w2, #0, #0xa       ; 低 10 位放到位 0..9（长度）
0x2519c3744: orr   w8, w8, #0x80000000    ; 置 bit31
0x2519c3748: rev   w8, w8                 ; 主机序 → 大端
0x2519c374c: str   w8, [x28], #4          ; 写出并前移 4 字节
```

于是 4 字节元素的线上字节（大端）为（`A02.3`，`W` 为打包前的值）：

```text
W       = 0x80000000 | (B7 << 24) | (D14 << 10) | L10
byte[0] = 0x80 | B7
byte[1] = D14 >> 6
byte[2] = ((D14 & 0x3F) << 2) | (L10 >> 8)
byte[3] = L10 & 0xFF
```

自检向量（供 `reference-impl` 与 `verify.py` 重算）：`B7=0x05, D14=0x2ABC, L10=0x155`
→ `W = 0x85AAF155` → 线上字节 `85 AA F1 55`；
解包该 4 字节应还原出 `L=0x155`、`D=0x2ABC`、`byte=0x85`。

## 2.4 差值的用途

`APSRTPPacketHandlerGetNextPacket`（`0x2519c1728`–`0x2519c1750`）把解包出的 14 位字段从包头时间戳里减掉：

```text
sub_packet_ts = packet_ts − D14          （最后一个子包不减，见 analysis/01 §1.9）
```

因此 `D14` 是"相对包头时间戳的回退量"，单位与 RTP 时间戳相同（`A02.5`）。具体单位（采样 tick 还是毫秒）本阶段无证据 → 与 `OPEN-CLK-3` 合并处理。

## 2.5 何时解析元素区（payload type 门）

`APSRTPPacketHandlerReadNewMessage`（`0x2519c0c90`）在搬入数据后立即判断：

```asm
0x2519c0d84: mov  w11, #0x3302       ; 允许集合的位图
...
0x2519c0d94: add  x8, x8, #0xc       ; 元素区起点 = 包基址 + 12
```

位图 `0x3302` 的置位为 bit 1、8、9、12、13，配合 `PT − 0x60` 的下标，得到允许集合：

```text
PT ∈ {0x61, 0x68, 0x69, 0x6c, 0x6d}
或  PT == 0x60 且 合并数(obj+0x1c) > 1
```

这 5 个值正好是 `analysis/03` 里"带扩展变体"的 payload type（`A02.6`、`A03.4`）。

## 2.6 未决

| 编号 | 未决点 | 现有证据 |
|---|---|---|
| `OPEN-RTP-4` | 取包路径还有第二套掩码（`0x2519c15dc`–`0x2519c1614`，`w24`/`w25` 两个位图，以及 `lsl w10,w8,#2; sub w10,w10,#3` 的指针前移），不能仅据此推出两种线序 | 掩码常量与指针算术已读取，但两类的具体线序未闭合 |
| `OPEN-RTP-5` | B7/L10在其他profile的消费语义及长度≤1023的上游保证 | Compose中B7取输入包装对象PT相关首字段低7位，L10取所复制音频数据长度低10位、不含元素自身；跨profile语义与长度上限保证未证（analysis/07） |
| `OPEN-RTP-8` | 网络输入到10B头音频消息M的映射及多段连续性保证 | 内部M复制到I+2已解释序号I+2/数据I+12，不再是内部指令冲突（analysis/11） |

## 2.7 元素列表的终结条件（`A02.10`）与缓冲读法的自洽性（`A02.11`）

扫描循环（`0x2519c0d90`–`0x2519c0dc0`）：

```asm
0x2519c0d94: add  x8, x8, #0xc          ; 首个元素 = 包基址 + 12
0x2519c0d9c: ldr  x0, [sp, #0x20]       ; 当前元素指针
0x2519c0da0: add  x1, sp, #0x2c         ; 出参：解出的元素值
0x2519c0da4: add  x2, sp, #0x20         ; 出参：下一个元素指针
0x2519c0da8: bl   #0x251ace454          ; APSRTPPacketHandlerReadExtendedHeader
0x2519c0dac: ldrb w8, [sp, #0x2c]
0x2519c0db0: tbz  w8, #7, #0x2519c0df0  ; bit7 == 0 → 结束扫描
0x2519c0db4: add  w21, w21, #1
0x2519c0db8: ldr  w8, [x19, #0x1c]      ; 最大子包数
0x2519c0dbc: cmp  w21, w8
0x2519c0dc0: b.ls #0x2519c0d9c          ; 未超上限则继续
```

两条实现要点：

1. **列表自终结**：只要遇到 1 字节元素（bit7=0）就停止，后面的字节全是载荷，不需要额外长度字段（`A02.10`）；
2. **上限兜底**：最多扫 `obj+0x1c` 个元素，超出走错误日志路径（`0x2519c0dc4` 起的 `gLogCategory` 比较）。

后续analysis/11补证（`A02.11`）：M+0为序号、M+10为数据；M复制到I+2后序号I+2、数据I+12恰好一致，结束坐标为消息总长T+2。旧“buf就是线上包”的唯一读法推断已撤回。`OPEN-RTP-8`只保留网络适配及多段消息前提，不再把内部偏移称为矛盾。
