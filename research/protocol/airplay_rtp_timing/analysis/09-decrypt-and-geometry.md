# 09 — 解密步骤与包几何（`OPEN-RTP-4` / `OPEN-RTP-8` 的关键突破）

> 起因：用 `firmware/tools/scan-offsets-rtp.py` 扫"谁读写 `+0x5c0`"，命中 `_APSRTPPacketHandlerDecryptCurrentMessage`。
> 该函数给出两条解密范围的算术分支；`+0x5c0` 与线上长度的对应仍需调用者证据。

---

## 9.1 结论摘要

| 编号 | 结论 | 强度 |
|---|---|---|
| `A09.1` | 存在解密步骤 `_APSRTPPacketHandlerDecryptCurrentMessage`（`0x2519c0934`），仅当 `obj+0x18` 的 **bit1** 置位时执行 | `CONFIRMED` |
| `A09.2` | 解密前按**同一 PT 门**（掩码 `0x3302`）把包分成两类几何 | `CONFIRMED` |
| `A09.3` | **带元素分支**：载荷指针 = `buf + 12 + (4C−3)`，载荷长度 = `[buf+0x5c0] − (4C−3) − 12`，其中 `C = [obj+0x678]` | `CONFIRMED（指令算术）` |
| `A09.4` | **连续类**：载荷指针 = `buf + 0xc`，载荷长度 = `[buf+0x5c0] − 0xc` | `CONFIRMED` |
| `A09.5` | 在**解密读路径**中，`buf+0x5c0` 被当作结束坐标参与载荷长度相减；它与提交写路径的统一语义仍未闭合 | `CONFIRMED（读路径）/ OPEN（统一语义）` |
| `A09.6` | 本函数在调用 cryptor 前读取内部 PT 并只处理选定载荷区间；不能由此断言所有传输头明文或所有媒体必加密 | `INFERRED（本路径）` |
| `A09.7` | 正常终止C=n+1、4C−3=4n+1已由A11.4闭合 | `CLOSED（原OPEN-RTP-14）` |
| `A09.8` | 消息M复制到I+2，L=T+2故L−12=T−10；网络适配仍缺 | `OPEN-RTP-8`（收窄但未关闭） |

## 9.2 解密入口（`A09.1`）

```asm
0x2519c0934: pacibsp
0x2519c0958: ldrb w8, [x0, #0x18]
0x2519c095c: tbz  w8, #1, #0x2519c0ac0   ; bit1 未置位 → cold 调用后返回 -0x1a4f
0x2519c0964: ldr  x0, [x0, #0xa0]        ; 当前输入对象，不能与第二入参 cryptor 混为一谈
0x2519c0968: cbz  x0, #0x2519c0acc       ; 无对象 → cold 调用后返回 0，不解密
0x2519c096c: ldr  x8, [x19, #0xa8]       ; 包缓冲
0x2519c0978: ldrb w9, [x8, #1]           ; PT
0x2519c097c: and  w9, w9, #0x7f
0x2519c0980: sub  w9, w9, #0x60
0x2519c0984: cmp  w9, #0xd
0x2519c0988: b.hi #0x2519c09d0
0x2519c0994: mov  w11, #0x3302
0x2519c0998: tst  w10, w11
0x2519c099c: b.eq #0x2519c09c0
```

指令只读取 `obj+0x18` 的 bit1，并在该位清零时跳过解密；因此本函数能确认的是**bit1 控制接收/解密路径**。bit0 的装配语义没有由本函数直接证明，不能从这条 `tbz` 指令外推整个字节的模式定义。

## 9.3 两类几何（`A09.2`–`A09.5`）

带元素分支（`0x2519c09a0`–`0x2519c09b8`）：

```asm
0x2519c09a0: ldr  w9, [x19, #0x678]      ; C
0x2519c09a4: lsl  w9, w9, #2             ; 4C
0x2519c09a8: sub  w9, w9, #3             ; 4C−3
0x2519c09ac: add  x10, x8, x9
0x2519c09b0: add  x22, x10, #0xc         ; 载荷指针 = buf + 12 + (4C−3)
0x2519c09b4: ldr  x8, [x8, #0x5c0]       ; 总长
0x2519c09b8: sub  x8, x8, x9             ; 中间值 = L − (4C−3)，还不是调用长度
0x2519c09bc: b    #0x2519c09d8           ; 必须继续走共用减 12
0x2519c09d8: sub  x21, x8, #0xc          ; 最终长度 = L − (4C−3) − 12
```

连续类（`0x2519c09d0`–`0x2519c09d8`）：

```asm
0x2519c09d0: add  x22, x8, #0xc          ; 载荷指针 = buf + 12
0x2519c09d4: ldr  x8, [x8, #0x5c0]
0x2519c09d8: sub  x21, x8, #0xc          ; 载荷长度 = 总长 − 12
```

两个可直接用于实现的结论：

1. 解密读路径把 `+0x5c0` 按“结束坐标”参与相减；提交写路径在同一偏移写入调用者长度。消息M到内部I+2已由analysis/11解释；网络适配仍为`OPEN-RTP-8`，不能把读侧解释扩展成通用线规；
2. 命中 `0x3302`，或 PT 为 `0x60` 且 `obj+0x1c >= 2`（`0x2519c09c0`–`0x2519c09cc`）时，用带元素分支；否则直接从 `buf+12` 起。两条路径都在 `0x2519c09d8` 减 12，`x21` 在 `0x2519c0a54` 作为解密长度实参。设 `L=[buf+0x5c0]`，两条路径的区间结束地址均为 `buf+L`。这不证明“交错”线序，也不关闭 `OPEN-RTP-10`。

## 9.4 加密结论（`A09.6`）

`_APSRTPPacketHandlerDecryptCurrentMessage` 的存在与调用形状说明：

- 头部（12 字节）在解密前已被解析（否则无法按 PT 选几何）；
- 解密只作用于"载荷区间"，即 `[载荷指针, 载荷指针+载荷长度)`；
- 只能说明本调用点的内部头已可读、选定区间交给 cryptor；之前是否存在外层解密、其它 profile 是否启用加密不能由此决定。音频AAD入口M[2:10]共8B已由analysis/11补证；具体provider、密钥和网络格式仍缺。

cryptor 来自第二入参（`x1 → x20`，`0x2519c0974`），后续 `0x2519c09f0..0x2519c0a60` 查询其接口并调用。`obj+0xa0` 是此前保存的输入对象，不应标成同一个“解密上下文”。

## 9.5 仍未闭合

| 编号 | 未决点 | 关闭条件 |
|---|---|---|
| `CLOSED（原OPEN-RTP-14）` | 正常终止计数C=n+1，4C−3=4n+1；该历史疑问已关闭 | 写入点与有限计数解释见analysis/11 §11.5及C14 |
| `OPEN-RTP-8` | 内部消息10B头到I+2映射已解释；网络输入/多段消息仍缺 | 核网络适配到消息M的映射、连续性和完整性门 |
| `OPEN-RTP-1` | 内部音频数据基址B与最终网络包坐标的映射 | 仍需 `OPEN-RTP-10` |
