# 03 — payload type 与流类型

> 覆盖要求第 3、6 项。两个函数：`_carAudioStream_getRTPPayloadType`（`0x2519c1d5c`，四字符码 → PT）与 `APSRTPPacketHandlerComposeRTPPacketWithBBuf`（`0x2519c348c`，PT 改写）。

---

## 3.1 结论摘要

| 编号 | 结论 | 强度 |
|---|---|---|
| `A03.1` | 存在"流类型四字符码 → RTP payload type"的硬编码表，8 个条目、无协商 | `CONFIRMED` |
| `A03.2` | 未识别的四字符码会记一条错误日志，并**返回入参本身**（`0x6d61696e`），不是返回 100 | `CONFIRMED` |
| `A03.3` | 多包合并装配时 PT 被改写：`0x60→0x61`、`0x64→0x68`、`0x65→0x69`、`0x6a→0x6c`，其余不变 | `CONFIRMED` |
| `A03.4` | 接收侧"是否带扩展元素"的判定集合 = `{0x61,0x68,0x69,0x6c,0x6d}`，即装配路径可能输出的全部 PT | `CONFIRMED` |
| `A03.5` | 四字符码到编解码器的对应、以及 PT 是否在控制面协商 | `OPEN-RTP-6` |
| `A03.6` | `0x6b`、`0x6d` 在装配路径没有改写规则，是否为"已是 buffered 形态" | `OPEN-RTP-7` |

## 3.2 四字符码 → payload type（`A03.1`）

`_carAudioStream_getRTPPayloadType`（`0x2519c1d5c`）以二分比较把 32 位四字符码映射到 8 位 PT：

| 四字符码 | 数值 | 返回 PT | 返回指令地址 |
|---|---|---|---|
| `'main'` | `0x6d61696e` | `0x64` (100) | `0x2519c1e48` |
| `'alt '` | `0x616c7420` | `0x65` (101) | `0x2519c1e40` |
| `'ared'` | `0x61726564` | `0x69` (105) | `0x2519c1db0` |
| `'mred'` | `0x6d726564` | `0x68` (104) | `0x2519c1de8` |
| `'auxo'` | `0x6175786f` | `0x6a` (106) | `0x2519c1e50` |
| `'oovc'` | `0x6f6f7663` | `0x6b` (107) | `0x2519c1e58` |
| `'axrd'` | `0x61787264` | `0x6c` (108) | `0x2519c1e10` |
| `'ovrd'` | `0x6f767264` | `0x6d` (109) | `0x2519c1e38` |

四字符码以 `mov w8, #0x696d` 之类的 16 位立即数拼出（`0x2519c1d70` 起），无表、无查表内存 ⇒ **硬编码，不存在运行期协商表**（`A03.1`）。

未命中时：

```asm
0x2519c1e60: mov  w20, #0x696e     ; 末尾拼回 'main'
...                                  ; 先按 gLogCategory 记一条错误
0x2519c1e6c: mov  x0, x20           ; 返回值 = 0x6d61696e
```

即**返回的是四字符码本身**（`0x6d61696e` = 1,835,365,486），不是 100（`A03.2`）。这一点对实现很关键：把"错误返回值"当 PT 会得到荒谬的 8 位截断值 `0x6e`。

## 3.3 多包合并时的 PT 改写（`A03.3`）

`APSRTPPacketHandlerComposeRTPPacketWithBBuf` 在 `obj+0x1c ≥ 2`（合并模式）下，写 PT 前先改写：

```asm
0x2519c3568: cmp  w8, #0x60      ; 0x60 → 0x61
0x2519c356c: b.eq #0x2519c35a4   ;   (0x2519c35a4: mov w8,#0x61)
0x2519c3570: cmp  w8, #0x64      ; 0x64 → 0x68
0x2519c3578: mov  w8, #0x68
0x2519c358c: cmp  w8, #0x65      ; 0x65 → 0x69
0x2519c35ac: mov  w8, #0x69
0x2519c3594: cmp  w8, #0x6a      ; 0x6a → 0x6c
0x2519c359c: mov  w8, #0x6c
```

| 输入 PT | 线上 PT |
|---|---|
| `0x60` | `0x61` |
| `0x64` | `0x68` |
| `0x65` | `0x69` |
| `0x6a` | `0x6c` |
| 其它 | 原值 |

而单包模式（`obj+0x1c < 2`）**改写分支完全被跳过**（`0x2519c3550` 的 `b.lo` 直接跳到 `0x2519c37f8`）⇒ 单包模式沿用输入 PT。

## 3.4 门集合与装配集合一致（`A03.4`）

| 侧 | 集合 |
|---|---|
| 装配可输出（合并模式） | `{0x61, 0x68, 0x69, 0x6c}` + 未改写的 `{0x6b, 0x6d, …}` |
| 接收解析扩展元素 | `{0x61, 0x68, 0x69, 0x6c, 0x6d}`，另加 `0x60` 且合并数>1 |

两个集合在 `{0x61,0x68,0x69,0x6c,0x6d}` 上重合，说明"带扩展元素"这件事由 **PT 取值**唯一决定，不需要额外标志位（`A03.4`）。这是本阶段对客户端最有直接用处的结论之一：**看到 PT∈该集合就必须按 `analysis/02` 解析元素区，否则元素区不存在**。

## 3.5 未决

| 编号 | 未决点 | 说明 |
|---|---|---|
| `OPEN-RTP-6` | 四字符码 ↔ 编解码器的对应（`main` 是否 AAC、`alt ` 是否 ALAC 等）；PT 是否在控制面（RTSP SETUP）协商、能否被车机改写 | 本阶段无控制面证据；`A03.1` 只证明**本机构建内**是硬编码表 |
| `OPEN-RTP-7` | `0x6b`/`0x6d` 在装配路径无改写规则：它们是"已经是 buffered 形态"还是"不支持合并" | 需读 `obj+0x1c` 的赋值者与两条队列的消费点 |
| `OPEN-RTP-9` | 实际会话里出现的 PT 组合（哪些流同时存在） | 需真实媒体抓包（`OPEN-RUN-1`） |
