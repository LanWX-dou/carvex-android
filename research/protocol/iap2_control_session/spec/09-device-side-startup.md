# spec/09 — 设备侧启动序列（正式章节）

本章把 `08` 里作为"实测骨架"给出的序列提升为**正式实现章节**：每一步写清方向、前置条件、期望响应与失败分支。

## 8.1 本章的证据标注约定

`R-8.1`（MUST / CONFIRMED）本章每条事实都必须带下列标注之一，实现方与评审方据此判断可信度：

| 标注 | 含义 | 来源 |
|---|---|---|
| `[24A446]` | 目标镜像的指令级证据，可用地址复查 | `analysis/` 各篇、`A` 结论编号 |
| `[23G90]` | 真实连接的观测（构建 23G90，车机 CFMOTO，蓝牙经典）| `runtime/23G90-bt-classic-2026-10-16.md` |
| `[建议]` | 本规范给出的实现策略，**不是**对端行为的断言 | 仅用于失败分支与超时 |

**禁止**把 `[23G90]` 的观测写成 `[24A446]` 的事实；也禁止把 `[建议]` 写成协议要求。

依据：`A00.1`、`A05.9`、`A05.10`。

## 8.2 角色与首帧

`R-8.2`（MUST / CONFIRMED）角色关系固定：**客户端 = 设备侧**（模拟 iPhone），**车机 = 配件侧**。由此决定三件事：

1. 链路由**车机发起**：车机发 SYN（`ctrl=0x80`），客户端回 SYNACK（`ctrl=0xc0`）`[23G90]`；观测中始终如此，客户端**默认不主动发 SYN**（能否主动发起未取证，见 `R-8.3` 步 2 的失败分支）。
2. 会话号必须与 SYN/SYNACK 确认的条目一致：样本中车机先提议 `02 00 02` 或 `03 00 02`，客户端沿用；随后 `hdr[7]` 为 2 或 3 `[23G90]`。不能由“iPhone 先发业务消息”推导其任意选号。
3. 识别由**客户端**发起（`0x1d00`），车机回识别信息（`0x1d01`），客户端再回接受（`0x1d02`）`[23G90]`。

这三条曾与 `link/spec/09` §9.3 的旧方向描述冲突（C-1）；link 已在 §9.3 按 `0x1D00 → 0x1D01 → 0x1D02` 修订，当前两处一致，历史处置见 `13-cross-docset-conflicts.md`。

依据：`A05.9`、`A02.13`。

## 8.3 启动序列总表

`R-8.3`（MUST / CONFIRMED）下表就是"能连上"的判定序列。`前置`= 执行该步必须已成立的条件；`期望`= 对端的正常响应；`失败分支`= 客户端自己的处置（`[建议]`，因为对端行为未取证）。

| 步 | 方向 | 前置 | 动作 | 期望 | 失败分支 `[建议]` |
|---|---|---|---|---|---|
| 1 | 车机 → 设备 | 传输通道已建立（RFCOMM 已连接、字节流双向可读）| — | 收到 `ctrl=0xee` 的链路握手帧 | `T_first_byte` = 2 s 内无帧：主动发 Detect（`FF 55 02 00 EE 10`，见 `link/spec/09` §9.4）|
| 2 | 车机 → 设备 | — | — | 收到 SYN（`ctrl & 0x80`）| `T_detect` = 5 s 仍无 SYN → 记 `NO_SYN`，重连 RFCOMM（`T_link` 只作 30 s 总上限，见 §8.8）|
| 3 | 设备 → 车机 | 收到并校验 SYN/条目 | 回 SYNACK（样本 `ctrl=0xc0`），携带协商参数/会话条目 | 校验和、确认号与状态匹配的 ACK；仅 ACK 位不足以判成功 | 由链路重传状态机处理；耗尽则停止，不能按任意 ACK 推进 |
| 4 | 设备 → 车机 | 链路 `Connected`，控制条目版本适用识别优先流程 | 发 `0x1d00`（无参数），`hdr[7]` = 已确认控制会话号 | `0x1d01`（识别信息）| 有界等待；重发须有 profile 依据并区别链路重传。超时只说明无进展，不能证明车机不支持识别 |
| 5 | 车机 → 设备 | 已发 `0x1d00` | — | `0x1d01`，顶层参数携带车机自述 | 按适用 profile 校验；失败不得发接受。`0x1d03` 门控放行不证明拒绝载荷 schema，未实现时本地报错停止 |
| 6 | 设备 → 车机 | `0x1d01` 通过适用 profile 校验 | 发 `0x1d02`（无参数）| 设备按版本门控进入下一步；样本接着由设备发 `0xaa00` | 未推进时记录状态/能力，不盲重发接受消息 |
| 7 | 设备 → 车机 | 已发 `0x1d02` | 进入认证或直接进入会话（取决于门控，见 8.5）| 见 `11-device-authentication.md` | — |
| 8 | 车机 → 设备 | 认证/识别及能力门控满足 | — | 适用业务消息，可能包括 `0x4301` | 按 spec/14 校验；不得要求全部 14 字段非空；平台必填性和统一错误响应未证，不猜造回包 |
| 9 | 设备 → 车机 | 收到 `0x4301` 并解析成功 | 启动 CarPlay 会话（`analysis/05` §5.4）| — | 见 `10-message-catalog.md` 9.6 节 |

**注意**：步 4 与步 6 的 `0x1d00`/`0x1d02` 都**没有参数**。`0x1d01` 有参数，且参数 ID 必须落在 `link/R-6.3` 的白名单内（上限 `0x22`）。

依据：`A05.9`、`A05.10`、`A02.13`、`A05.3`。

## 8.4 版本门控：客户端走哪条路

`R-8.4`（MUST / CONFIRMED）控制会话的 `version` 来自**会话表项的第 3 字节**（`[24A446]`）：`iap2_sessionControl_getVersion`（`0x10011d4b8`）读 `[表项+2]`，查不到表项时为 0。`start` 按 `version == 2` 分岔：

| `version` | 日志串（`[24A446]`）| 启动的流程 |
|---|---|---|
| `== 2` | `"Control session version = 2, starting Identification..."` | 识别优先（传 1）|
| `!= 2` | `"Control session version != 2, starting Authentication..."` | 认证优先（传 0）|

**谁写这个字节**：SYN 线上条目的第三字节由 ParseSYNData 展开，CheckNegotiation 复制到工作块，NotifyConnection 再提交到生效表，见 `A02.15`。条目版本与 SYN 载荷首字节的链路版本是不同字段。初始 profile 分配及全部协商选择分支仍属 `OPEN-SES-1`。

依据：`A05.3`、`A05.4`、`A05.5`、`A05.6`。

`R-8.5`（SHOULD / 建议）首次台架实现可选取已观测的控制 version 2 profile，但必须使用握手确认的版本；不能只在本地强行置 2。其他版本未实现时显式报不支持，不暗中改版。

`R-8.6`（MUST / CONFIRMED）验证实验（用于在 24A446 上确认）：

1. 同时记录 SYN/SYNACK 控制条目的版本及双方消息方向；
2. 比较设备在已确认条目下先发 `0x1d00` 还是先发 `0xaa00`；本流程中 `0xaa00` 是设备出站，不能等待车机发送它来判版本；
3. 如需验证其他 profile，单独协商并记录结果，不通过任意改会话表版本来猜测对端。

依据：`A05.3`、`A05.4`、`A05.5`、`A05.6`、`A05.9`、`A02.13`。

## 8.5 会话号

`R-8.7`（MUST / CONFIRMED）样本会话号必须从握手追踪到业务消息，不得任意自选：

| 项 | 要求 |
|---|---|
| 取值 | 采用握手确认的控制会话条目；样本为 2/3，不能据此声称 1–254 任取均能互通 |
| 声明时机 | 先在 SYN/SYNACK 三字节条目中出现，再用于业务消息的 `hdr[7]` |
| 稳定性 | 整个连接期间不变 |
| 复用 | 新连接可以换号，也可以复用（`[23G90]` 观测到同一端点两次连接用了 2、3）|

依据：`A02.13`、`A02.14`、`A03.1`。

## 8.6 失败时的可观测锚点

`R-8.8`（MUST / CONFIRMED）客户端必须实现下面四条日志（措辞可自定，语义必须对应），否则无法区分"没收到"与"被门控拦下"：

| 锚点 | 对应固件串（`[24A446]`）| 触发位置 |
|---|---|---|
| 收到某消息 | `"Incoming Message ID: 0x%04X (%d bytes) for endpoint %@"`（`0x1001db8ab`）| 解析完成、**门控之前** |
| 被准入拦下 | `"Not identified for incoming message ID: 0x%04X! (endpoint %@)"`（`0x1001db8e2`）| 门控拒绝 |
| 无处理器 | `"No message handler found for incoming message ID: 0x%04X!"`（`0x1001db920`）| 门控通过但无实现 |
| 处理器失败 | `"Message handler returned false! (0x%04X for endpoint %@)"`（`0x1001db95a`）| 处理器返回假 |

依据：`A08.3`、`A08.4`。

## 8.7 本章不保证的事

`R-8.9`（未定义 / OPEN）下列三项本章不作保证，实现方必须自行验证：

1. **24A446 上的真实时序**：全章时序来自 23G90（`OPEN-RUNTIME-1`）；
2. **初始 profile 分配与完整协商选择规则**：表填充链已确认，跨版本和多会话仍未完整验证（`OPEN-SES-1`）；
3. **超时与重试次数**：固件里没有对应的重试逻辑证据，本章的 3 次/2 s 是 `[建议]`。

依据：`A02.9`、`A02.13`、`A08.2`。

## 8.8 定时器分层（跨 docset 唯一来源）

`R-8.10`（SHOULD / `[建议]`）下面三个定时器**只在本文档定义**；其他 docset 必须引用这里给出的名字与数值，
不得各自另写一个。三个值都是经验值，**不是固件常量**（无 `[24A446]` 依据），可按平台调整，
但必须保持 `T_first_byte < T_detect < T_link`。

| 定时器 | 值 | 起止 | 超时后的动作 |
|---|---|---|---|
| `T_first_byte` | 2 s | RFCOMM 打开 → 收到对端第一个字节 | 主动发 Detect（`R-8.3` 步 1）|
| `T_detect` | 5 s | 发出 Detect → 收到 SYN | 判 `NO_SYN`，重连 RFCOMM |
| `T_link` | 30 s | RFCOMM 打开 → 链路进入 `Connected` | 超时即重连 RFCOMM（总上限，兜底 `R-8.3` 步 1–2）|

`T_link` 必须覆盖「等首字节 + 发 Detect + 等 SYN」三段的正常耗时；`T_detect` 只覆盖最后一段。

引用方（改值时三处一起改）：

| 文档 | 位置 | 用法 |
|---|---|---|
| `link/spec/09-client-implementation-guide.md` | §9.10「`Detect` 等待对端 SYN」行 | `T_detect` = 5 s |
| `bluetooth_rfcomm/spec/09-client-open-rfcomm.md` | §9.5 R-9.17 / R-9.18 | `T_first_byte`、`T_detect`、`T_link` |

依据：`[建议]`，无固件常量来源。
