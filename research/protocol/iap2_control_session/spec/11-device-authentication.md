# spec/11 — 设备侧认证

本章只讲**设备侧**（模拟 iPhone）要做的事：向车机索取证书、发挑战、验签名、收尾。

## 10.1 认证的方向与目的

`R-10.1`（MUST / CONFIRMED）`[23G90]` 观测到的认证是**车机向设备证明自己**：车机提供证书链并对设备发出的挑战签名，设备验证。方向不要搞反。

| 角色 | 提供什么 | 验证什么 |
|---|---|---|
| 车机（配件侧）| 证书链（`0xaa01`）、证书序列（`0xaa06`）、对挑战的签名（`0xaa03`）| — |
| 客户端（设备侧）| 挑战（`0xaa02`）、收尾（`0xaa05`）| 证书链、签名 |

本序列验证的是**车机**，不能由此推出仿 iPhone 客户端必须持有配件私钥或签名凭证。客户端需要可信的验证材料与正确的验证实现。设备自身认证另有代码证据：link `R-6.5`、`R-6.6` 列出入站 `0xAA10/12/14/15`、出站 `0xAA11/13`，查询 feature 7；尚无该路径的端到端互通样本。`0x4301` 的 `mutualAuth` 不能仅凭名字等同于这套消息。若目标要求设备认证，其凭证身份、合法获取方式和协议须另行确认，不能假设任意 MFi 配件凭证可以代表 iPhone。

依据：`A05.10`、`A05.7`。

> **协议族边界**：本章只描述 **AccAuthentication**（`0xAA00`–`0xAA06`）的 23G90 七步样本。`link/spec/06` 还记录 DeviceAuthentication（`0xAA10`–`0xAA15`，feature 7）与 MFi4Auth（构造侧 `0x5100`/`0x5110`/`0x5111`/`0x5112`/`0x5113`/`0x5115`）两套不同的消息族；三者不能互推，也不能把本章七步套到另外两族。`0x4301` 的 `mutualAuth` 同样不能仅凭名字等同于其中任一族。

## 10.2 七步序列

`R-10.2`（MUST / CONFIRMED）`[23G90]` 观测到的完整序列，方向为设备侧视角：

| 步 | 方向 | 消息 | 参数 | 客户端动作 |
|---|---|---|---|---|
| 1 | 设备 → 车机 | `0xaa00` | `00 04 00 00`（空参数）| 发出请求 |
| 2 | 车机 → 设备 | `0xaa06` | ID 0 = 32 字节 ASCII 十六进制串 | 解析并保存（当作证书序列/选择符）|
| 3 | 设备 → 车机 | `0xaa00` | **无参数** | 发出第二次请求 |
| 4 | 车机 → 设备 | `0xaa01` | ID 0 = 607 字节 DER（PKCS#7）| 解析证书链、验链、取出叶证书公钥 |
| 5 | 设备 → 车机 | `0xaa02` | ID 0 = 32 字节随机数 | 生成挑战并保存 |
| 6 | 车机 → 设备 | `0xaa03` | ID 0 = 64 字节签名 | 用叶证书公钥验签 |
| 7 | 设备 → 车机 | `0xaa05` | **无参数** | 验签通过后发出 |

**步 2 与步 3 的差异是观测事实**：第一次 `0xaa00` 带 `len=4` 空参数，第二次不带参数。它们是否等价（例如"带空参数=请求序列，不带=请求证书"）**未取证**，实现方应按观测照发，不要合并成一次。

依据：`A05.10`、`A02.14`。

## 10.3 参数格式

`R-10.3`（MUST / CONFIRMED）**范围仅为样本**：下表是 23G90 的参数形态，直接位于消息参数区（API 称组 0；不额外编码一层“组 0”容器），不是嵌套消息。不能推广为所有认证参数 ID 均为 0：24A446 的 `0xAA01` handler 还读取 ID 1（auth type/U8）、ID 2（证书数据），见 link `R-6.6.1`。

| 消息 | 参数 ID | 值长度 | 编码 | 证据来源 |
|---|---|---|---|---|
| `0xaa00`（首次）| — | 0 | 仅 `00 04 00 00` 空参数 | `[23G90]` |
| `0xaa00`（二次）| — | — | 无参数 | `[23G90]` |
| `0xaa06` | 0 | 32 | ASCII 十六进制（`4C…CB` 形态）| `[23G90]` |
| `0xaa01` | 0 | 607（本样本）| DER：`30 82 …` 为 `ContentInfo(signedData)` | `[23G90]` |
| `0xaa02` | 0 | 32 | 随机字节 | `[23G90]` |
| `0xaa03` | 0 | 64 | 裸 `r‖s`（各 32 字节，P1363）| `[23G90]` + 可重复验签（§10.5）|
| `0xaa05` | — | — | 无参数 | `[23G90]` |

`0xaa01` 的长度**随证书链变化**，实现方必须按"参数长度"读，不能假设 607。

依据：`A05.10`、`A04.1`。

## 10.4 证书链校验

`R-10.4`（MUST / CONFIRMED）`[23G90]` 抓到的证书链里可读出的结构（DER OID 直接可读，不是猜测）：

| OID（十六进制）| 含义 |
|---|---|
| `2a 86 48 86 f7 0d 01 07 02` | PKCS#7 `signedData`（外层封装）|
| `2a 86 48 ce 3d 04 03 02` | `ecdsa-with-SHA256`（签名算法）|
| `2a 86 48 ce 3d 02 01` | `id-ecPublicKey`（`1.2.840.10045.2.1`，公钥算法，不是曲线）|
| `2a 86 48 ce 3d 03 01 07` | `prime256v1` / P-256（`1.2.840.10045.3.1.7`，曲线参数）|
| `2a 86 48 86 f7 63 64 06 24` | Apple 自定义扩展（`1.2.840.113635.100.6.36`）|
| `55 04 03` + `"Apple Accessories Certification Authority - 00000002"` | 样本叶证书的 issuer CN；不能证明容器包含该 CA 证书 |

客户端的校验职责（安全实现要求，不代表已经验证了完整信任链）：

1. 解析 `0xaa01` 的 PKCS#7 并提取证书。此样本实际只包含**一张叶证书**，不能要求线上容器至少包含叶 + 中间 CA；
2. 使用可信来源的 CA/信任锚构建并验证证书路径，执行适用的用途、有效期、撤销与扩展策略；本 docset 尚未提供足以完成该验证的信任材料。不能将对端自带根直接设为可信；
3. 样本中 `0xaa06` 文本等于叶证书 serialNumber 的大写十六进制形式（脚本已复核）；24A446 `0x100185708`–`0x100185734` 也有提取序列并比较的路径。其他证书类型的转换与不匹配处理仍待核实（`OPEN-SES-29` 尚未整体关闭）；
4. 任一步失败 → 不发送 `0xaa05`，按 `R-10.6` 处理。

**不得**把"验签通过"实现成"只看链长"或"只看 CN 字符串"，也不得跳过有效期检查。

依据：`A05.10`。

## 10.5 签名校验

`R-10.5`（MUST / CONFIRMED）**限两次 23G90 交换**：用样本证书公钥实际验证 `0xaa03`，结果如下：

| 项 | 值 | 证据 |
|---|---|---|
| 曲线 | P-256（prime256v1）| 证书公钥参数 OID `1.2.840.10045.3.1.7` |
| 验签输入 | 直接使用 `0xaa02` 的 32 字节作为 ECDSA digest | `VerifyHash(challenge, signature)` 成功 |
| 签名编码 | 裸 `r‖s`，64 字节 | 显式使用 P1363 格式验签成功 |
| 错误变体 | 先 SHA-256(challenge) 再验签 | `VerifyData(..., SHA256)` 失败；翻转挑战一位也失败 |

复现：`pwsh -NoProfile -File research/protocol/iap2_control_session/runtime/verify-auth-sample.ps1`。脚本先校验原始日志 SHA256，再验证两次交换。**证书自身的签名 OID 不决定挑战响应的哈希处理方式**；不得因看到 `ecdsa-with-SHA256` 就把线上挑战再哈希一次。本结果不证明信任链有效、其他 auth type 行为相同或所有车机兼容；其他认证 profile 须按适用规范与证据实现。

依据：`A05.10`、`A05.8`。

## 10.6 失败与重试

`R-10.6`（未定义 / OPEN）本阶段**没有**认证失败路径的证据：

- 固件的入站/出站恒放行名单里有 `0xaa04`（出站，`0x100005138` 的 mask `0x35`），但**没有语义证据**；不得把它当作"认证失败"消息使用，除非抓到实际帧（`OPEN-SES-30`）；
- 车机对"验签失败"的反应未知。

`[建议]` 客户端的失败处理：

| 失败点 | 处置 |
|---|---|
| `0xaa01` 解析失败 / 链不完整 | 不发 `0xaa05`；断开重连，最多 2 次 |
| 验签失败 | 同上，且记录挑战与签名（便于对比）|
| 8 s 内无 `0xaa06`/`0xaa01`/`0xaa03` | 重发对应请求一次，再超时则断开 |

依据：`A05.10`、`A07.1`。

## 10.7 证据边界

`R-10.7`（MUST / CONFIRMED）本章每条结论的来源必须可区分：

| 结论 | 来源 | 强度 |
|---|---|---|
| 七步顺序、方向 | `[23G90]` 抓包 | 观测 |
| 参数长度、值形态（32/607/64 字节）| `[23G90]` 抓包 | 观测 |
| 曲线/哈希 OID | `[23G90]` 证书字节 | 观测（OID 直读）|
| 裸 r‖s 编码、挑战作为 digest | `runtime/verify-auth-sample.ps1` 两次交换 + 负向验证 | **样本实证**，不是全版本规范 |
| `0xaa04` 的语义 | 名单里存在 | **未知** |
| 设备认证 | link `R-6.5`/`R-6.6` 有 handler/发送代码 | **静态路径已见**；凭证要求、与 `mutualAuth` 的关系及端到端互通未知 |

实现方在评审时必须按此表说明"哪一段是推断"，不得把推断写成协议要求。

依据：`A05.10`、`A05.8`、`A00.1`。

## 10.8 与 MFi 的关系

`R-10.8`（MUST）证书链、根证书、双向认证所需的设备凭证、以及任何与 Apple 协处理器相关的步骤，全部以 **MFi 规范与授权材料**为准。本章只描述"线上看到什么、客户端要在什么时机做什么"，不定义密码学参数、不提供根证书、不描述凭证签发流程。

实现方应：

1. 用 MFi 材料里的根证书做 `R-10.4` 的验链；
2. 若需设备自身认证，结合 link 已确认的 `0xAA10`–`0xAA15` 路径，另行核实合法凭证和签名流程；不能把配件认证七步当成设备认证实现（`OPEN-SES-31`）；
3. 不要用本章的 P-256 观测去反推 MFi 的技术规范细节。

依据：`A05.8`、`A05.10`。
