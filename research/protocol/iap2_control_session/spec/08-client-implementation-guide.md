# spec/08 — 客户端实现指南（能做什么、不能做什么、怎么把不能变成能）

本文件不是协议条款的重复，而是**施工指南**：把一个"想连上车机的客户端"拆成可执行的步骤，逐步标注"依据是什么条款 / 哪一步没有证据"。

本文件的条款编号为 `R-7.x`（第 7 章）。凡写 `未定义 / OPEN` 的地方，实现方必须自己选定一种做法并写进自己的设计文档，不得声称"协议规定如此"。

## 7.1 结论先行：当前证据能支撑到哪一步

`R-7.1`（MUST / CONFIRMED）现有证据为下列四块提供实现依据，但**不能声称完整实现或无需继续取证**：链路 OPEN 项、完整协商选择、错误路径与跨 profile 行为仍须核验；内存布局不要求照搬。

| 块 | 依据 |
|---|---|
| 链路层（成帧、校验、序号、确认、重传、SYN 协商、状态机） | 上一阶段 `link/`（`link/R-2.x`–`link/R-5.x`） |
| 会话层结构（endpoint/链路对象、会话表几何、5 条发送队列） | `R-1.x` |
| 会话号路由与四类数据面分发 | `R-2.x` |
| 消息层与参数层编解码 | `R-3.x` |

依据：`A00.1`、`A01.3`、`A02.2`、`A02.5`、`A03.1`、`A04.1`。

`R-7.2`（MUST / CONFIRMED）下列三块可以**部分实现**，但有必须用实验补的空白：

| 块 | 已有 | 空白 |
|---|---|---|
| 准入控制（两张白名单 + 认证/识别状态） | 名单与条件均已确认 | 两个集合**何时**被填（`OPEN-SES-15`）→ 需知道对端何时把某 ID 加进集合 |
| 会话建立（缓冲、处理器注册、版本门控、启动顺序） | 结构、填充提交与顺序有静态依据 | 初始 profile 分配与跨版本协商（`OPEN-SES-1`） |
| 拆除与重连 | 释放清单与顺序确认 | 异步清理与释放的同步（`OPEN-SES-26`）、解析器与链路对象的释放（`OPEN-SES-28`） |

依据：`A07.1`、`A07.4`、`A07.8`、`A05.1`、`A05.5`、`A12.1`、`A12.4`、`A12.6`。

`R-7.3`（未定义 / OPEN）下列三块**现在还不能完整实现**，因为缺的是"顺序"和"会话号取值"，不是"格式"；`0x4301` 的静态字段格式已经在 [spec/14](<14-carplay-start-schema.md>) 闭合，但运行时平台交接仍未闭合：

| 块 | 缺什么 | 编号 |
|---|---|---|
| 识别/认证的消息交换顺序 | 谁先发、发几条、什么条件推进 | `link/OPEN-ID-1`、`link/OPEN-AUTH-1` |
| 会话号的初始分配与完整选择 | 初始 profile 分配、多会话冲突及跨版本规则；SYN 填充提交已确认 | `OPEN-SES-1` |
| CarPlay 启动交接 | 平台必填性、错误响应、Wi-Fi/IP 与后续控制/媒体/输入结果 | `OPEN-SES-2` |

依据：`A02.9`、`A05.15`、`A05.17`、`A01.8`。

> 已有 23G90 单 profile 的时序和握手会话号证据；仍缺完整的跨版本协商、认证信任策略和 CarPlay 网络/媒体实现。不能把“有格式参考”当作“端到端已具备”。

## 7.2 建议的实现顺序

`R-7.4`（MUST / CONFIRMED）**先写接收路径，再写发送路径。** 理由是可判定的：入站白名单让对端在识别完成之前就能发 `0x1d01`、`0x1d05`、`0x1d06`、`0xaa01`、`0xaa03`，而客户端发出的任何非白名单消息都要先满足"认证 2 + 识别 6 + 集合含 ID"。先做接收端，能在还不知道顺序的情况下把对端说的话全部收下来并记账。

依据：`A07.1`、`A07.3`、`A07.4`、`A08.2`。

`R-7.5`（MUST / CONFIRMED）接收路径必须按字节流实现，不按包：一个包可以含多条消息，一条消息可以跨多个包；解析器返回"一条消息完成"才进入门控。

依据：`A03.5`、`A08.2`。

`R-7.6`（MUST / CONFIRMED）每条消息的处理顺序固定为：解析 → 记录日志 → 门控 → 查处理器 → 调用。日志必须在门控**之前**打，否则出问题时无法区分"没收到"和"被门控拦下"。

依据：`A08.3`、`A08.4`、`A07.7`。

## 7.3 会话号怎么处理（当前唯一可行的策略）

`R-7.7`（MUST / CONFIRMED）样本中的会话号在 **SYN/SYNACK 阶段已经出现**，不是第一条业务消息才声明。version 1 的 10 字节固定头后，第一条连接双方条目均为 `02 00 02`，第二条均为 `03 00 02`；车机 SYN 早于 iPhone SYNACK 和 `0x1d00`。

| 客户端角色 | 做法 |
|---|---|
| 设备侧（连车机的那一侧） | 使用握手确认的控制会话条目；样本中沿用车机 SYN 的 2/3，并以相同号发送 `0x1d00`，不得另选号仅在业务帧中声明 |
| 配件侧 | 样本中先发含 2/3 的 SYN；不得把配件描述成直到第一条业务消息才得知会话号 |

依据：`A02.13`。

与之相对，**类型编号（0/1/2/4）可以硬编码**：它在分发 switch 与 26 个查表调用点的立即数上三处一致（`R-2.10`）。实现方最常见的误判是"类型能硬编码 ⇒ 会话号也能"，这两件事必须分开判断。

依据：`A02.11`、`A02.12`。

`R-7.8`（未定义 / OPEN）**初始号的具体分配规则**未闭合：两次样本 2/3 不能证明递增算法。已确认的填充链是 `ParseSYNData → CheckNegotiation → NotifyConnection`（`A02.15`），字面偏移扫描不能否定块复制写入。

实现方应记录 SYN 提议、SYNACK 结果、提交的会话表和后续 `hdr[7]` 的对应关系。不能任意换号重试；多会话、冲突和初始 profile 选择仍为 `OPEN-SES-1`。

依据：`A02.9`、`A02.10`、`A02.13`。

## 7.4 把"未知"变成"已知"的三个实验

`R-7.9`（SHOULD / INFERRED）测试建议一：同时记录 SYN/SYNACK 条目、提交表和业务包 `hdr[7]`，不能仅按消息族猜号。判据：

- 链路控制包的 0 不作为业务会话；业务包必须对应已协商条目。
- 多个 ID 按协商的类型映射检查，不照抄另一连接的号码。
- 比对接收、提交、首条业务发送的时间，检查提前发送和陈旧路由。

依据：`A02.2`、`A02.5`、`A03.1`。

`R-7.10`（SHOULD / INFERRED）测试建议二：在本地回放/模拟对端中注入未知号、重复 ID/类型和超限条目，确认客户端拒绝或隔离，不错误分发。不以“真实对端未回应”证明其内部路由，也不把未经确认的 `0x0004` 当探针消息。

依据：`A07.4`、`A10.6`、`A02.3`。

`R-7.11`（SHOULD / INFERRED）测试建议三：在授权停车台架上按已确认状态机主动发起并记录顺序，仅对定义了应答的消息发送应答。不能对每条已知消息自动回复，也不能仅被动等待本应由设备主动发起的识别/认证。一次成功时间线不等于所有 profile 的规范。

依据：`A07.1`、`A07.3`、`A08.5`。

## 7.5 卡点定位

`R-7.12`（MUST / CONFIRMED）实现方的日志里必须能区分四种失败，它们对应固件的四条日志串（地址为 24A446 的常量池地址）：

| 现象 | 固件日志串 | 含义 | 下一步 |
|---|---|---|---|
| 收到但没处理 | `"Incoming Message ID: 0x%04X (%d bytes) for endpoint %@"`（`0x1001db8ab`） | 日志在门控**之前**打印，出现即只代表"收到了" | 继续看后三条 |
| 被准入拦下 | `"Not identified for incoming message ID: 0x%04X! (endpoint %@)"`（`0x1001db8e2`） | 认证/识别状态或集合不满足 | 检查状态机，或该 ID 本就不在名单内 |
| 没有处理器 | `"No message handler found for incoming message ID: 0x%04X!"`（`0x1001db920`） | 门控通过但无实现 | 补处理器 |
| 处理器返回失败 | `"Message handler returned false! (0x%04X for endpoint %@)"`（`0x1001db95a`） | 解析或参数不合法 | 检查参数编码（`R-3.7`、`R-3.8`） |

依据：`A08.3`、`A08.4`。

## 7.6 离线自测

`R-7.13`（MUST / CONFIRMED）客户端在接真机前必须能通过一组离线向量，判据只用本规范已确认的规则：

| 用例 | 期望 |
|---|---|
| 一条 `40 40 len id …` 消息被拆成 3 段喂入 | 第 3 段喂完后才产生"消息完成"事件（`R-3.5`） |
| 一条消息的总长字段与实际参数长度不符 | 以总长为准，不得靠"游标走到尾"推断（`R-3.2`） |
| 参数总长为 4（无值） | 通用遍历器接受该零值 TLV 并继续；是否解释为 presence/请求标记由 message profile 决定（`R-3.8`） |
| 参数值里含 `40 40` | 若实现按长度跳过参数区，则不受影响；若逐字节扫描起始标记，会失步（`R-3.6`） |
| 表项数为 0 时收到任一入站数据 | 丢弃且不投递（`R-2.4`） |
| 类型 3 的表项 | 分发返回 0，静默丢弃（`R-2.9`） |
| 消息尾部出现 `len=4` 的空参数（`00 04 00 00`） | 仅在对应 message profile 中作为 presence/空值处理；通用遍历器按 parent/prev 和边界执行，不得把 len=4 一概判坏 |

依据：`A03.4`、`A03.5`、`A04.3`、`A04.4`、`A02.3`、`A02.8`、`A03.7`。

## 7.7 握手骨架（已移入正式章节）

`R-7.15`（MUST / CONFIRMED）设备侧启动序列的**权威版本**在 [spec/09](<09-device-side-startup.md>) 的 `R-8.3`（总表含每步的前置条件、期望响应与失败分支）。本节不再重复维护那张表，以免两份清单漂移；`R-7.15` 在此只保留一句声明：

> 23G90 上存在一条可复现的启动序列（`0x1d00 → 0x1d01 → 0x1d02 → 0xaa00/06/00/01/02/03/05 → 业务消息`），它是本客户端实现 DEFAULT，但不是 24A446 的常量。

依据：`A05.9`、`A05.10`、`A02.13`、`A02.14`。

## 7.8 还需要补的证据（按对"能连上"的影响排序）

`R-7.14`（未定义 / OPEN）按 7.7 的骨架实现之后，仍然缺下面四项。它们可能阻止路由、门控或 CarPlay 交接，不能保证“不影响连接”：

| 优先 | 缺什么 | 编号 | 补齐方式 |
|---|---|---|---|
| 1 | `0x4301` 平台交接与下游 CarPlay 结果 | `OPEN-SES-2` | 用真实车机验证字段必填性、错误/重试、Wi-Fi/IP、控制、媒体与输入 |
| 2 | 两个准入集合的填充时机 | `OPEN-SES-15` | 用 7.4 实验一的时间线，看某 ID 第一次被放行时发生了什么 |
| 3 | 初始 profile 分配及完整协商选择 | `OPEN-SES-1` | 已有填充/提交链，继续覆盖多会话冲突及跨版本；不能以首个业务帧猜号 |
| 4 | 24A446 同构建的运行样本 | `OPEN-RUNTIME-1` | 用目标构建设备抓一次，放进 `runtime/` 并登记 sha256 |

依据：`A01.8`、`A05.15`、`A05.17`、`A07.8`、`A02.9`。
