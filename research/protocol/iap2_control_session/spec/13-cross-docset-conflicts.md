## 12.2 优先级规则

`R-12.2`（MUST / CONFIRMED）两份文档重叠时按主题划分优先级，不得笼统说"某一份为准"：

| 主题 | 以谁为准 | 理由 |
|---|---|---|
| 成帧、校验和、序号/确认/重传、SYN 参数、链路 FSM | **link** | 那些规则在 link 里逐字节取证过，control 只是引用 |
| 会话层（表、路由、队列）、消息/参数编码 | **control** | control 有 `analysis/02`–`04` 的指令级证据 |
| 识别与认证的**方向、顺序** | **control** | 有 24A446 门控 + 23G90 实测双重证据；link 侧无实测 |
| 认证数据的**封装形态** | **control** | 抓包直接可读 |

依据：`A05.9`、`A05.10`、`A03.1`。

## 12.3 对实现方的要求

`R-12.3`（MUST / CONFIRMED）实现方若同时读了两份文档，必须在代码里体现 `R-12.2` 的划分：

1. 帧/校验/重传逻辑按 link 的 `R-2.x`–`R-5.x`；
2. 识别与认证的消息方向、顺序按 `spec/09`/`spec/11`；
3. 遇到两份文档对同一字段给出不同结论时，**以本章清单为准**，并把分歧写进自己的设计记录（不要私下选一个）。

依据：`A05.9`、`A05.10`。

## 12.4 变更请求的提交方式

`R-12.4`（MUST）本阶段采用"只记录、不改动"的方式：

| 项 | 做法 |
|---|---|
| 是否修改 link 文件 | 原阶段不改；全 docs 复核阶段已按用户授权修订，保留证据与历史 |
| 记录位置 | `CHANGE-REQUESTS/CR-001-link-identification-and-auth.md` |
| 内容要求 | 逐条给"原文位置 + 原文引用 + 建议改法 + 证据地址"，使 link 的维护者能独立复核 |
| 状态 | `PARTIAL`：CR-2 文案已对齐；CR-3 边界重新限定；CR-4 及端到端验证仍待处理 |

依据：`A00.1`。

## 12.5 不接受的做法

`R-12.5`（未定义 / OPEN）明确禁止三种"和稀泥"：

1. 把 `C-1` 写成"两种方向都可能"——24A446 的门控名单是单向的，不存在双向；
2. 把 `C-2` 写成"两种封装都支持"——除非抓到 `0x5500` 嵌套的真实帧，否则那是无证据的扩展；
3. 把配件身份验证与客户端签名身份混为一谈，或因为缺少验证材料便跳过认证并发送成功。

依据：`A07.2`、`A05.10`。
