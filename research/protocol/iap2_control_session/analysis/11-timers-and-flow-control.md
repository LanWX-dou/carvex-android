# analysis/11 — 定时器与流量控制

结论先行：**会话层没有定时器，也没有流控。** 所有超时、重传、窗口都在链路层；会话层唯一的资源限制是"每类型一条 255 项的发送队列"。

## 11.1 建链时建立的定时器与参数

`_iAP2LinkCreate`（`0x100033fd0`）在建链时一次性建好：

```
0x1000340cc  mov w8,#0xff
0x1000340d0  strb w8,[x19,#0xc2]        ; 定时器句柄初值 0xFF = 空闲
0x100034100–0x10003410c  创建定时器对象 → [link+0xc8]
                         两个回调：0x1000342c0 / 0x10003435c
0x1000341a4  [link+0x160] = x21          ; SYN 参数源对象
0x1000341a8–0x1000341c0  从 x21 拷 0x38 字节到 link+0x168；再拷 2 字节到 link+0x198
0x1000341cc  w10 = 0x3e8ffff
0x1000341d0  str w10,[link+0x19e]        ; +0x19e = 0xFFFF ; +0x1a0 = 1000
0x1000341d8  [link+0x1a2] = 10           ; (u16)
0x1000341dc  d0 = [0x1001b3348]          ; 常量字节 01 01 1e 00
0x1000341e4  str s0,[link+0x19a]         ; 发送方向 SYN 参数默认值
0x1000341ec  [link+0x1a4] = 0xFFFF0100   ; 会话表项数 = 0
```

常量 `0x1001b3348` 的实测字节是 `01 01 1e 00`，即 `{ver=1, maxRetrans=1, maxCumAck=30}`。这三个值就是链路层"重传 1 次、累积确认阈值 30"的来源，与上一阶段的 SYN 参数布局一致。

| 偏移 | 值 | 本阶段可确认的用途 |
|---|---|---|
| `+0x0c2` | `0xff` → 定时器句柄 | 收包后启动 0xD 类定时器时写回（`analysis/02` 步骤 4） |
| `+0x0c8` | 定时器对象 | 全链路唯一 |
| `+0x198` | 来自 SYN 源（u16） | 未定 → `OPEN-SES-23` |
| `+0x19a` | `01 01 1e 00` | 发送方向 SYN 参数 |
| `+0x19e` | `0xFFFF` | 未定 → `OPEN-SES-23` |
| `+0x1a0` | `1000` | 未定（毫秒级超时的强候选）→ `OPEN-SES-23` |
| `+0x1a2` | `10` | 0xD 类定时器的超时参数（`0x1000327f4` 读它）|
| `+0x1a4` | `0xFFFF0100` | 低字节 = 会话表项数（0）；高 3 字节未定 → `OPEN-SES-24` |

## 11.2 会话层没有任何定时器

逐项核对：

| 检查 | 结果 |
|---|---|
| `sessionControl_init` 是否建定时器 | 否，只建缓冲（`0x10011d174`–`0x10011d184`） |
| `sessionControl_start` 是否建定时器 | 否，只有一次 `startFeatureFromDevice`（`0x10011d470`） |
| endpoint 上是否有会话级定时器字段 | 未发现；`+0xc8` 是控制缓冲，不是定时器 |
| 控制消息是否有"等确认超时" | 无证据；`…AndCallbackOnACK` 只是注册回调（`OPEN-SES-21`） |
| 是否有会话级心跳消息 | 无证据；EA 面的"0 字节包"是数据面合法事件，不是会话心跳 |

所以"控制会话保活"这件事在本层**不存在**：链路层断连直接触发 `linkStateChanged(0)`（`analysis/09`），不需要会话层超时判定。

## 11.3 唯一的背压：每类型发送队列

```
0x10003416c  x24 = link+0x130
0x100034170  w25 = 5
0x100034174  loop:
0x100034180      x22 = iAP2ListInit(x22, 0xff, 8)     ; 容量 255、元素 8 字节
0x100034184      [x24 + i*8] = x22
0x1000341a0      b.ne loop
```

- 5 条队列，对应类型 0–4。
- 每条容量 **255 项**（`0xff`），元素 8 字节（存的是包指针）。
- 入队时按表项 `[1]` 选队列（`analysis/02` 的出站证据）。
- **没有看到入队失败的处理**：`iAP2LinkQueueSendDataWithSentCallback`/`PacketInternal` 在两处都对表项数与匹配结果做了 `cbz` 分支（找不到会话即失败），但没有对"队列已满"做判断 —— 队列满的行为未取证 → `OPEN-SES-25`。

按"一条控制消息 ≤ 65535 字节、链路单包载荷上限由 `+0xc0` 决定"推算，队列满意味着最多 255 个待发包；真实上限取决于链路层窗口（`maxCumAck=30`），所以**背压实际上先由链路层触发**，会话队列很难真正填满。

## 11.4 与上一阶段的衔接

上一阶段把 `+0x120`/`+0x128` 记作两条 8 字节元素表并登记了 `link/OPEN-SES-1`。本阶段确认它们与**会话无关**：会话表在 `+0x1a4`/`+0x1b8`，而 `+0x120`/`+0x128` 是建链时按 `bufSize` 建的两条表（`0x100034130`、`0x100034154`），之后由链路层使用（`+0x118` 指向"当前收包"即其证据之一）。

> `link/OPEN-SES-1` 因此**部分解答**：会话表的位置已确定；两条 8 字节表的具体角色仍属链路层，本阶段不改上一阶段的结论。
