# analysis/04 — 参数编码与嵌套

消息头之后是参数区。本文件把参数的 4 字节头、嵌套规则、以及 parent/prev 遍历和空参数的边界取证。

## 4.1 四字节参数头

| 偏移 | 宽度 | 内容 | 证据 |
|---|---|---|---|
| `+0` | 2 | **该参数总长（大端，含这 4 字节头）** | `0x100067740` `ldrh w9,[x1]` → `0x100067744` `rev16`；`0x1000053e0` 累加 |
| `+2` | 2 | **参数 ID（大端）** | `0x100067710`：`ldrh w8,[x0,#2]` → `rev w8,w8` → `lsr #16` |
| `+4` | n | 值 | `0x1000677cc` `add x8,x1,#4`（返回值指针）；`0x100067814` `mov x0,x8` |

`iAP2MsgGetParamID`（`0x100067710`）只有四条指令：

```
0x100067710  ldrh w8,[x0,#2]     ; 取 +2 处的 16 位
0x100067714  rev  w8,w8          ; 32 位字节反转
0x100067718  lsr  w0,w8,#0x10    ; 取高 16 位 = 原 16 位的大端解释
0x10006771c  ret
```

`rev` + `lsr #16` 等价于"按大端读 16 位"，与 `iAP2MsgGetMsgID`（`0x100004b60` 的 `rev16`）同构。所以参数 ID 与消息 ID 都是**大端 16 位**。

**值长度 = 参数长度 − 4**，这条在 `0x100067748`–`0x10006774c` 显式算了：`w9 = rev16(*p)`；`subs w9,w9,#4`；`csel w9,wzr,w9,lo`（小于 4 时取 0，防下溢）。

## 4.2 遍历与边界

`iAP2MsgGetFirstParam(msg, parent)` 的第二个参数是**父参数指针**，不是“上一个参数”：

- `parent == 0`：从消息缓冲 `buf+6` 取顶层第一个参数。它检查剩余空间至少 4 字节，并检查第一个参数声明长度不超过消息剩余空间；这里没有把长度 4 一概拒绝的门槛。
- `parent != 0`：先验证父参数总长与消息边界，再把父参数值区 `parent+4` 作为子参数序列起点。父参数自身总长必须至少 5；子参数声明长度至少 4 且不得超过父值区剩余长度。因而子参数可以是 `len=4` 的空值。
- `GetNextParam(msg, parent, prev)` 由 `0x100067824` 把错误指针置零后跳到 `0x100005448`；该 helper 以 `prev` 的声明长度推进到下一个同级参数，检查下一项起点小于父参数末尾、剩余消息空间足够容纳下一项；但没有证明下一项的整个值区都在父末尾以内，也没有在返回前统一检查下一项 len>=4。调用方必须把 `parent` 保持不变，不能把 `prev` 作为第二参数传回 `GetFirstParam`。

因此应区分三种长度规则：消息头后的顶层首项可为 4；嵌套父项必须至少 5；嵌套首子项声明长度至少 4，Next helper 检查当前 prev 长度至少 4。长度 4 并不等于“非法参数”，只是值长度为 0；是否允许它由消息 profile 和上层 getter 决定。23G90 的 `0xaa00` 尾部 `00 04 00 00` 是线路旁证，不能用通用 getter 的 typed-value 检查替代 TLV 边界检查。

证据：

| 位置 | 结论 |
|---|---|
| `0x100067774..0x1000677b0` | 顶层起点 `buf+6`、剩余至少 4、声明长度不越界 |
| `0x1000677c4..0x100067820` | 父参数边界、父总长 ≥5、子项从 `parent+4` 起且 `len>=4` |
| `0x100067824` → `0x100005448` | `GetNextParam` 的真实跳转；按 `prev` 长度推进 |
| `0x100005448..0x1000055e4` | 同级/嵌套范围检查与错误路径 |

## 4.3 嵌套参数

`0x10016d3ac` 的 `0x4301` handler 对外层参数取得父参数后，再调用参数遍历器读取其子参数，并在失败时打印 `Subparam ID ... ignoring message`。静态证据确认了“父参数值区承载同格式子 TLV”这一结构；结合 `0x100067738` 的父参数分支，子序列起点是 `parent+4`，边界是父参数总长减去 4 的值区。

实现时必须把 `parent` 与 `prev` 分开保存：

```c
Param *parent = get_first_param(msg, 0);
for (; parent; parent = get_next_param(msg, 0, parent)) {
    Param *child = get_first_param(msg, parent);
    for (; child; child = get_next_param(msg, parent, child))
        consume(child);
}
```

若父参数总长小于 5、子项不足 4 字节、声明长度越过父值区，遍历器返回 NULL；这不是“消息一定损坏”，而是该父参数的子序列不可继续。外层消息是否拒绝由对应 message profile 决定。

> `OPEN-SES-10` 已收窄：父/子边界与首个子项起点已由 `0x100067738` 直接确认；next helper 的异常边界和所有 profile 的拒收策略仍需补证。实现必须额外校验每项 len>=4 且整个项在所属父值区内，不得照搬缺失检查。

## 4.4 写入侧

`iAP2MsgInit`（`0x100003424`）把写游标放在 `msg+0x20 = buf+6`，之后每加一个参数由 `iAP2MsgInitParam`（`0x100003a68`）写下 4 字节头并前移游标，最后由 `iAP2MsgCalcMessageLen`（`0x1000053a4`）把所有参数长度累加回填消息头。三段职责清晰：

| 阶段 | 函数 | 动作 |
|---|---|---|
| 建立 | `iAP2MsgInit` | 写起始标记、消息 ID、把游标放到 `+6` |
| 追加 | `iAP2MsgInitParam` / `iAP2MsgAddU8Param` … | 写 `{长度, ID}` 头与值，游标前移 |
| 收尾 | `iAP2MsgCalcMessageLen` | 累加参数长度，回填消息总长 |

> **`OPEN-SES-11`**：`iAP2MsgInitParam`（`0x100003a68`）与 `iAP2MsgAddU8Param`（`0x1000042b4`）已导出但未逐指令核对，因此"追加阶段写的是占位长度、由收尾阶段修正"这一常见做法**未被证实**；只能说收尾阶段确实重算了总长。
