# analysis/03 — 消息帧格式

iAP2 **消息**（message）与 iAP2 **包**（packet）是两层不同的封装。上一阶段处理的是包（`FF 5A | 长度 | ctrl | seq | lt | session | 头校验 | 载荷 | 载荷校验`，见 `link/R-3.1`）。本文件处理包内载荷里的消息层。

## 3.1 六字节消息头

`_iAP2MsgInit`（`0x100003424`）是唯一的消息构造入口：

```
0x100003428–0x100003434  memset(msg, 0, 0x48)          ; 消息对象 0x48 B
0x100003438  [msg+0x18] = buf                          ; 缓冲区
0x10000343c  [msg+0x10] = buflen
0x100003440  [msg+0x28] = x4 ; [msg+0x30] = x5         ; 两个回调
0x100003448  ldr d0,[0x1001b3ad0]                      ; 常量 40 40 00 06
0x100003450  str s0,[buf]                              ; ★ buf[0..3] = 40 40 00 06
0x100003454  lsr w8,w1,#8 ; strb w8,[buf,#4]           ; ★ buf[4] = msgID 高字节
0x10000345c  strb w1,[buf,#5]                          ; ★ buf[5] = msgID 低字节
0x100003460  [msg+0x20] = buf + 6                      ; 参数写游标
```

常量 `0x1001b3ad0` 的实测字节是 `40 40 00 06`：前两字节是起始标记，后两字节是长度字段的初值 6（只有消息头时的总长）。所以线段布局为：

| 偏移 | 宽度 | 内容 | 证据 |
|---|---|---|---|
| `+0` | 2 | 起始标记 `0x40 0x40` | `0x100003450`，常量 `0x1001b3ad0` |
| `+2` | 2 | **总长（大端，含 6 字节消息头）** | `0x10000528c`（读）、`0x100005428`（写） |
| `+4` | 2 | **消息 ID（大端）** | `0x100003454`–`0x10000345c`（写）、`0x100004b5c`（读） |
| `+6` | … | 参数区 | `0x100003460` |

四个取值函数的读法一致，都先校验 `[msg+0x10] >= 6`：

| 函数 | 读法 | 证据 |
|---|---|---|
| `iAP2MsgGetSom` `0x100067694` | `rev16(*(u16*)buf)`，等于 `0x4040` | `0x1000676ac`–`0x1000676b0` |
| `iAP2MsgGetMsgLen` `0x100005274` | `rev16(*(u16*)(buf+2))` | `0x10000528c`–`0x100005290` |
| `iAP2MsgGetMsgID` `0x100004b44` | `rev16(*(u16*)(buf+4))` | `0x100004b5c`–`0x100004b60` |
| 参数游标 | `buf+6` | `0x100003460`、`0x10006777c` |

注意 `0x100004b54` 与 `0x100005284` 都用 `cmp w9,#6; b.lo` 拒绝短于 6 的消息——**长度不足 6 的消息连 ID 都取不出来**，因此"最短合法消息 = 6 字节，无参数"。

## 3.2 长度重算

`_iAP2MsgCalcMessageLen`（`0x1000053a4`）：

```
0x1000053b8  iVar4 = 6                                  ; 起点：消息头
0x1000053c0  puVar2 = buf + 6                           ; 第一个参数
0x1000053c4  若 参数区为空 或 剩余 < 4 → 直接落 0x100005428（长度 = 6）
0x1000053e0  循环:
0x1000053e0      iVar4 += rev16(*(u16*)puVar2)          ; 累加参数自身声明的长度
0x1000053e4      puVar2 = iAP2MsgGetNextParamWithError(msg, 0, puVar2, 0)
0x1000053e8  while (puVar2 != 0)
0x100005428  buf[2] = iVar4 >> 8 ; buf[3] = iVar4 & 0xff ; ★ 写回大端总长
0x100005438  return iVar4
```

要点：

- 总长是**累加**出来的，不是"写游标 - 起点"，因此参数区里一旦有长度字段与实际内容不一致，消息总长会跟着错——长度字段是权威。
- `iAP2MsgSendControl`（`0x10000530c`）在发消息前又算了一次并**重写** `buf[2..3]`（`0x100005340`–`0x100005350`），随后才把 `msg[0] = buf`、`[msg+8] = 长度`（`0x10000535c`–`0x100005364`）。两处写同一个字段，值是同一个函数算出来的，属于冗余而非冲突。

## 3.3 解析器与字节流

控制会话收数据时并不假设"一段 = 一条消息"，而是**逐字节喂解析器**：

```
_iap2_sessionControl_parseIncomingMessage  0x10011d518
    for (i = 0; i < len; i++)
        iAP2MsgParserConsumeByte(component[0x78], buf[i], &msg)
        当解析器报告一条消息完成时 → 处理 msg
```

解析器在 `iap2_endpoint_create` 里创建（`0x1001295e0`）：`malloc(0x1001f)` = **65567 字节**缓冲，`iAP2MsgParserInit(0xffff, buf, link, 0x4040)`——第 1 参数 `0xffff` 是单条消息上限，第 4 参数 `0x4040` 与消息头的起始标记同值。

推论（有界）：一条消息最大 65535 字节，而链路单包载荷上限由 `link+0xc0`/`link+0x1a6` 决定（上一阶段 `link/R-4.x`）。所以**一条大消息必须跨多包重组**，重组由解析器按字节流完成，不依赖包的边界。这解释了为什么 `parseIncomingMessage` 的循环是"喂字节"而不是"喂包"。

> **`OPEN-SES-8`**：`iAP2MsgParserConsumeByte`（`0x10008eb68`）与 `iAP2MsgParserInit`（`0x10008eb48`）已导出但未逐指令核对，因此"起始标记 0x4040 只出现在消息首位、参数区内部出现 0x4040 不会误判"这一点**未证明**。若解析器只认 `0x40 0x40 + 合理长度`，则参数区含 0x4040 时应依赖长度字段跳过；若它做无状态扫描，则存在误同步风险。

## 3.4 消息层与包层的关系

| 层 | 起始标记 | 长度字段 | 校验 |
|---|---|---|---|
| 包（link） | `FF 5A` | 2 字节大端，整包长 | 头校验 + 载荷校验（`link/R-3.x`） |
| 消息（session） | `40 40` | 2 字节大端，整条消息长 | **无**（无消息级校验和） |

消息层没有独立校验和，完整性完全依赖包层的两个校验和。这一点在实现上是自洽的：控制消息跨包重组时，若中途丢包，包层会先失败，不会把残缺字节流喂到解析器。

> **`OPEN-SES-9`**：包内载荷是多条消息首尾相接还是"一包一消息"，本阶段未取证。`parseIncomingMessage` 的逐字节设计暗示前者，但没有找到"下一次调用从上次未完成位置继续"的状态证据以外的反证。
