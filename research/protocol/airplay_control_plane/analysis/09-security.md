# 09 · 安全边界

> 覆盖要求 #11。只写"能从固件证据支撑"的部分；没有证据的安全假设一律标 `OPEN`。

## 9.1 三方密钥的分层

| 层 | 作用 | 证据 |
|---|---|---|
| 长期身份密钥（Ed25519） | Pair-Setup 里签 M5/M6，用于互相记住 | `Pair-Setup-Controller-Sign-*`（`0x18bf6c3c7`/`0x18bf6c3e7`）、`Pair-Setup-Accessory-Sign-*`（`0x18bf6c4ca`/`0x18bf6c4e9`） |
| 临时 ECDH 密钥与配对加密密钥 | 本完整Verify路径先生成临时密钥、求共享秘密，再派生TLV加密密钥 | `A14.1`：ECDH标签用于M1私钥材料，Encrypt标签用于M2共享秘密的后处理，不能混同 |
| 传输密钥 | 控制/事件/数据流各自的 AEAD 密钥 | `Control-*`/`Events-*`/`DataStream-*`（`0x251bdf6ca` 起） |
| FairPlay 密钥 | 内容解密，独立于配对 | `fp-setup`（4CC `fp25`，`0x24fda5b40`） |

`A09.1`：配对、传输、FairPlay内容密钥互不替代——配对成功不等于能解密内容。
不能仅凭独立密钥层次推断 `/fp-setup` 失败后调用者一定保留配对/连接状态。

## 9.2 对端认证与中间人

`A09.2`：已核常规peer分支验证M2 Ed25519签名，输入为对端临时公钥、对端ID、本地临时公钥（`A14.2`）。
绑定双方公钥并使用可信ID绑定的长期公钥，才为防止密钥替换提供依据；不能只检查签名数学上成立。
callback/AppleID及目标CarPlay profile仍由 `OPEN-AP-19` 限定。

`A09.3`：`coreUtilsPairing_validateMFiCertificate`（`0x251aafbb0`）存在，说明有 MFi 证书链校验路径；
它是否在 CarPlay 连接里强制执行、失败是否致命，未取证（`OPEN-AP-34`）。

## 9.3 重放与降级

- 重放：M1 的临时公钥每次新生成，M2 的 nonce 虽是固定串，但密钥来自新 ECDH，旧密文无法复用（`A09.4`，推断）；
- 降级：SPAKE2+ 与 SRP 两条路径并存，握手里有 `"### PairSetup client SPAKE2+ not supported by server"` 的回落分支
  （`0x18bf6c24e`）。`A09.5`：客户端**不应**在没有明确理由时回落到更弱的口令路径；回落条件属 `OPEN-AP-12`。

## 9.4 客户端实现约束

1. 长期私钥只存在安全存储里，不写日志、不进文档、不进测试向量（`A09.6`）；
2. 控制/事件/数据流密钥按上下文派生，不复用（`A04.2`/`A04.3`）；
3. 任何"配对成功 = 可播放"的判断都不成立（`A09.1`）；
4. 失败不得推进为配对成功；清理/重连策略需显式定义。固件仅已核ACL错误TLV构造成功后reset，不能推广为所有M2失败都执行同样清理（`A14.4`）。
