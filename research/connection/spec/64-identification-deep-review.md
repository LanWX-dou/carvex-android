# 64 — 深度分支审阅：Identification 本批收口与后续规则


## 1. 统一审阅规则

每个将要实现的分支必须记录：

1. 原函数地址、镜像身份、实际调用入口；switch还须核查表和全局注册器。
2. 输入来自哪个端点、消息、字段、平台provider或旧状态；区分缺失、空、0、false和无效。
3. 条件成立和不成立分别做什么；检查宽度、字节序、符号扩展、位掩码、比较边界与短路次序。
4. 是否先改状态后验证；错误时保留、回滚、释放还是继续；哪些副作用跨字段/跨消息存在。
5. 返回值如何被调用者解释：0、非0和bit0不能混用；函数返回成功不等于线上消息成功。
6. 初次、重复、更新、拒绝后再次提交、超时、取消、发送失败、重连和旧回调分别如何进入。
7. 当前手机真实生产路径和测试位置；仅helper被测、未接入调用链的不能算已实现。
8. 测试预期来自哪些原条件；至少覆盖真假两侧、边界值、字段顺序和错误后状态。

状态只用明确边界：`REVIEWED-LOCAL`（所列局部分支已静态复核）、`OPEN-CALLEE`（调用依赖未闭合）、`OPEN-COMBINATION`（跨条件组合未闭合）、`NOT-RUN`（未执行）。禁止用函数数、反编译行数、测试PASS数量宣称全覆盖。原生潜在泄漏/异常宽容不应被无说明复制到托管实现；安全收紧须单独标明。

## 3. 对实施顺序有影响的新发现

### A. 不能继续使用“unknown统一忽略”规则

初次1D01的全局注册回调找不到handler，或已注册handler失败时，ForEach返回非0；主handler跳过正常required/checkAll，进入授权后拒绝分支。未知字段放最后也不能被解释为忽略后接受。

但8/9/20等**不是这份固件里的未知字段**；它们属于其他注册feature的解析器。手机旧注释和旧测试把它们误作未注册，因此应纠正分类和测试预期，不能简单把旧known集合之外全部拒绝。

### B. 初次1D01与更新1D06必须分开

原1D06只在state6处理，本消息的0..5身份字段按非NULL值合并；未更新字段保留。更新ID6的原消费者只记录不支持语言更新，其他未知更新字段记录后继续；不更新初次1D01的6/7消息能力集合，也不因此再次发1D02。

手机当前复用全量parser，要求6/7、用null覆盖缺失身份、替换消息能力集合；并且完成交接后的runtime消费链不完整。应分离数据模型/入口/测试，不能修一个parse函数后宣称全流程已修。

### C. 拒绝后的可恢复性必须与字段收紧一起处理

原1D03发送成功后state3可再次收1D01。手机本地拒绝后重抛，不能在同link继续等待；外层究竟terminal还是新attempt取决于异常类型，不可笼统写成全部断链或全部重试。若先增加字段拒绝而不处理生命周期，可能把可纠正请求变成新的连接障碍。

### D. 重复和空值没有统一答案

合法重复身份标量/消息列表是替换；13语言集合重复值会拒绝；组件0/1次数、BT子3次数及active至多一次又有独立限制。BT/Wireless的active在已审局部可以缺失。成功解析集合、出现次数、消息声明集合、feature已处理集合不能合并成一个`Set`。

### E. provider和副作用须单列

字段9的本样本provider按父连接type选择100/500，不是统一常量或只按Bluetooth/TCP选择；240另走平台插件mode4。部分失败在局部没有同ID拒绝TLV。Wireless能力标记还存在“先写info后验证组件ID”的顺序；手机实现应明确失败状态隔离，不无说明照搬半成功状态或原生资源缺陷。

## 4. 本轮执行与测试含义

重跑现有3组测试：

```powershell
.\gradlew.bat :protocol-carplay:testDebugUnitTest --tests '*IapIdentifyInfoTest' --tests '*PeerNegotiationControllerTest' --tests '*BootstrapNegotiationTest' --no-configuration-cache
```

结果：`IapIdentifyInfoTest` 2项、`PeerNegotiationControllerTest` 9项、`BootstrapNegotiationTest` 33项，共44项，0失败、0错误、0跳过；本轮实际执行测试任务。

**这只证明旧测试与当前手机行为一致**。其中“8/9以CString编码仍期待接受”“重复6/7一律拒绝”“1D06使用完整1D01形状”等预期或夹具并不等价于24A446。不能用44项通过反驳已核原分支差异；也不能把上一批744项通过当成本轮新发现已修。

本轮新增的分支回归向量仍为`NOT-RUN`。未执行原固件代码、未做CF/平台服务仿真、未取得同版本实车新抓包。文档工具只校验来源/链接/JSON，不校验互操作。

最终资料复核：四个只读复核工具在本机重新执行，41/22/33/8条函数记录分别匹配原镜像；15份去重的当前手机源码/测试快照哈希匹配。`validate_docset.py`通过（28份Markdown、21份JSON），`git diff --check`通过。核心字段分册另经独立交叉审阅，无阻断项。这些结果不提升为协议全分支运行覆盖或实车通过。

## 5. 下一批修改的依赖顺序

1. 先拆开初次识别、更新、取消与拒绝后重试的事务入口，补实际调用链和发送失败/世代测试。
2. 建立有序字段解析结果、required成功集合、全局注册分类和承载上下文；不全局放宽IapFields、不固定未知provider。
3. 逐feature接入确定的值/消息规则；未知功能与未实现消费者明确边界，不靠“认识消息ID”宣布支持。
4. 以本批原分支表重写测试oracle与夹具，检查输出字节、状态、未输出消息和清理；再跑全量回归和Kotlin编译。
5. 持续按同一规则推进蓝牙→iAP2→网络交接→AirPlay认证/SETUP→首帧/重连；当前只完成Identification的这次有界审阅，其他阶段不能沿用“全部检过”的标签。

最终目标仍是24A446成套行为，包括条件分支和旧对端路径，不是逐车型白名单，也不是只修改版本号。静态差异不直接作为某辆车连接失败的根因。
