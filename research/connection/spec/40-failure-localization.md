# “卡阶段”的定位方法

本章诊断模型是 `LOCAL_DESIGN`，不是苹果线上的错误码表。根据 [总图](01-connection-map.md) 的事实检查点定位，不依据车机 UI 阶段文字猜测根因。

## 1. 一个失败的最小记录

每次连接建立独立 `attempt_id`，记录本地单调时钟、墙钟关联点、车机匿名标识、首次/重连、网络接口与地址族、源承载与目标承载的连接世代。每条事件带方向、通道、事务标识、请求方法或消息号、字节数、解析结果及错误来源。

控制响应保留当前连接、方向、方法、CSeq（若有）和实际request/waiter关联；缺失或错误CSeq不自行补造，不能只靠相邻时间判定归属。原固件对象关联与当前App同步/异步策略不同，见 [22](22-control-wire-contract.md) 和 [60](60-implementation-differences.md)。iAP2 必须保留链路世代、控制会话 ID/版本、seq/ack 与消息方向。不同设备的墙钟未校准时，不直接相减得出传输延迟。

标准报告格式：

```text
车机界面提示：AirPlay
最后成功：当前控制连接的某次 SETUP 收到并通过结构校验
下一预期：视频专用数据端点连接 / 或前置认证结果（注明具体分支）
实际结果：连接超时 / 响应拒绝 / 没有进入发送 / 数据已发但无显示
证据：原日志行号、请求/响应关联、对端观察有无
当前结论：已定位失败边界；尚未证明根因
区分实验：只改变一个相关条件并保留成功基线
```

|---|---|---|---|---|
| 蓝牙 | 系统 bond | 目标服务发现及选定 RFCOMM socket | SDP记录/角色不匹配、端口拒绝、选错设备、权限 | SDP原响应、socket方向、远端身份、Android API错误；不能用bond代替 |

| iAP2 | Link协商 | 可用控制session与识别/认证各自完成 | session ID/版本错误、能力声明不完整、证书/挑战/状态拒绝 | 按选定session版本重建认证与识别各自事务；不假定固定先后 |
| iAP2 | 收到IdentificationInfo | required-success、条件组件、feature和授权通过 | 字段出现但回调失败、消息列表方向反、当前承载缺组件 | [12](12-identification-contract.md) 的字段结果/成功集合/拒绝TLV；本地reason与线上body分开 |
| iAP2 | 识别/认证 | 对应启动/网络配置分支 | 430x/570x能力未声明、业务gate未开、权限未授予 | 发送/接收能力表、最后请求、原状态回调、响应字段完整性 |
| iAP2/Wi-Fi | 获得网络参数 | Wi-Fi关联及IP可达 | 安全类型、频段/信道、权限、凭据、接口或路由 | 系统网络回调+接口地址/路由；不要记录明文密码 |
| iAP2/AirPlay | Wi-Fi关联 | 正确IP/端口/服务/邀请路径 | 无地址、IPv6 scope缺失、mDNS错接口、绑定错误 | 源与目的地址族、scope、SRV端口、端点来源、实际socket结果 |
| AirPlay | 服务/启动端点可用 | 与当前对端匹配的控制会话与认证 | 本地配对记录错配、错误安全分支、协议字段缺失 | 精确记录选路输入与分支、配对记录状态及拒绝阶段；不泄漏密钥 |
| AirPlay | TCP连接 | 对应控制请求的有效响应 | 无发送、发送阻塞、CSeq/framing解析错、对端拒绝 | SEND/完整WRITE/REPLY区分、Content-Length和CSeq关联、双向原始记录 |
| AirPlay | 已读到响应 | 当前waiter完成与方法字段校验 | 只有header无完整body、unmatched响应、本地解析失败 | expected/received长度、reader模式、原请求/token或pending键、原status与本地error域 |
| AirPlay | SETUP 2xx | 回复结构校验、事件/流端点按路径建立 | 缺字段/类型错、错误流类型/数量、端口不可达 | 记录实际响应键类型和消费结果；2xx不等于结构有效 |
| AirPlay/黑屏 | 视频SETUP结构有效 | 专用视频transport可用 | 数据端口错误、地址族/绑定错、对端未监听 | 控制与媒体socket分别记录，确认使用回复dataPort |
| 已连接/黑屏 | 视频socket可写 | 配置record与可解码帧被对端接收 | 配置缺失、NAL格式、长度/端序、密钥或时钟错 | 原record长度/hash与接收/解密/解码观察，首次关键帧前配置 |
| 已连接/黑屏 | 对端解码成功 | 资源允许且实际显示 | 屏幕资源/输出状态、显示呈现 | 只读对端日志（如可取）、车机录像/人工确认，不能仅看编码器预览 |
| 曾显示后停顿 | 曾实际显示 | 后续帧持续更新 | 网络背压、编码停产、控制/keepalive断开、资源变化 | 同时记录编码产出/发送耗时/队列/响应/显示时间线 |
| 重连失败 | 上次显示过 | 旧资源释放、新会话独立开始 | 旧socket/回调/ID残留、缓存身份与对端不符 | 每个attempt资源和epoch清单；禁止把上一会话成功认证直接套本次 |

## 3. 必须分开的认证

系统蓝牙 bond、iAP2 配件认证、AirPlay 配对/验证、媒体加密材料协商、用户连接许可属于不同层。记录各自的“开始、输入来源、证据绑定、成功/拒绝/未知”，不能归并为一个 `authenticated=true`。

一次收到证书不等于信任验证通过；验证历史挑战的签名不等于对当前新挑战认证成功；取得媒体密钥不等于画面已解密。细节见两个协议章节，证据不足时保留未知。

## 4. 超时和恢复

各章已核实的原状态/回复错误优先；未核实原定时器时，不编造“苹果必须在N秒内”的值。当前Android超时只用于解释当前App：见[差异](60-implementation-differences.md)。

一个超时至少拆为：排队/锁等待、网络连接、请求发送、等待响应、平台操作、整体尝试预算。到期报告哪一个计时器拥有本次失败及最后活动，不统一标“连接失败”。

源蓝牙断开与目标AirPlay失败分开看：切换过程中源断开可能是路径行为，不能直接推为视频终止；但也不能在目标未准备好时把断开当作交接成功。新尝试不得消费旧尝试的晚到成功回调。

本章不授权降级认证、删除配对记录、重置车机或修改车机；这些操作不是默认的诊断步骤。
