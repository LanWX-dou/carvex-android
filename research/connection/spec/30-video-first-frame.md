# 30 视频：从已建控制会话到首帧、持续显示和重连

研究日期：2026-10-29。基线：24A446 的 iPhone 发送端；本章不是所有 iOS／车机的通用定值表。

当前证据等级：原始镜像哈希校验、函数字节与镜像比对、局部反编译及关键指令复核。**本轮没有取得一个与 24A446 对齐的端到端无线 CarPlay 抓包，也没有新做实车显示验收。** 因而本章给出已确认的生产路径、排障门槛与待补证项，不把“能构造报文”写成“车机已接受”。

## 2. 已确认的局部顺序，不是推测的完整上线时序

```text
对端显示描述、会话和安全上下文
  → 创建 screen endpoint 对象                       [V01]
  → Resume 内请求 setup-stream、解析成功响应           [V02,V03]
  → 从响应取 NetworkPortData，建立屏幕数据 transport    [V03,V04]
  → 安装取编码样本的回调，进入 resumed                 [V03]
  → 样本格式／几何变化时生成配置记录 type=1             [V05,V06]
  → 生成帧记录 type=0，按协商的 cryptor 加密载荷         [V05,V07,V08]
  → 交给 transport；对端接收／解密／解码／显示          [接收侧验收尚缺]
```

这里的 resumed、编码样本计数与 socket 写成功，均不是对端显示证明。RECORD、资源模式通知、运行时 iAP2 通道与上述对象操作的完整跨模块偏序，须与控制会话章及真实时间线结合；本章不凭名称规定它们必须依次执行。

V03（`___screenstream_Resume_block_invoke @ 0x251bd65d8`）的关键行为：调用 session setup 接口得到响应与 cryptor；读取 `_kAPSenderSessionStreamKey_NetworkPortData`；使用端口构造 transport stream；设置取样回调；在本地启动成功后才发布 resumed。不能先把编码输出当成已配置好的数据通道。

## 3. 逐阶段合同：九个问题逐项回答

### V-A：显示能力与屏幕对象

1. **前置条件**：本地已有可用 endpoint 描述／session；在 `APEndpointStreamScreenCreate` 选定分支需要非空显示数组，无法取得所需对象时返回错误。[V01]
2. **发起方与承载**：手机本地读取已取得的对端显示描述并创建屏幕对象；不是此函数直接发送一个“分辨率请求”。线上显示信息获取见控制会话章。
3. **输入与输出**：内部 `DisplayDescriptionArray` → 每屏描述 → 屏幕对象；`carEndpoint_setupScreenStreams` 明确调用 `APEndpointStreamScreenCreate`。[V10]
4. **字段条件**：见第 4 节。内部常量 `PixelSize`、`MaxFPS` 不可未经映射就认定为线上同名字段。
5. **定值或动态**：尺寸、几何、UUID、帧率来自对端／选定显示与本地策略；本轮未证明某一固定分辨率、码率或 GOP 是所有车机要求。
6. **接受／拒绝条件**：这里证实的是发送端本地校验，非车机拒绝规则；数组为空、所需 UUID 缺失等会走失败分支。不能将这类失败改名为车机“不支持视频”。
7. **成功证据**：实际选择的 display、其像素尺寸、对应对象创建成功。仅打印对端支持的显示列表仍不够。
8. **超时／重试／退出**：这两个本地构造函数没有提供一个可直接引用的全链路超时；上层取消与重试调度待追。失败应保留字段缺失和函数错误码，不猜默认值。[待验证 V-OPEN-01]
9. **下一事件**：选定屏幕对象的 setup/resume；不是立即“已显示”。

### V-B：屏幕流 SETUP 与数据通道

1. **前置条件**：有效会话、选定屏幕类型／选项、必要的安全上下文；V02 会检查取消和 session 状态。[V02]
2. **发起方与承载**：手机通过已有控制 transport 发 setup 操作；数据流随后单独建立。
3. **请求／响应**：请求含一项 stream 的集合；本次审计的单流函数要求响应集合恰有一项且 `type` 等于请求类型。[V02]
4. **字段条件**：`type`、生成的连接标识、调用者选项、返回的数据端口；完整线上字符串与所有条件字段仍须由生产者、序列化器及接收端三方闭合，见第 4 节。
5. **定值或动态**：110/111 是本屏幕实现的类型分支；连接标识每次由生成器产生，数据端口取响应，不使用固定车机端口。`streamID` 与 `streamConnectionID` 不能混为一谈。
6. **接受／拒绝条件**：V02 的发送端检查包括响应类型、项数、字段读取错误、取消；这些是手机接受响应的条件，不是车机接收请求的完整规则。
7. **成功证据**：SETUP 成功响应及可解析的数据端口，随后数据 transport 的连接／启动成功。HTTP/RTSP 200 本身不证明这两层都完成。
8. **超时／重试／退出**：精确网络等待预算及自动重试次数尚未从这一函数闭合；失败记录应保留控制错误、解析错误和数据连接错误三类。不要把 Android 的 URL 回退当成 iPhone 必经流程。[待验证 V-OPEN-02]
9. **下一事件**：配置记录和可解码帧进入已建立的数据通道；控制会话启动许可／资源状态仍是独立条件。

### V-C：配置与首个帧记录

1. **前置条件**：screen transport 可用、编码样本可取、所选 cryptor 准备完成。
2. **发起方与承载**：手机样本回调组装记录交给屏幕 transport。此回调返回 buffer 不等于 socket 已写出。[V05]
3. **消息格式**：本章确认的记录路径是 128 字节头加正文，配置 type=1，帧 type=0；不是音频 RTP 包。[V05,V06]
4. **字段条件**：配置存在变化条件；帧正文长度包含密码附加输出及可选尾段，不应只填编码帧原长度。已确认字段见第 5 节。
5. **定值或动态**：头长／记录类型是路径内常量；正文长、几何、时间、配置内容、密码状态动态生成。不能复制一包 iPhone 头反复使用。
6. **接受／拒绝条件**：本轮发送端有连续 buffer、crypto 返回码、格式／附件校验。目标车机的边界值、可接受 profile、解码限制尚未逐车取证。
7. **成功证据**：区分配置已构造、帧已构造、transport 已接收、网络已发送、接收端已解密及解码。最终首帧判据必须包含车机实际显示。
8. **超时／重试／退出**：加密或样本处理失败进入 fatal error 通知路径；原地加密失败不证明载荷与 nonce 已回滚，不能不加区分地重试同一对象。[V05,V07,V13]
9. **下一事件**：持续显示不同内容，并证明时间线／队列前进；单张静态截图只证明一个时刻。

### V-D：持续更新、停止与重连

1. **前置条件**：已经取得首帧的外部显示证据。
2. **发起方与承载**：编码样本、数据 transport、控制会话分别可能停止／失败，不能用一条连接心跳代替三者。
3. **消息／操作**：本地 Suspend 停统计 timer、暂停生产侧、拆 transport、清理队列并发布 resumed=false。[V11]
4. **字段／状态**：teardown 移除数据回调、清空 transport 引用及 codec 缓存、释放 cryptor 等关联状态；某些上层配置被保留。具体 wire TEARDOWN 字段由控制章单列。[V12]
5. **定值或动态**：新连接是否复用身份与配对资料属于上层；屏幕数据口、连接标识、密码上下文不可从“已配对”推出可复用。
6. **成功／失败条件**：本地停止成功与车机确认释放是两个证据；异常断网时可能无法收到 TEARDOWN 响应，不能阻塞清理直到永远。
7. **成功证据**：旧生产者不再向旧连接写入；新会话独立完成 SETUP、配置、首帧及持续更新。最后一项仍需车机显示。
8. **超时／重试／退出**：V12 有布尔条件决定是否调用 session teardown；[24](24-disconnect-reconnect.md) 已核对Suspend传0、fatal cleanup传1的两条生产链。其它原因、精确延时／重试与上层整会话关闭仍待追，不能归为同一包序。[V-OPEN-06]
9. **下一事件**：重新进入合适的连接阶段，而不是设置一个 UI “connected” 标志后恢复旧帧队列。

## 5. 记录格式：只写有本轮证据的范围

固定头长 128 字节由两处构造器直接分配 `0x80` 并写字段证明；在这条 ARM64 小端记录路径中整数原位写入，未见这些字段的网络序转换。[V05,V06]

| 偏移／类型 | 配置记录 | 帧记录 | 证据／限制 |
|---|---|---|---|
| `0x00`，32位 | 配置正文长度 | 本条正文总长，含计算出的附加长度 | V06 `0x251b4407c`；V05 `0x2519b0e88`；不得将frame总长简化成NAL原长 |
| `0x04`，8位 | 1 | 0 | V06 `0x251b44080`；V05 `0x2519b0e8c` |
| `0x05`，8位 | 来自配置存储字段 | bit7来自一附件状态，bit4来自同步附件处理结果 | V06 `0x251b44084–88`；V05 `0x2519b1038–1058`；不能仅由这些bit认定实际NAL为IDR |
| `0x06`，8位 | 基础0x12，受多个本地条件修改；cryptor存在会置bit2 | 本轮未建立通用语义 | V06 `0x251b4408c`起；不是恒定0x16的苹果标准 |
| `0x07`，8位 | 1 | 本轮未建立通用语义 | V06 `.c` 对该字节赋值 |
| `0x08`，64位 | 由网络时钟转换结果组装 | 由网络时钟转换结果组装 | V05,V06；完整单位／锚点／回退策略尚未闭合 |
| 配置几何 | 多个浮点值由当前配置生成 | 不适用 | V06；几何来源与全部坐标单位仍需逐项映射 |

在 V05 的 `avc1` 且一个模式位未置位的分支，会读取格式描述扩展中的 codec data，缓存变化可触发配置重发；配置构造器将缓存 data 作为 type1 正文。[31](31-video-codec-contract.md) 已追加原常量/类型检查及 `avcC` 到正文的局部链，还精确核对了两个帧附件标志：**仍不能认定全部模式固定4字节NAL长度、每帧必有SPS/PPS或支持同一H.264 profile**。[V05 `.c` 424起；V06；VC-C01/02]

本地拼装顺序确认为：若产生了配置buffer，先配置记录，再帧头，再帧载荷。证据：V05 `.s` `0x2519b1178–11bc`。这证明局部buffer顺序，不证明对应字节已到车机。

## 6. 视频密码路径不能照搬音频

V02 对110/111并非无条件使用同一个 cryptor：`SupportsCoreUtilsPairingAndEncryption` 对应的内部能力分支影响 key-holder 与 cryptor。现代分支取32字节输出材料并以 flag=0 创建 ChaCha cryptor；另一分支调用 legacy key／IV接口。[31](31-video-codec-contract.md) 已从原缓存解出后者到 `APSCryptorCTRCreate` 的直接跳板，但完整CTR材料、参数与生命周期仍未闭合。[V02 `.c` 744–795；V14；VC-S01/VC-P01]

已独立核对的现代分支相关事实：

- `coreUtilsKeyHolder_CreateEncryptionKeysForStream` 构造 `DataStream-Salt` 加所传整数十进制字符串；两个标签分别是 `DataStream-Input-Encryption-Key`（长度31）及 `DataStream-Output-Encryption-Key`（长度32）。对应 requested output length 与输出指针是不同参数，不能将标签长度当成密钥长度。[V09]
- `_sbpd_encryptBBuf` 把完整header buffer与载荷分别传入 cryptor，载荷输入输出指针相同，即原地处理；crypto附加输出追加到正文。连续长度不等于总长时拒绝。[V07]
- 已读取的 ChaCha encrypt 方法将传入的头／长度交给AAD处理，再处理载荷；flag=0时附加输出16字节，flag非0时24字节并追加8字节计数材料。内部8字节计数按小端进位。[V08]
- [31](31-video-codec-contract.md) 已补上述包装器→ChaCha虚表/导入符号及新对象零填充→初始计数0的原证据；仍不是运行验证，不允许旧对象在恢复时任意归零。不得把“头长128／附加16”外推到 legacy、UDP、所有profile。
- 配置记录的构造与帧载荷加密路径分开；有可选尾段时同一帧头可能用于第二次 crypto 调用。不能简单规定“每条记录必加密一次并只推进一次nonce”。[V05 `.s` `0x2519b1150–1168`、`0x2519b12e8`起；V07]

在取得精确安全上下文、stream标识、key方向与nonce生命周期证据前，不做在线轮换算法／AAD的试探。`cryptor==NULL` 的局部no-op不是认证失败可明文降级的许可。

## 7. 实际投屏验收：不能由发送侧代替接收侧

下列为项目验收要求，不是宣称固件内存在这些测试时长或日志键。

| 级别 | 必需证据 | 尚不能证明 |
|---|---|---|
| P0 编码 | 尺寸、codec config摘要、输出帧时间／序号 | 网络建立 |
| P1 网络发送 | 本次连接标识、目标地址／端口、实际写出字节和时间 | 对端已解密 |
| P2 接收 | 对端或合法被动抓包可对应同一连接的字节 | 应用接受和解码 |
| P3 解密／解码 | 可取得的接收端日志、离线解码结果及配置对应关系 | 实车显示；离线解码不等于目标车机解码 |
| P4 首帧显示 | 车机屏幕出现本次测试的唯一可辨内容，带时间关联 | 持续更新／重连 |
| P5 持续更新 | 例如带秒数／递增帧号的画面持续变化，记录冻结与恢复 | 未测试时长以外的稳定性 |
| P6 重连 | 首次配对、已配对重连、异常断线后各自重新达到P4/P5 | 所有车型和所有异常都通过 |
